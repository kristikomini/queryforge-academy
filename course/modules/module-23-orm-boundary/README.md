# Module 23 · The ORM boundary

> Site chapters: [38](../../../site/chapters/38-the-orm-boundary.html)

## 1 · The idea

Here is the fact that makes this module a career skill rather than a topic:

> **Most SQL you will be asked to fix was generated by an ORM.**

You will be handed a slow query nobody wrote. Your job is to read it, work out which
line of C# or Java or Python produced it, and fix it *there* — because fixing the SQL
by hand is a change that the next model update overwrites. Reading generated SQL back
to the code that generated it is a distinct skill, and it is most of what a database
person does in a team that uses an ORM.

The dominant defect is **N+1**, and what makes it dangerous is how it hides:

> **N+1 shows up as a huge call count on a trivial query, never as a slow query.**

Load a hundred orders, then touch `order.Customer` inside the loop, and you have issued
one hundred and one queries. Each takes two milliseconds. Not one of them appears in a
slow-query log, no threshold is crossed, no alert fires — and the page takes two
seconds. This is why the diagnostic rule is about *sorting*:

> **Sort by call count to find N+1. Sort by total time for everything else.**

Average duration is the metric that hides N+1 completely, because the average is
excellent.

The fix is eager loading, and the useful move in a conversation is to **name it in the
developer's own framework** — `Include` in EF Core, `joinedload`/`selectinload` in
SQLAlchemy, `includes` in Rails, `JOIN FETCH` in JPA. Saying "you need eager loading
here, `Include` on the Customer navigation" gets the fix made; saying "the ORM is
generating N+1 queries" gets you agreement and no change.

But eager loading has its own trap, and it is the second-order knowledge worth having:

> **Two eager-loaded collections in one query is a Cartesian explosion. Split the
> queries.**

`Include(o => o.Lines).Include(o => o.Payments)` is the fan-out from module 08, produced
by a framework instead of by hand — three lines and two payments become six rows, and
the ORM materialises and de-duplicates them in application memory. EF Core's split
queries and SQLAlchemy's `selectinload` exist precisely for this.

Three more failure modes that look like nothing in the code:

**An ORM selects every mapped column.** Your entity has twenty columns; your list view
shows three. That is the covering-index argument from module 05 being lost by default.
Project into a DTO — `Select(new { ... })` — when it matters.

**Untranslatable predicates get evaluated client-side.** A filter the ORM cannot convert
to SQL is applied in application memory *after* fetching the rows — so a `WHERE` that
should have returned ten rows fetches ten million first. Newer EF Core versions throw
instead of silently doing this, which was a good decision.

**Parameter type mismatch silently defeats an index.** The ORM sends `nvarchar` for a
`varchar` column, or a `bigint` for an `int`; the engine inserts an implicit conversion;
the index becomes unusable. Nothing in the code or the generated SQL looks wrong, and the
only evidence is a convert warning in the plan.

The closing position is the mature one, and it is worth being able to state as a
recommendation rather than a complaint:

> **ORM for writes, hand-written SQL for reports.** That is CQRS without the ceremony.

Writes are where an ORM genuinely earns its place — change tracking, unit of work,
identity map, validation. Reports are where it does not: a report is a projection over
a shape that has nothing to do with your object graph, and it is the thing you will
spend the most time fixing if you let a framework write it.

## 3 · Do it

### a) Build an N+1 and watch it not be slow

```bash
node api/server.mjs
```

The service has no ORM, so build the pattern by hand against the reference database:

```sql
-- One query for the list...
SELECT id, customer_id FROM orders LIMIT 100;
-- ...then, for each of the hundred rows, one more:
SELECT name FROM customers WHERE id = ?;
```

Time a single customer lookup — it is sub-millisecond, and would never appear in a slow
query log at any threshold you would set. Then multiply by a hundred and compare with
the one query that answers the whole thing:

```sql
SELECT o.id, c.name FROM orders o JOIN customers c ON c.id = o.customer_id LIMIT 100;
```

Same data. One round trip instead of a hundred and one. Now say which of the two shapes
a per-query monitoring dashboard would flag.

### b) Reproduce the double-Include explosion

```sql
-- What .Include(o => o.Lines).Include(o => o.Payments) generates:
SELECT o.id, l.line_no, p.id AS payment_id
FROM orders o
LEFT JOIN order_lines l ON l.order_id = o.id
LEFT JOIN payments    p ON p.order_id = o.id
WHERE o.id = 3;
```

Count the rows against the line count and the payment count. The ORM will hand your
application the right objects, having transferred and de-duplicated the product of the
two collections. Now write the split version — two queries, each to one collection — and
compare the total rows transferred.

### c) Feel the cost of selecting every mapped column

```sql
EXPLAIN QUERY PLAN SELECT customer_id, placed_at FROM orders WHERE customer_id = 7;
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE customer_id = 7;
```

The first can be served by `ix_orders_cust_date` alone. The second must visit the table
for every row, because the index does not contain every column. An ORM issues the second
by default — that is the covering-index win it cannot take.

### d) Defeat an index with a type mismatch

```sql
CREATE TABLE t (code TEXT PRIMARY KEY, v INTEGER);
INSERT INTO t VALUES ('00042', 1);
EXPLAIN QUERY PLAN SELECT * FROM t WHERE code = '00042';   -- seeks
EXPLAIN QUERY PLAN SELECT * FROM t WHERE code = 42;        -- does not
```

The second is what a parameter typed as a number against a text column produces. The
answer may even be right. The index is gone and nothing in the application code shows it.

### e) The exercise

Take `leaderboard` from [`api/sql/queries.sql`](../../../api/sql/queries.sql) and write,
in the ORM you know best, the code that would produce an equivalent result. Then write
down every difference between what you would get and what is in the file: the columns
selected, the joins, whether the `ORDER BY` can use the index, and how the `LIMIT` is
applied. Finally, decide which of those differences you would accept in a real codebase
and which you would drop to SQL for — with the reason. That final judgement is the
interview answer to "when would you not use the ORM".

## 4 · Golden rules

- Most SQL you are asked to fix was generated. Reading it back to the code is a distinct skill.
- N+1 shows up as a huge call count on a trivial query, never as a slow query.
- The fix is eager loading, named in the developer's own framework.
- Two eager-loaded collections in one query is a Cartesian explosion; split the queries.
- An ORM selects every mapped column. Project into a DTO when it matters.
- Untranslatable predicates get evaluated client-side, after fetching everything.
- Parameter type mismatch silently defeats an index and looks like nothing at all.
- Sort by call count for N+1; sort by total time for everything else.
- ORM for writes, hand-written SQL for reports. That is CQRS without the ceremony.
- An ORM is not a defence. Its raw-SQL escape hatch is injectable like anything else.
- N+1 is invisible in every per-query report. Sort by total duration to see it.

## 5 · Interview questions

**“What is the N+1 problem and how do you find it?”**
One query to fetch a list, then one more per row to fetch a related entity — so a
hundred rows cost a hundred and one round trips. It is hard to find because every
individual query is fast and trivial: nothing crosses a slow-query threshold and the
average duration looks excellent. You find it by sorting the query statistics by **call
count**, or by total duration, never by average. The fix is eager loading, and the useful
thing is to name it in the developer's own framework.

**“You fixed an N+1 with eager loading and now it is slower. Why?”**
Probably two collections eager-loaded in one query, which is a Cartesian product: each
child of one collection is repeated once per child of the other, and the ORM transfers
and de-duplicates all of it in memory. Split it into separate queries — EF Core's split
queries, SQLAlchemy's `selectinload` — so each collection is fetched once.

**“Why is `SELECT *` a particular problem with an ORM?”**
Because an ORM must populate the whole mapped entity, so it selects every mapped column
whether you use them or not. That is the covering-index benefit lost by default: an index
that contains the two columns your list view shows cannot serve the query, so the engine
visits the table for every row. Projecting into a DTO restores it, and is the thing to
reach for on read-heavy list endpoints.

**“How can an ORM silently defeat an index?”**
By sending a parameter whose type does not match the column — `nvarchar` against a
`varchar` column, a wider integer against a narrower one. The engine inserts an implicit
conversion around the column, which makes the predicate non-sargable, so the index is
unusable. The result is still correct and neither the application code nor the generated
SQL looks wrong; the only evidence is the convert warning in the execution plan.

**“Should we stop using the ORM?”**
No — use it for what it is good at. Writes benefit genuinely from change tracking, unit
of work and validation, and hand-writing them is a lot of code for little gain. Reports
and list endpoints are where an ORM struggles, because they are projections over shapes
that have nothing to do with the object graph. ORM for writes, hand-written SQL for
reads that matter: that is CQRS without the ceremony, and it is a recommendation rather
than a complaint.
