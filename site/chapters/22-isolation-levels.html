Isolation levels and the anomalies they allow

Dirty read, non-repeatable read, phantom, lost update — each mapped to the level that still permits it.

From the advert

“Esperienza su ambienti di produzione” — and this is the chapter that explains the bugs that only ever happen under load.

The four anomalies

🧒 Simple

Two people writing in the same notebook at the same time. How much are they allowed to see of each other's half-finished sentences? Letting them see everything is fast and produces nonsense. Letting them see nothing until the other has finished is safe and slow. The isolation level is where you set that dial.

AnomalyWhat happensConcrete example
Dirty readYou read data another transaction has not committedYou see a €5 000 transfer that is then rolled back
Non-repeatable readYou read the same row twice and it changedA stock check says 5, then 3, inside one transaction
Phantom readYou run the same query twice and new rows appear“Orders today” returns 40, then 41
Lost updateTwo read-modify-writes; one overwrites the otherTwo agents both set the discount, one silently wins

🎓 The standard describes anomalies, not implementations

Each engine implements these differently and some of them exceed the requirement. PostgreSQL's REPEATABLE READ is a genuine snapshot and prevents phantoms too, even though the standard allows them. InnoDB's REPEATABLE READ — its default — also prevents phantoms for plain reads, using next-key locks, but not for locking reads without care. Oracle offers only READ COMMITTED and SERIALIZABLE; asking for the other two gets you one of those. Naming one such divergence is what marks the answer as experience rather than a memorised table.

SQL Server is the interesting case

SQL Server historically used pessimistic locking: at READ COMMITTED a reader takes shared locks and therefore blocks on writers. That is why so much legacy T-SQL is peppered with WITH (NOLOCK) — it is people working round reader/writer blocking. Two settings change the model entirely:

SettingEffect
READ_COMMITTED_SNAPSHOT ONDatabase-level. READ COMMITTED now uses row versions, so readers never block writers — PostgreSQL-like behaviour, and usually the right change
ALLOW_SNAPSHOT_ISOLATION ONEnables the explicit SNAPSHOT level: a consistent view for the whole transaction
⚠ Trap — WITH (NOLOCK) is not “a bit faster”

NOLOCK is READ UNCOMMITTED under another name, and it does not merely risk reading uncommitted rows. It can also:

  • Miss committed rows entirely, or return the same row twice, if a page split moves rows while your scan is passing.
  • Fail with error 601 (“could not continue scan with NOLOCK due to data movement”).

So a financial report with NOLOCK can produce a number that was never true at any instant. The correct fix for reader/writer blocking is READ_COMMITTED_SNAPSHOT, not a hint on nine hundred queries. Being able to say this precisely is one of the strongest single answers available in a SQL Server interview.

🎓 Lost update is the one that actually bites

It is not in the standard's table, it happens at the default isolation level in every engine, and it produces no error. The three fixes, in order of preference:

  1. Make the update atomic: SET qty = qty + 5 rather than reading then writing. Free, and it eliminates the window entirely.
  2. Optimistic concurrency: a version column and WHERE version = ?; zero rows affected means you lost, so retry.
  3. Pessimistic locking: SELECT … FOR UPDATE, holding a lock from read to write. Correct, and it costs concurrency.

What SERIALIZABLE really costs

PostgreSQL implements it as Serializable Snapshot Isolation: transactions run optimistically, and the engine aborts one with a serialization_failure (SQLSTATE 40001) if the interleaving could not have happened serially. That means your application must be prepared to retry — a serialisable transaction is not a transaction that always succeeds, it is one that always succeeds or tells you it did not. SQL Server implements it with range locks instead, so the cost appears as blocking and deadlocks rather than as aborts.

  1. Four anomalies: dirty read, non-repeatable read, phantom, lost update.
  2. READ COMMITTED is the default nearly everywhere and permits everything except dirty reads.
  3. The standard names anomalies, not implementations. PostgreSQL's REPEATABLE READ also prevents phantoms; Oracle offers only two levels.
  4. SQL Server readers block writers until READ_COMMITTED_SNAPSHOT is on. That setting, not NOLOCK, is the fix.
  5. NOLOCK can miss committed rows and return duplicates during page splits — not just read uncommitted data.
  6. Lost update is not in the anomaly table, happens at the default level, and raises no error.
  7. Prefer an atomic update (SET x = x + n) over read-modify-write; then optimistic concurrency; then locking.
  8. PostgreSQL's SERIALIZABLE aborts transactions with SQLSTATE 40001. Using it means writing a retry loop.

Interview questions this chapter answers

What isolation levels are there, and what does each prevent?

Read uncommitted (prevents nothing), read committed (no dirty reads — the usual default), repeatable read (no non-repeatable reads), serializable (no phantoms either). Then add that engines differ: PostgreSQL's repeatable read is a full snapshot and prevents phantoms, Oracle only implements two of the four.

Is WITH (NOLOCK) a good idea?

Rarely. It is read uncommitted, so it can read rows that get rolled back — and worse, during page splits it can skip committed rows or return the same row twice, producing a total that was never true. If the problem is readers blocking writers, the fix is READ_COMMITTED_SNAPSHOT at database level.

Two users edit the same record. How do you stop one overwriting the other?

If it is a simple increment, make the write atomic: SET qty = qty + n. Otherwise optimistic concurrency — a version column, WHERE version = ?, and treat zero rows affected as a conflict to report or retry. Pessimistic locking works but holds a lock across the user's thinking time, which is usually unacceptable.
