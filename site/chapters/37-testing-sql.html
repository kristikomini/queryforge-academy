Testing SQL, and CI against a real engine

Fixtures, transactional rollback, tSQLt and pgTAP, and why an in-memory fake is not a database.

No advert asked for this

The thing that separates “writes SQL” from “ships SQL”. No junior advert asks. Every senior interview does.

What is worth testing

🧒 Simple

You do not need to test that the database can add up. You need to test the things you decided: that the wrong data is refused, that the rule about who can see what still holds, and that the report agrees with the invoice.

TestWorth it?
Constraints reject bad data✅ Yes. It is your specification, executable
A view or report returns the right numbers for known input✅ Yes. This is where the money is
A stored procedure's behaviour, including its error paths✅ Yes. It is code with no other tests
Migrations apply cleanly to a real, populated schema✅ Yes. And that they are re-runnable
Row-level security actually isolates tenants✅ Yes. Nothing else will tell you
That an index is used⚠ Fragile — the plan legitimately changes with data volume. Test the outcome, not the plan
That SELECT 1 + 1 is 2❌ No

Making tests independent

🎓 Three strategies, in increasing order of cost and fidelity
  1. Transaction rollback. Each test runs inside a transaction that is always rolled back. Fast, and the isolation is perfect. Its one limitation is real: you cannot test anything about transactions or concurrency, because you are already inside one.
  2. Truncate and reseed. Slower, and it lets a test commit — so deadlocks, isolation levels and triggers that depend on commit are testable.
  3. A fresh container per suite. Testcontainers or an equivalent starts a real engine, applies the migrations and destroys it. The slowest and the only one that also tests the migrations themselves.
⚠ Trap — the in-memory fake is not a database

Testing against an in-memory provider, or SQLite when you deploy PostgreSQL, cheerfully passes tests that fail against anything you would ship. It has different type coercion, different NULL and collation behaviour, different transaction semantics, and it does not implement most of the SQL you actually wrote. Test against the engine you deploy, at the version you deploy — a container makes this cheap enough that there is no longer an excuse. (This site's own accounts service runs SQLite in production, so its tests use SQLite honestly — which is the same principle, not an exception to it.)

The frameworks

Or just test from the application's test framework

A perfectly good option, and often the right one: the tests live with the rest of the suite, run in the same CI job, and use tooling the team already knows. What you lose is the ability to test objects the application never calls directly. What you gain is that they actually get run.

Fixtures: deterministic, minimal, named

✔ Three properties of a fixture that ages well
  1. Deterministic. No random(), no now() — pass the clock in, or freeze it. A test that fails on the 31st of the month, or in a different time zone, is worse than no test. (The reference database's seed is deliberately generated with arithmetic rather than random() for exactly this reason.)
  2. Minimal. Insert the three rows this test needs, not the whole demo dataset. A shared fixture means changing one test breaks four others.
  3. Named for the scenario, not the data: an_order_that_has_shipped, not order_7. The name is what the failure message will say.

In CI

🎓 Two CI checks nobody thinks of and everybody needs
  • Run the migrations twice. If the second run fails, the migration is not re-runnable — which matters enormously on MySQL and Oracle, where a failed migration cannot be rolled back and will be re-run by hand at the worst possible moment.
  • Assert schema invariants, not just behaviour. Every foreign key has an index; no column is FLOAT in a monetary table; every table has a primary key. These are three queries against the catalogue, they run in a second, and they catch the class of mistake code review misses. The reference database ships exactly these as reference/labs/schema-invariants.sql.
  1. Test the decisions you made — constraints, reports, procedures, security — not the engine's arithmetic.
  2. Transaction rollback per test is fast and perfect, except for anything about transactions.
  3. An in-memory fake is not a database. Test against the engine and version you deploy.
  4. Fixtures must be deterministic: no random(), no now().
  5. Fixtures must be minimal and named for the scenario, because the name is the failure message.
  6. Do not assert on execution plans; assert on outcomes. Plans legitimately change with volume.
  7. Run migrations twice in CI. If the second run fails, they are not re-runnable.
  8. Assert schema invariants from the catalogue: every FK indexed, no float money, every table keyed.

Interview questions this chapter answers

How do you test SQL?

Against a real engine at the deployed version, usually in a container, with migrations applied from scratch. Each test isolated by a rolled-back transaction, with minimal deterministic fixtures named for the scenario. I test what I decided — constraints rejecting bad data, reports returning known numbers, procedures including their error paths — not that the engine can add up.

Why not use an in-memory database for tests?

Because it is a different implementation: different type coercion, different null and collation behaviour, different transaction semantics, and it does not support most of the SQL you actually wrote. It passes tests that fail against the thing you deploy, which is worse than having no tests, because it produces confidence.

What would you check in CI besides the tests passing?

That migrations apply to an empty database and then apply again without failing — otherwise they are not re-runnable, which matters on engines where DDL is not transactional. And a few schema invariants queried from the catalogue: every foreign key has a leading index, no monetary column is a float, every table has a primary key.
