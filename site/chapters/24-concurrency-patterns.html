Concurrency patterns that actually hold

Optimistic vs pessimistic, SELECT … FOR UPDATE SKIP LOCKED, and a work queue in a table done properly.

No advert asked for this

The reference database is built on these. They are also the fastest way to sound senior in an interview.

Optimistic concurrency

🧒 Simple

Two ways to share a book. Pessimistic: take it off the shelf and hold it, so nobody else can even open it while you decide what to write. Optimistic: note which edition you read, go away and think, then come back and say “I want to change page 4 of edition 7” — and if it is now edition 8, you are told, and you look again.

🎓 Professional

A version column, incremented on every write, and every update carrying the version it read. The row count is the answer: one means you won, zero means somebody changed it since you read it, so you reload and either retry or tell the user. It costs one integer column and holds no lock across the user's thinking time — which is why it is the default choice for anything a human edits.

EngineIdiomatic version column
AnyAn INTEGER you increment yourself. Portable, obvious, testable
SQL Serverrowversion / timestamp — maintained automatically, database-unique
PostgreSQLThe system column xmin works, and is what Hibernate uses; an explicit column is clearer
OracleORA_ROWSCN, with ROWDEPENDENCIES enabled on the table
⚠ Trap — a timestamp is not a version

WHERE updated_at = ? looks equivalent and is not: two updates inside the same clock tick produce the same value, and clock resolution is coarser than you think (SQL Server's DATETIME is accurate to about 3 ms). Under load that is a lost update with no error. Use a counter or a real rowversion.

Pessimistic locking, and SKIP LOCKED

✔ SKIP LOCKED is the whole reason a queue in a table works

Without it, ten workers polling the same job table all block on the first unclaimed row and you have a one-worker system with nine spectators. With it, each worker takes a different row on the first attempt. PostgreSQL 9.5+, MySQL 8+, Oracle. SQL Server spells it WITH (UPDLOCK, READPAST). It converts “a queue in a database is a bad idea” into “a queue in a database is fine up to a few thousand jobs a second”.

A work queue in a table, done properly

Three details that make it production-grade
  1. A claim timeout. A worker that dies holding a claim must not hold the job forever. Reclaim anything claimed more than n minutes ago.
  2. An attempts counter and a dead-letter rule. A message that fails permanently will otherwise be retried until the end of time.
  3. A partial index on exactly the worker's predicate. WHERE published_at IS NULL — the index stays tiny however large the table grows, because published rows leave it entirely.

The transactional outbox

🧒 Simple

You need to save the order and send the confirmation email. Send first and the save might fail — you promised something that did not happen. Save first and the send might fail — it happened and nobody was told. So instead you write the email into a letters to post box in the same notebook, in the same stroke of the pen, and a postman empties the box later.

🎓 Professional

There is no transaction spanning your database and a message broker, so “save and publish” is a dual-write problem with no atomic solution. The outbox converts it into a single local transaction: the row and the message are written together, and a separate worker reads the outbox and publishes. Delivery becomes at-least-once, so consumers must be idempotent (chapter 20) — and that is the honest trade, not a flaw to hide.

The last-unit problem

Two customers order the last item at the same moment. Three defences, and the strongest one is not the code:

✔ Say this in an interview

“I would make the decrement a single conditional update rather than a read followed by a write, so there is no window to race in, and I would still put a CHECK (on_hand >= 0) on the table — because the constraint is the only defence that holds when somebody writes a second application against the same database.”

  1. Optimistic concurrency: a version column and WHERE version = ?. Zero rows affected is the conflict signal.
  2. A timestamp is not a version. Two updates in one clock tick share a value.
  3. Pessimistic locking is correct and costs concurrency. Never hold a lock across a user's thinking time.
  4. SKIP LOCKED is what makes a queue-in-a-table work with more than one worker.
  5. A production queue needs a claim timeout, an attempts counter and a partial index on the worker's predicate.
  6. There is no transaction across a database and a broker. The outbox turns the dual write into one local transaction.
  7. Outbox delivery is at-least-once, so consumers must be idempotent. Say so rather than implying exactly-once.
  8. Prefer a single conditional update to read-modify-write: there is no window to race in.
  9. Back every concurrency pattern with a constraint. It is the only defence that survives a second application.

Interview questions this chapter answers

Optimistic or pessimistic locking?

Optimistic where conflicts are rare and the edit involves a human — a version column costs nothing and holds no lock across thinking time. Pessimistic where a conflict is likely and retrying is expensive, or where I must serialise a multi-step operation. For a simple decrement I would use neither: a single conditional update has no window at all.

How do you stop two customers buying the last item?

Make the decrement one atomic conditional statement — UPDATE … SET on_hand = on_hand - :q WHERE id = :id AND on_hand >= :q — and treat zero rows affected as "out of stock". Then add CHECK (on_hand >= 0) so the invariant holds even if somebody later writes different code against the same table.

How do you publish an event reliably when you save a record?

A transactional outbox: write the domain change and the message into the same database transaction, and have a worker read the outbox and publish. It removes the dual-write problem at the cost of at-least-once delivery, so consumers must be idempotent — usually a unique constraint on the message id.
