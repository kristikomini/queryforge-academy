Predicates, filtering and sargability

WHERE, LIKE, IN, BETWEEN — and the one habit that quietly disables every index you own.

From the advert

“Ottimizzazione e tuning delle query” — most “tuning” turns out to be one of the four habits in this chapter, found and removed.

The word they will use: sargable

🧒 Simple

A phone book is sorted by surname, so finding “Rossi” is instant. But if I ask for everyone whose surname has six letters, the sorting is useless — you have to read every page and count. The information was there; the way I asked destroyed the shortcut.

🎓 Professional

A predicate is sargable (Search ARGument able) if the engine can use it to seek into an index instead of scanning. The rule is short: the indexed column must appear alone on one side of the comparison, untouched. Wrap it in a function, do arithmetic on it, or force a type conversion, and the index on it becomes unusable — because the index stores column, not f(column), and the engine has no way to know what range of stored values satisfies your expression.

The four ways people destroy an index

1 · A function on the column

-- Not sargable: the index stores placed_at, not YEAR(placed_at).
WHERE YEAR(placed_at) = 2026

-- Sargable: an ordinary range over stored values.
WHERE placed_at >= DATE '2026-01-01'
  AND placed_at <  DATE '2027-01-01'
Why half-open, not BETWEEN

BETWEEN '2026-01-01' AND '2026-12-31' silently drops everything that happened on 31 December after midnight, because a timestamp of 23:59:30 is greater than the date 2026-12-31 at 00:00. The >= start AND < next-start form is correct for dates, timestamps and every precision the column might later be changed to. Use it always and you never have to think about it again.

2 · Arithmetic on the column

WHERE total_cents / 100 > 500      -- not sargable
WHERE total_cents > 50000          -- sargable: move the maths to the constant

3 · A leading wildcard

WHERE name LIKE '%rossi%'          -- scan. An index is sorted by prefix; there is no prefix.
WHERE name LIKE 'rossi%'           -- seek: this is a range over names starting "rossi"

If you genuinely need infix search, an index cannot help and you need a different tool: a full-text index, a trigram index (pg_trgm), or a search engine (chapter 43). “Add an index” is the wrong answer and saying so is the right one.

4 · Implicit conversion — the invisible one

-- vat_number is VARCHAR. The literal is a number.
WHERE vat_number = 12345678901
-- The engine converts the COLUMN to a number, on every row, to compare.
-- Plan shows a scan and a CONVERT_IMPLICIT warning that nobody reads.

WHERE vat_number = '12345678901'   -- sargable
⚠ Trap

Implicit conversion is the hardest of the four to spot because the query is correct and returns the right answer — it is merely a hundred times slower. It appears when an ORM binds a parameter as NVARCHAR against a VARCHAR column (a classic .NET/SQL Server incident), or when a column that holds digits was declared as text. In SQL Server the plan carries a CardinalityEstimate or PlanAffectingConvert warning; in PostgreSQL you will see a cast in the filter. Look for it whenever a query is slow and the index “obviously” exists.

OR, IN and the shape of the range

IN (a, b, c) is a union of equality seeks and is generally fine. OR across different columns is not: no single index covers both sides, so the engine often falls back to a scan. 

-- Frequently a scan: no index has both columns as a leading key.
WHERE email = ? OR phone = ?

-- Two seeks the optimiser can cost independently, then combine:
SELECT ... WHERE email = ?
UNION
SELECT ... WHERE phone = ?
🎓 The optional-parameter pattern, and why it is poison

This shape appears in every reporting screen ever built, and it is the single most common cause of a catastrophically bad cached plan: 

WHERE (@customer_id IS NULL OR customer_id = @customer_id)
  AND (@status      IS NULL OR status      = @status)

One plan is compiled and reused for every combination of supplied and omitted parameters, so a plan built for “no filters at all” gets reused when a single customer is requested, and vice versa. The fixes are OPTION (RECOMPILE), or building the statement with safe dynamic SQL and parameters (chapter 34). Naming this pattern in an interview is a strong signal — it means you have maintained a reporting screen. 

-- In the playground, run both and compare the plan (EXPLAIN QUERY PLAN in SQLite,
-- EXPLAIN ANALYZE in PostgreSQL, "Include Actual Execution Plan" in SSMS).
EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE placed_at >= '2026-01-01' AND placed_at < '2026-02-01';

EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE strftime('%Y-%m', placed_at) = '2026-01';

When you cannot change the query

Sometimes the non-sargable expression is in a vendor application you cannot edit. Two ways out, both worth knowing by name:

  • An expression index (PostgreSQL, Oracle): CREATE INDEX ix ON orders (date_trunc('month', placed_at)); — the index now stores the expression, so the predicate becomes sargable against it.
  • A persisted computed column plus an index (SQL Server): add order_month AS DATEFROMPARTS(YEAR(placed_at), MONTH(placed_at), 1) PERSISTED and index it. SQL Server will match the original expression to it automatically.
  1. Sargable means the engine can seek. The indexed column must appear alone and untouched on one side of the comparison.
  2. Never wrap the column in a function. Rewrite as a half-open range: >= start AND < next_start.
  3. BETWEEN on a timestamp loses the last day. Half-open ranges do not.
  4. Move arithmetic to the constant side of the comparison.
  5. LIKE 'x%' seeks; LIKE '%x%' cannot. Infix search needs full-text or trigrams, not an index.
  6. Implicit conversion silently disables an index and returns the right answer, so nothing looks broken. Check the plan for a convert warning.
  7. OR across different columns often defeats indexing; UNION of two seeks lets the optimiser cost each half.
  8. The (@p IS NULL OR col = @p) pattern caches one plan for every parameter combination. Recompile it or build it dynamically with parameters.
  9. If you cannot change the query, index the expression — an expression index or a persisted computed column.

Interview questions this chapter answers

What does “sargable” mean?

That a predicate can be used to seek into an index rather than forcing a scan. It requires the indexed column to appear alone on one side of the operator — no function, no arithmetic, no implicit conversion. The index stores the column's values, so an expression over it cannot be turned into a range.

This query has an index on the date column and still scans. Why?

Almost certainly the predicate wraps it: YEAR(placed_at) = 2026, CAST(placed_at AS DATE) = …, or a type mismatch causing an implicit convert. Rewrite it as a half-open range on the raw column and the seek comes back.

How would you make LIKE '%text%' fast?

You cannot, with a B-tree — there is no prefix to seek on. The honest answer is to change the tool: a full-text index, a trigram GIN index in PostgreSQL, or an external search engine if the requirement is really relevance-ranked search rather than substring matching.
