How an index actually works

A B-tree drawn out, clustered vs non-clustered, the heap, and the lookup that costs more than a scan.

From the advert

“Ottimizzazione e tuning delle query” — and you cannot tune what you cannot picture. This chapter is the picture.

A B-tree, drawn

🧒 Simple

A phone book, but with a contents page at the front: “A–F on page 1, G–M on page 200, N–Z on page 400”. To find Rossi you read one page, jump to page 400, read one more page, and jump again. Three pages instead of eight hundred. Add ten times more people and you read four pages instead of three — that is why an index still works when the table gets huge.

🎓 Two properties, and everything follows from them
  1. It is sorted. So it answers equality, ranges, prefix LIKE, MIN/MAX, and can supply an ORDER BY without a sort. It cannot answer anything about a value it does not store — which is the whole of sargability.
  2. It is shallow. With ~8 KB pages and a narrow key, a level holds hundreds of entries, so three or four levels covers hundreds of millions of rows. A seek is three or four page reads whether the table has a thousand rows or a billion — which is why "add an index" scales and "the table got bigger" usually does not explain a slowdown on indexed access.

Clustered, non-clustered, heap

StructureWhat the leaf holdsNotes
Clustered indexThe whole rowThe table is the index. One per table. It decides physical order
Non-clustered indexThe key + a pointer to the rowMany per table. The pointer is the clustering key, or a RID on a heap
Heap—No clustered index: rows in insertion order. Fine for a staging table, bad for almost anything else
The engines disagree, and it matters
  • SQL Server and InnoDB cluster by the primary key by default. So the primary key choice is a physical storage decision.
  • PostgreSQL has no clustered index at all: the table is always a heap, and every index is secondary, storing a tuple id. CLUSTER reorders a table once and does not maintain it.
  • Oracle heaps by default, with index-organised tables as an option.

The key lookup, and why a scan can beat a seek

🎓 The tipping point

A non-clustered index seek finds the key, but the row is elsewhere. To fetch a column the index does not contain, the engine follows the pointer — a key lookup (SQL Server) or bookmark lookup — which is a random read per row.

Random reads are far more expensive than sequential ones, so past roughly 1–5% of the table the optimiser correctly decides that scanning everything sequentially is cheaper than seeking and looking up each row. That is why "it has an index but it's doing a scan" is very often the optimiser being right — and why the real fix is usually to make the index cover the query so there is no lookup at all. 

-- ix_orders_status is (status, placed_at). This needs customer_id too:
SELECT customer_id FROM orders WHERE status = 'shipped';
--  seek on the index, then one lookup per matching row

-- Covered, so zero lookups:
CREATE INDEX ix_orders_status_cov ON orders (status, placed_at) INCLUDE (customer_id);

Fill factor and fragmentation

Pages fill up. An insert or a widening update into a full page causes a page split: the page becomes two half-empty pages, and the index now occupies more space and takes more reads forever. Fill factor leaves free space in each page at rebuild time to absorb that.

⚠ Trap — the nightly rebuild nobody questions

Rebuilding every index every night was reasonable advice in 2005. Today: on SSDs, logical fragmentation barely affects random reads; the rebuild generates enormous log and cache churn; and — the part people miss — a rebuild is often only helping because it updates the statistics as a side effect. Updating statistics directly is far cheaper. Rebuild for a measured reason; do not rebuild because a maintenance plan wizard offered to. 

-- In the playground, watch a seek turn into a scan.
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE customer_id = 7;
-- SEARCH orders USING INDEX ix_orders_cust_date (customer_id=?)

EXPLAIN QUERY PLAN SELECT * FROM orders WHERE total_cents > 500000;
-- SCAN orders   ← no index on total_cents, and it would not help much anyway

Index types that are not B-trees

TypeForWhere
HashEquality only — no ranges, no orderingPostgreSQL, memory-optimised tables in SQL Server

GiST / SP-GiSTGeometry, ranges, nearest-neighbourPostgreSQL, PostGIS

Full-textWord and phrase search, rankedAll of them, differently

BRIN is the one worth remembering for an interview: an index on a billion-row append-only log, a few hundred kilobytes in size, that works only because the physical order matches the column order. It is a lovely illustration that "index" does not mean one thing.

  1. An index is sorted and shallow. Sorted is why it answers ranges; shallow is why it scales.
  2. A seek costs three or four page reads whether the table has a thousand rows or a billion.
  3. A clustered index leaf holds the whole row: the table is that index, and there is one per table.
  4. Every non-clustered index carries the clustering key, so a wide primary key inflates all of them.
  5. PostgreSQL has no clustered index; every index is secondary and the table is a heap.
  6. A key lookup is a random read per row. Past ~1–5% of the table, a scan is genuinely cheaper.
  7. “It has an index and still scans” is usually the optimiser being right. Make the index cover the query.
  8. Page splits fragment an index. Fill factor buys headroom; nightly rebuilds are mostly cargo cult on SSDs.
  9. Hash, GIN, GiST, BRIN, columnstore and full-text exist. Reaching for the right one is a real skill.

Interview questions this chapter answers

How does an index make a query faster?

It is a sorted structure with a shallow tree over it, so finding a key is three or four page reads instead of scanning the table. Being sorted also lets it answer ranges, prefix matches and ORDER BY without a sort. The cost is that every write has to maintain it.

Clustered versus non-clustered?

A clustered index's leaf level is the table, so it defines physical order and there is one per table. A non-clustered index stores the key plus a pointer, so reading other columns costs a lookup per row. In PostgreSQL the distinction does not exist — every index is secondary.

There is an index on the column and the plan still shows a scan. Why?

Either the predicate is not sargable, or the optimiser has decided the seek plus a lookup per row is more expensive than a sequential scan — which is usually correct once the query returns more than a few percent of the table. If the query genuinely needs to be fast, make the index cover it so there is no lookup.
