The job posting, decoded

This course was not written from a syllabus. It was written backwards from five real Italian SQL / Database Developer postings, so that every chapter can point at the line it answers — and so that the chapters that answer no line have to justify themselves.

Where these came from

Five postings collected in September 2026 from Indeed Italia, Glassdoor, Experis and Jooble, for roles titled SQL Developer, Database Developer, Programmatore SQL Server and Sviluppatore PL/SQL junior. The exact wording is quoted below. See docs/ADVERTS.md in the repository for the full text of each.

The lines, and what each one really means

Job adverts are written by someone who is not the person you will work for, usually by pasting three older adverts together. Read literally they are intimidating. Read properly they are a short list of things a team is tired of not having.

The three sentences that are really one sentence

🧒 Simple

Imagine a shop with a very big cupboard. Everything the shop knows lives in that cupboard: who ordered what, how much things cost, which parcel went out on Tuesday. The advert is the shop saying three things. Find things in the cupboard quickly. Put things in the cupboard without breaking what is already there. Tell us when the cupboard is about to fall over. Everything else in this course is one of those three.

🎓 Professional

Strip the buzzwords and every posting reduces to three responsibilities:

  1. Read paths. Retrieve correct data at acceptable latency — which is query formulation (Part 2), physical design (Part 4) and knowing what the optimiser will do with both.
  2. Write paths. Change data without violating an invariant and without two concurrent sessions producing a state neither intended — constraints (Part 1), transactions and isolation (Part 3).
  3. Operability. The system tells you when it is unhealthy, and can be restored when it is not — backup, monitoring and safe schema change (Parts 5 and 6).
⚠ Trap

The most common failure in a junior SQL interview is not a missing feature — it is answering the syntax question and stopping there. Asked “what is the difference between WHERE and HAVING?”, the weak answer is “HAVING filters groups”. The strong answer adds why: WHERE runs before grouping so it can use an index and reduces the rows the aggregate has to touch; HAVING runs after, on rows that already cost you the work. Same fact, and one of them tells the interviewer you understand the machine.

Which engine should you learn?

The postings name four, and Italian shops in practice run three of them: Microsoft SQL Server (dominant in gestionali and manufacturing ERP), Oracle (banks, insurance, large public-sector), and MySQL/MariaDB (everything with a web front end). PostgreSQL is growing fast and is what new projects start on.

The pragmatic answer

Learn the standard deeply and one dialect fluently. About 85% of what you write is portable; the differences are a lookup table you internalise in a week (chapter 44 is that table). This course writes standard SQL by default and flags dialect-specific spellings inline like this: 

-- Portable: works everywhere
SELECT customer_id, SUM(total_cents) AS spend
FROM orders
WHERE placed_at >= DATE '2026-01-01'
GROUP BY customer_id;

-- Top-N, and the four spellings you will meet
SELECT ... FETCH FIRST 10 ROWS ONLY;   -- standard, Oracle 12c+, PostgreSQL, DB2
SELECT ... LIMIT 10;                   -- PostgreSQL, MySQL, MariaDB, SQLite
SELECT TOP (10) ...;                   -- SQL Server
WHERE ROWNUM <= 10;                    -- Oracle, legacy, and NOT the same thing

Open the playground — a real SQL engine, in your browser, with the reference order-fulfilment database loaded. Run this and read the shape of the answer before you read the rest of this course: 

SELECT status, COUNT(*) AS n, SUM(total_cents) / 100.0 AS eur
FROM orders
GROUP BY status
ORDER BY n DESC;

How to use this course

  1. Read a chapter with the switch on “Both”. The 🧒 box builds the intuition; the 🎓 box is the sentence you would say to an interviewer.
  2. Reread it with the switch on “🧒 Simple” and try to produce the professional version out loud before you reveal it. That is the whole trick — the switch is not a display preference, it is a retrieval exercise.
  3. Take the test at the bottom. Every question you answer enters a spaced repetition schedule; Review brings them back on the day you are about to forget them.
  4. Once a week, do the viva — no options, you say the answer, then mark yourself against the model.
  5. Before a real interview, run the simulator. It has a clock, it does not let you go back, and it opens with mi parli di lei.
  1. An advert is a list of things a team is tired of not having, not a specification of you.
  2. Every posting reduces to three responsibilities: read paths, write paths, operability.
  3. Answer the syntax question, then answer the why. The second half is the interview.
  4. Learn the standard deeply and one dialect fluently; the differences are a week's lookup table.
  5. “3 years in production” means “has been on the wrong end of a deadlock”. Most of that is learnable without the scar.
  6. If a requirement is genuinely missing from your experience, say so in one sentence and say what you would do about it. Hedging is what loses the room, not the gap.

Interview questions this chapter answers

Which databases have you worked with?

Name one you know deeply and be specific about what you did in it — “SQL Server: I wrote the reporting views and tuned the two slowest ones from 40s to under a second”. Then name the others honestly with the level attached: “I read PL/SQL comfortably, I have not shipped a package.” A precise small answer beats a vague large one every time.

Why do you want to work with databases rather than application code?

Because the data outlives every application written on top of it, so the decisions made here are the expensive ones. It is also the layer where correctness is checkable — a constraint either holds or it does not.

You have no commercial experience. Why should we take you?

Point at something concrete you built and can be questioned on. This course ships a reference database — a real order-fulfilment schema with a state machine, optimistic concurrency and a transactional outbox — precisely so that you have an answer to this that is not a sentence about being a fast learner.
