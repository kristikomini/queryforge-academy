NULL and three-valued logic

NULL is not a value, = NULL is never true, and NOT IN with a NULL returns nothing. All three bite in production.

From the advert

“Ottima conoscenza del linguaggio SQL” — the fastest way to prove you have written SQL in production rather than only in tutorials is to be fluent about NULL.

NULL is not a value. It is the absence of one.

🧒 Simple

Two envelopes, both sealed. Are the numbers inside them the same? You cannot say yes and you cannot say no — you can only say I don't know. That third answer is what breaks everything, because computers usually only have two.

🎓 Professional

SQL uses three-valued logic: TRUE, FALSE, UNKNOWN. Any comparison involving NULL yields UNKNOWN, including NULL = NULL and, notoriously, NULL <> NULL. WHERE, ON and HAVING keep rows only where the predicate is TRUE, so UNKNOWN behaves like FALSE there — but CHECK constraints accept UNKNOWN, which is the opposite and is the source of a whole class of surprises.

Note the two bold cells: FALSE AND UNKNOWN is FALSE, because whatever the unknown turns out to be, the conjunction is false. Similarly TRUE OR UNKNOWN is TRUE. Three-valued logic is not arbitrary; it is what you get by asking “is this true for every possible value of the unknown?”

Six places NULL changes the answer

1 · = NULL never matches

WHERE shipped_at = NULL      -- always empty, even for unshipped orders
WHERE shipped_at IS NULL     -- correct

2 · NOT IN collapses

-- If ANY row of the subquery is NULL, this returns zero rows.
WHERE id NOT IN (SELECT customer_id FROM orders)   -- customer_id nullable? empty result.
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id)   -- correct

3 · Aggregates ignore NULL — except COUNT(*)

-- 4 rows: 10, 20, NULL, 30
COUNT(*)        -- 4   counts ROWS
COUNT(amount)   -- 3   counts NON-NULL VALUES
SUM(amount)     -- 60  ignores the null
AVG(amount)     -- 20  = 60/3, NOT 60/4  ← the one that produces wrong reports
⚠ Trap

AVG divides by the count of non-null values. If a missing rating means “no rating” that is right; if it means “zero” it is wrong and your average is inflated. Decide which, and if it is the latter write AVG(COALESCE(rating, 0)) — explicitly, where the reviewer can see the decision.

4 · UNIQUE does not constrain NULLs (mostly)

Two nulls are not equal, so they do not collide. PostgreSQL, Oracle and MySQL allow many null rows in a unique index; SQL Server allows only one, which is a genuine portability trap. PostgreSQL 15+ offers UNIQUE NULLS NOT DISTINCT to opt in to the SQL Server behaviour. If you need "at most one active row per customer", use a filtered/partial unique index instead of relying on null semantics: 

CREATE UNIQUE INDEX uq_one_active_cart
  ON carts (customer_id) WHERE status = 'active';   -- PostgreSQL, SQL Server

5 · ORDER BY disagrees across engines

PostgreSQL and Oracle sort nulls last ascending; SQL Server, MySQL and SQLite sort them first. If the position matters, say so: ORDER BY x NULLS LAST where supported, otherwise ORDER BY CASE WHEN x IS NULL THEN 1 ELSE 0 END, x.

6 · Concatenation and arithmetic propagate

'Rossi' || NULL      -- NULL in PostgreSQL, SQL Server, SQLite
                     -- (Oracle treats '' as NULL and concatenation ignores it)
100 + NULL           -- NULL, everywhere
CONCAT('Rossi', NULL) -- 'Rossi' — CONCAT() deliberately ignores nulls

-- NULLIF as a division guard: no CASE, no error.
SELECT delivered_count * 1.0 / NULLIF(total_count, 0) AS delivery_rate
FROM daily_stats;
-- total_count = 0 gives NULL ("undefined"), which is honest, rather than an error.

Designing so it comes up less

🎓 Ask what the null means

NULL is overloaded in practice, and different meanings want different designs:

  • Not yet known — shipped_at on an unshipped order. Legitimate. Keep the null; it is exactly what the model means.
  • Not applicable — vat_number on a private customer. Often a sign the table is really two kinds of thing and would be better as a subtype table.
  • Nobody filled it in — a nullable country that everybody leaves blank. This is a missing NOT NULL and a missing default.
✔ Say this in an interview

“I try to make columns NOT NULL unless the null carries meaning, and when it does I make sure I know which meaning — unknown, inapplicable, or not yet. Most of the NULL bugs I have seen came from a column where nobody had decided.”

  1. NULL is unknown, not empty and not zero. Every comparison with it is UNKNOWN.
  2. WHERE keeps only TRUE, so UNKNOWN filters the row out. CHECK accepts UNKNOWN, which is the reverse.
  3. Use IS NULL, never = NULL.
  4. One null in a NOT IN subquery returns the empty set. Use NOT EXISTS.
  5. COUNT(*) counts rows; COUNT(col) counts non-null values; AVG divides by the non-null count.
  6. UNIQUE permits multiple nulls in most engines but only one in SQL Server. For “at most one active”, use a filtered unique index.
  7. Null ordering differs by engine. State it with NULLS FIRST/LAST if it matters.
  8. NULLIF(x, 0) is the idiomatic division guard.
  9. Decide what a null means in each column: unknown, inapplicable, or not yet. Undecided is where the bugs live.

Interview questions this chapter answers

What is the result of NULL = NULL?

UNKNOWN, not TRUE and not FALSE. In a WHERE clause that means the row is dropped. To compare null-safely use IS NULL, or IS NOT DISTINCT FROM where the dialect supports it.

Difference between COUNT(*) and COUNT(column)?

COUNT(*) counts rows regardless of content. COUNT(column) counts rows where that column is not null. In a LEFT JOIN that difference is the whole point: COUNT(*) reports 1 for a customer with no orders, COUNT(o.id) reports 0.

Why did this NOT IN query suddenly return nothing?

A null appeared in the subquery result. x NOT IN (…, NULL) expands to a conjunction containing x <> NULL, which is UNKNOWN, so the predicate can never be true for any row. Rewrite as NOT EXISTS, which is null-safe and usually plans the same or better.
