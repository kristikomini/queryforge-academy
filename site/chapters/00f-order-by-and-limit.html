ORDER BY and LIMIT: reading a result you can trust

Rows have no order until you ask for one — and every dialect spells “just the first ten” differently.

No advert asked for this

The most common belief beginners hold about SQL — that rows come back in the order they were inserted — is false, and nothing reports an error when you rely on it. It works in testing and stops working in production, which is the worst possible combination.

A table is a set, so there is no order

🧒 Simple

The cards are in a box, not in a line. When you ask for them, someone hands you a pile — and nobody ever promised which way up. If you want them in a particular order you have to say so, every time. If you do not say so, the order you get is the order that was convenient, and convenient changes.

🎓 Professional

A relation is a set, and sets are unordered. Without ORDER BY, the row order of a result is undefined: it reflects whichever access path the optimiser chose, and that changes when an index is added, when statistics shift, when the query goes parallel, or when the same query runs on a replica. The order you observe today is an accident that is stable enough to be believed and not stable enough to be relied on.

Putting the four clauses together

  1. Without ORDER BY the row order is undefined — not insertion order, and not stable across runs, indexes or servers.
  2. Several sort columns means tie-breaking, and text sorts by the database's collation rather than by ASCII.
  3. Every paginated ORDER BY needs a unique tie-breaker, or pages can repeat and skip rows.
  4. “The first ten” is LIMIT, TOP or FETCH FIRST by dialect, and is meaningless without an ORDER BY.
  5. OFFSET produces and discards every skipped row, so deep pages get slower without limit.
  6. ORDER BY runs after SELECT, which is why it — alone among the clauses — can use a column alias.

Why is a query without ORDER BY not guaranteed to return rows in the same order twice?

Because a table is a set and the result order is whatever the chosen access path produced. Add an index, change the statistics, run it in parallel or run it on a replica, and the order can change. It usually looks stable, which is exactly why relying on it fails in production rather than in testing.

A paginated list sometimes shows the same row on two pages. What is the most likely cause?

The ORDER BY has ties and no unique tie-breaker, so the engine may order the tied rows differently for each page's query. Append the primary key to the sort. If rows are also being inserted while the user pages, offset-based paging shifts everything as well — keyset pagination fixes both.
