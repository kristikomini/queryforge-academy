Reading an execution plan

Scan vs seek, nested loops vs hash vs merge, and the two numbers to look at before anything else.

From the advert

“Ottimizzazione e tuning delle query” — this is the skill the phrase actually names. Everything else is guessing with confidence.

Getting a plan

⚠ Estimated is not actual

An estimated plan is what the optimiser intends; an actual plan additionally reports what happened. Nearly every performance problem is a gap between the two, so a plan without actual row counts is missing the diagnostic information. In PostgreSQL that means EXPLAIN ANALYZE, not plain EXPLAIN — and note it really executes the statement, so wrap a DELETE in a transaction you roll back.

The two numbers to look at first

🧒 Simple

Somebody planned a trip expecting twelve people and booked a small car. Four hundred turned up. The car is not the problem — the guess about how many people were coming is the problem, and everything that went wrong afterwards followed from it. When you read a plan, look first for the place where the database expected a few and got a lot.

🎓 Before you read a single operator name
  1. Estimated rows vs actual rows. A gap of more than about 10× at any operator is the root cause, and everything downstream of it is a consequence, not a problem in itself. Fix the estimate — statistics, a rewritten predicate, a temp table — and the plan often changes shape entirely.
  2. Where the time or the reads actually went. PostgreSQL prints actual time per node; SQL Server gives a percentage-of-batch cost, and SET STATISTICS IO ON gives logical reads per table, which is more trustworthy than the percentage because it is measured rather than estimated.

The warnings worth knowing by name

🎓 Three that each explain a whole class of slowness
  • Spill to tempdb / external merge sort. A sort or hash asked for less memory than it needed, because the row estimate was low, and finished on disk. Look at the estimate that caused it, not at the sort.
  • Implicit conversion / CONVERT_IMPLICIT. A type mismatch is preventing a seek. See chapter 07.
  • Missing index suggestion. SQL Server will propose one. Treat it as evidence, not instruction: it considers one query in isolation, routinely suggests an index with fourteen included columns, and does not know you already have one that differs by a single column. Read it, then design the index yourself.

A method, in order

  1. Get an actual plan plus STATISTICS IO / BUFFERS.
  2. Find the largest estimate-versus-actual gap. Start there, not at the most expensive-looking node.
  3. Find the table with the most logical reads. That is where the work is, regardless of what the cost percentages claim.
  4. Ask what the engine had to do that it should not have: a scan where a seek was possible, a sort an index could have supplied, a lookup a covering index would remove, a spool over a correlated subquery.
  5. Change one thing, re-measure. Two changes at once and you have learned nothing about either.
✔ How to talk about a plan in an interview

Narrate it as a story about work: “It seeks the index on status, gets about four hundred rows, then does a key lookup for each one to fetch the customer id — so four hundred random reads. Making that index cover customer_id removes the lookup entirely.” That is more convincing than naming operators, because it shows you know what the operator costs.

  1. Get an actual plan. An estimated plan is missing the diagnostic half.
  2. The biggest estimate-versus-actual gap is the root cause; everything below it is a consequence.
  3. Logical reads are measured; cost percentages are estimated. Trust the measured one.
  4. A scan is not automatically wrong, and a seek is not automatically right.
  5. A key lookup with a high execution count means the index should cover the query.
  6. A sort operator is an invitation to ask whether an index could supply the order.
  7. A spill to disk means the memory grant was too small, which means the estimate was too low.
  8. Missing-index suggestions are evidence, not instructions. They see one query and no existing indexes.
  9. Change one thing and re-measure.

Interview questions this chapter answers

How do you approach a slow query?

Get the actual plan and the IO statistics. Look for the largest gap between estimated and actual rows, because everything downstream of a bad estimate is a symptom. Then look at which table did the most logical reads and ask what work the engine did that it should not have — a scan instead of a seek, a sort an index could have supplied, a lookup per row. Change one thing, re-measure.

You see a key lookup executed 50 000 times. What does that mean?

The index found the rows but did not contain every column the query needed, so the engine is following the pointer back to the table once per row — 50 000 random reads. Adding the missing columns to the index, as INCLUDE where available, removes the lookup completely.

Should you always follow SQL Server's missing-index suggestions?

No. They are generated per query in isolation, so they ignore indexes you already have, propose very wide INCLUDE lists, and take no account of write cost. I treat them as a hint about which columns matter, then design the index — often by extending one that already exists rather than adding a fourth similar one.
