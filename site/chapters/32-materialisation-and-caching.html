Materialised views, pre-aggregation and caching

Trading freshness for speed on purpose, and the three questions to answer before you cache anything.

From the advert

“Reporting con SSRS e Power BI” — when the report takes forty seconds and the query cannot be made faster, the remaining move is to compute it earlier.

The trade you are making

🧒 Simple

Working out the total every time somebody asks is slow but always right. Writing the total on a card and handing over the card is instant but might be out of date. There is no third option — so the only real question is how out of date is allowed, and who decides.

🎓 The three questions, before you cache anything
  1. How stale may it be? A dashboard tile: minutes. A stock level on a checkout page: zero. If the answer is “zero”, caching is not the tool.
  2. What invalidates it? A schedule, a trigger, an event, or a TTL. If you cannot name the mechanism, you have not designed a cache — you have created a bug with a delay.
  3. What happens when it is wrong? A slightly stale sales figure is fine. A stale permission check is a security incident. The blast radius decides how much machinery the invalidation deserves.

A plain view is not a cache

CREATE VIEW v_order_totals AS SELECT ... ;   -- a NAME for a query, nothing more

A view is expanded into whatever selects from it and re-executed every time. It is an excellent interface — it lets the tables underneath change without every report changing — and it does nothing at all for performance. People are surprised by this regularly enough that it is worth saying explicitly.

⚠ SQL Server's indexed view is a different bargain

It is always current, because every write to a base table updates it synchronously — so the cost lands on your writes, permanently, not on a refresh window. It also carries a long list of restrictions (SCHEMABINDING, no outer joins, no subqueries, COUNT_BIG(*) required with GROUP BY, deterministic expressions only). Knowing it is synchronous — and that PostgreSQL's is not — is the distinction that matters, because it decides which one is safe on a write-heavy table. 

-- PostgreSQL: refreshed on a schedule, readers never blocked.
CREATE MATERIALIZED VIEW mv_monthly_sales AS
SELECT date_trunc('month', o.placed_at) AS month,
       r.name                           AS region,
       COUNT(*)                         AS orders,
       SUM(o.total_cents)               AS revenue_cents
FROM orders o
JOIN customers c ON c.id = o.customer_id
JOIN cities   ci ON ci.id = c.city_id
JOIN regions   r ON r.id = ci.region_id
WHERE o.status <> 'cancelled'
GROUP BY 1, 2;

CREATE UNIQUE INDEX ON mv_monthly_sales (month, region);   -- required by CONCURRENTLY
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_monthly_sales;

Summary tables, and the incremental refresh

A full refresh recomputes everything, which stops scaling once "everything" is two years of data. The pattern that does scale is to refresh only what changed: 

-- Recompute only the affected slice, inside one transaction. Naturally idempotent,
-- so re-running it after a failure is safe. See chapter 20.
BEGIN;
  DELETE FROM summary_daily_sales WHERE d = :day;
  INSERT INTO summary_daily_sales (d, region, orders, revenue_cents)
  SELECT date(placed_at), region, COUNT(*), SUM(total_cents)
  FROM v_orders_geo
  WHERE date(placed_at) = :day AND status <> 'cancelled'
  GROUP BY 1, 2;
COMMIT;
Always store when it was computed

A computed_at column costs nothing and answers the only question anyone asks about a summary table: “is this current?”. Show it on the report — “as at 06:00 today” — and stale data stops being a support ticket and becomes a stated property. That one line of UI saves more arguments than any amount of refresh engineering.

Maintained counters, and why they hurt

-- Tempting: keep orders.total_cents in step with a trigger on order_lines.
-- Correct, and it serialises every concurrent write to the same order behind one
-- row lock — because they all update the same parent row. On a hot parent this is
-- a contention point you cannot index your way out of.
🎓 The standard fix: sharded counters

Instead of one row per counter, keep n rows and have each writer update a random one; read the counter as a SUM over the n. Writes spread across n locks, reads cost one small aggregate. It is the same idea behind PostgreSQL's advice to avoid a single hot row, and it is a good thing to know exists — although the honest first answer is usually “compute it on read, with the right index, until measurement says otherwise”.

⚠ Cache stampede

A popular cached value expires; a thousand concurrent requests all miss; a thousand identical expensive queries hit the database at once and it falls over — because the cache was working. Mitigations: a lock so only one request recomputes, serving stale while refreshing in the background, or jittered expiry so a batch of keys does not expire together. Naming this failure mode signals real production experience.

  1. Caching trades freshness for speed. Decide the tolerated staleness first, in numbers.
  2. If you cannot name the invalidation mechanism, you have not designed a cache.
  3. A plain view is a name for a query and does nothing for performance.
  4. PostgreSQL materialised views are refreshed manually; SQL Server indexed views are maintained synchronously on every write.
  5. Refresh incrementally by slice. A full refresh stops scaling.
  6. Store and display computed_at. Stale becomes a property, not a bug report.
  7. Trigger-maintained counters serialise concurrent writes on the parent row.
  8. Application-memory caches multiply by the number of instances.
  9. Expiring a popular key can stampede the database. Use a lock, serve-stale, or jittered TTLs.

Interview questions this chapter answers

A report takes 40 seconds and the query is already optimal. What now?

Compute it earlier. I would ask how stale it may be — usually the answer is "this morning is fine" — then build a summary table refreshed incrementally by day, with a computed_at column shown on the report. A materialised view is the same idea with engine support; on SQL Server an indexed view is always current but moves the cost onto every write.

Difference between a view and a materialised view?

A view is a stored query, expanded and re-executed each time — it is an interface, not a cache. A materialised view stores the result, so reads are fast and the data is as fresh as the last refresh. PostgreSQL refreshes on demand; SQL Server's indexed views are maintained synchronously, which makes writes more expensive but removes staleness entirely.

What is a cache stampede?

A hot cached value expires and every concurrent request misses at once, so the database gets hundreds of identical expensive queries simultaneously. Fixes are a mutex so one request recomputes while the others wait, serving the stale value while refreshing in the background, or adding jitter to expiry times so keys do not expire together.
