UPSERT, MERGE and idempotent writes

ON CONFLICT, ON DUPLICATE KEY, MERGE — and why “check then insert” is a race, not a pattern.

From the advert

“Esperienza nello sviluppo ETL con SSIS” — the actual daily problem of an ETL job is not transforming data. It is making the load safe to re-run after it failed halfway through at 03:40.

“Check then insert” is a race, not a pattern

🧒 Simple

Two people look in the fridge, both see there is no milk, and both go and buy milk. Looking and acting were two separate moments, and something changed in between. The fix is not to look harder — it is to make “buy the milk if there isn't any” a single indivisible action.

🎓 Professional

The gap between the check and the act is a time-of-check to time-of-use race, and no isolation level below SERIALIZABLE closes it — because the row does not exist yet, so there is nothing to lock. The two real fixes are: perform the operation atomically with an upsert, or let a unique constraint catch it and handle the violation. Both require the unique constraint. It is the constraint doing the work, not the syntax.

The four spellings

⚠ Trap — MERGE has a reputation, and it earned it

SQL Server's MERGE has a documented history of bugs and surprises, and several well-known SQL Server MVPs advise avoiding it outright:

  • It is not atomic against concurrent inserts unless you take an explicit HOLDLOCK / SERIALIZABLE hint on the target — the default can still raise a duplicate-key error under concurrency.
  • If the USING source produces more than one row per target row, it raises error 8672 sometimes, depending on the plan.
  • It has historically interacted badly with triggers, filtered indexes and foreign keys.

Knowing that MERGE exists and that the safe SQL Server pattern is often a plain UPDATE followed by an INSERT … WHERE NOT EXISTS in one transaction is a genuinely senior answer.

Idempotency: the actual requirement

🎓 What “idempotent” buys you

An operation is idempotent if running it twice has the same effect as running it once. That is what lets you retry safely — and every distributed system you will ever touch retries: the ETL job that failed at 03:40, the payment webhook delivered twice, the message queue that guarantees at-least-once. Without idempotency, “just re-run it” is a sentence that creates duplicate invoices.

The three mechanisms

1 · A natural business key with a unique constraint. The most robust, because the database enforces it whatever the application does.

2 · A watermark. For incremental loads: record the highest source timestamp or id you have processed, and next time start from there.

⚠ Trap — the strictly-greater-than watermark

> watermark loses rows whose timestamp ties with the maximum but which were committed after you read it. >= reprocesses the boundary — which is fine, and correct, precisely because the load is idempotent. This is the pairing that matters: an idempotent load lets you use the safe, overlapping window. If your load is not idempotent you are forced into the lossy comparison.

Upserting a batch, not a row

✔ That WHERE clause is the senior detail

A nightly load where 99% of rows are unchanged still rewrites every row without it — bloating the table, filling the log, and firing every trigger. Adding the “only if different” predicate turns a two-hour job into a two-minute one, and it is the kind of thing nobody notices until somebody looks.

  1. Check-then-insert is a race. No isolation level below serialisable closes it, because the row does not exist to be locked.
  2. An upsert is only safe because of the unique constraint. The constraint does the work; the syntax is convenience.
  3. ON CONFLICT (PostgreSQL/SQLite) names the constraint; ON DUPLICATE KEY (MySQL) fires on any of them.
  4. SQL Server's MERGE needs HOLDLOCK to be concurrency-safe, and has a long list of known issues. Update-then-insert in a transaction is often better.
  5. Idempotent means running twice equals running once — which is what makes “just re-run it” safe.
  6. Three mechanisms: a unique business key, a watermark, or delete-and-reload by slice.
  7. Update the watermark in the same transaction as the load, and use >= because an idempotent load can absorb the overlap.
  8. Upsert a batch from a staging table, not a row at a time, and skip rows that have not changed.

Interview questions this chapter answers

How do you make a nightly import safe to re-run?

Give every source record a stable business key, put a unique constraint on it, and load with an upsert — so a re-run updates rather than duplicates. For incremental loads, advance the watermark inside the same transaction as the insert, and use an inclusive comparison, which is safe precisely because the load is idempotent.

What is wrong with SELECT-then-INSERT?

There is a window between the two in which another session can insert the same row. It is a race that only appears under concurrency, so it passes every test and fails in production. Use an atomic upsert, or let a unique constraint reject the duplicate and handle the violation.

Would you use MERGE?

In Oracle, yes. In SQL Server I am cautious: it is not concurrency-safe without HOLDLOCK, it has a documented history of bugs, and it errors unpredictably when the source has duplicate keys. For a simple upsert I would often write an update followed by an insert-where-not-exists in one transaction, which is easier to reason about.
