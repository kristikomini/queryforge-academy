Your own table: CREATE, INSERT, UPDATE, DELETE

Making a table, putting rows in it, changing them, removing them — and the two habits that prevent the worst day.

No advert asked for this

Reading data is half the job; this is the other half, at the smallest possible scale. Chapters 19 to 24 do it properly, with concurrency and idempotency. Here you only need to be able to make a table and put rows in it — safely.

Two kinds of statement

🧒 Simple

There are statements that change the boxes printed on the cards — making a new kind of card, adding a box to it, throwing the whole pile away. And there are statements that change what is written in the boxes — adding a card, correcting one, removing one. They are different kinds of thing, and the first kind is much harder to undo.

🎓 Professional

DDL — data definition language: CREATE, ALTER, DROP. It changes the schema. DML — data manipulation language: INSERT, UPDATE, DELETE. It changes the rows. The distinction is operational, not academic: DDL takes heavier locks, and in some engines — Oracle, MySQL — it commits the current transaction whether you wanted it to or not, so a DDL statement in the middle of your careful transaction has already made everything before it permanent.

INSERT: putting rows in

UPDATE: changing rows that already exist

⚠ An UPDATE with no WHERE updates every row

There is no confirmation prompt. There is no undo. The statement is valid SQL, the engine does exactly what it was told, and the row count tells you afterwards. This is the single most expensive mistake a beginner makes, and the habit below removes it entirely.

DELETE, and the transaction that makes it reversible

DELETE, TRUNCATE and DROP are three different things

StatementRemovesNotes
DELETE FROM t WHERE …Matching rows DML. Row by row, fully logged, can be rolled back, fires triggers. Slow at volume, and the only one that can be filtered.
DELETE FROM tEvery row Still row by row. The table, its columns and its indexes remain.
TRUNCATE TABLE tEvery row DDL in most engines: deallocates pages, minimally logged, very fast. Cannot be filtered, usually refuses while a foreign key points at the table, and resets identity counters.
DROP TABLE tThe table itself The rows, the columns, the indexes, the constraints and the permissions. There is nothing left to select from.
✔ The sentence that answers this at interview

“DELETE is DML and removes rows; TRUNCATE is DDL and removes all of them by deallocating pages; DROP removes the object. In some engines DDL commits the open transaction, which is why a TRUNCATE in the middle of one is not the same as a DELETE.” That one answer covers five follow-up questions at once.

  1. DDL changes the schema, DML changes the rows — and in some engines DDL commits the open transaction.
  2. Always name the columns in an INSERT: positional inserts break silently when the table gains a column.
  3. An UPDATE or DELETE with no WHERE affects every row, with no prompt and no undo.
  4. Write the SELECT first, copy the predicate into the write, and check the row count against it.
  5. Wrap a destructive statement in BEGIN … ROLLBACK/COMMIT — and know that most clients are in autocommit until you do.
  6. ROLLBACK restores rows but does not give back consumed identity values; gaps are normal.
  7. DELETE removes rows, TRUNCATE removes all of them by deallocating pages, DROP removes the table.

What is the difference between DELETE and TRUNCATE?

DELETE is DML: row by row, fully logged, filterable, rollback-able, and it fires triggers. TRUNCATE is DDL in most engines: it deallocates the table's pages, is minimally logged and very fast, cannot be filtered, resets identity counters, and is usually refused while a foreign key references the table. On a large table the performance difference is enormous, which is why the question is asked.

You have just run an UPDATE and it reports 40 000 rows changed instead of 4. What now?

If you are inside a transaction: ROLLBACK, immediately, before anything else. If you are not, stop touching the database and tell someone — the recovery is a point-in-time restore (chapter 41) and every further statement makes it harder. Then adopt the habit that prevents it: SELECT first, transaction always.
