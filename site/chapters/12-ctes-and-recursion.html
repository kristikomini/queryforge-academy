CTEs and recursive queries

WITH for readability, WITH RECURSIVE for trees and hierarchies, and the optimisation fence that surprises people.

From the advert

“Ottima conoscenza del linguaggio SQL” — a 200-line nested query and a 200-line query built from named steps contain the same SQL. Only one of them can be reviewed.

A CTE is a name for a step

🧒 Simple

A recipe that says “put the thing you made in step 2 into the thing you made in step 4” is unreadable. A recipe that says “add the sauce to the base” is not. A CTE is giving a step a name so the next line can say what it means.

Written as nested derived tables that is the same logic with the reader's eye starting in the middle. Written as a chain of CTEs it reads top to bottom, and each step can be run on its own while you are debugging it — which is the practical benefit nobody mentions.

The optimisation fence: the thing that surprises people

🎓 Is a CTE materialised?

It depends on the engine, and it matters:

  • SQL Server, MySQL 8+ — a CTE is an inline view. It is expanded into the outer query and optimised as a whole, and a CTE referenced twice is evaluated twice.
  • PostgreSQL before 12 — always materialised. This was a genuine optimisation fence, used deliberately to stop predicate push-down.
  • PostgreSQL 12+ — inlined when referenced once and side-effect free; materialised otherwise. You can force either with WITH x AS MATERIALIZED (…) or AS NOT MATERIALIZED.
  • Oracle — decides by cost; /*+ MATERIALIZE */ forces it.
⚠ Trap

“I put it in a CTE so it only runs once” is false in SQL Server and MySQL. If an expensive CTE is referenced three times it runs three times. When you genuinely need single evaluation, materialise it explicitly: a temporary table, or AS MATERIALIZED in PostgreSQL. A temp table also gets statistics, which an inline CTE does not — often the real reason the rewrite is faster.

Recursive CTEs: hierarchies, and how the machine runs them

🧒 Simple

Start with the boss. Ask “who reports to the people I already have?” Write them down. Ask again about the new ones. Keep going until an ask produces nobody new. Now you have the whole company.

🎓 The three rules of a recursive CTE
  1. The recursive member may reference the CTE once, and not inside an outer join, aggregate or subquery.
  2. UNION ALL keeps everything and is what you normally want. UNION deduplicates each iteration, which also breaks cycles — at the cost of a sort per step.
  3. Always bound it. A depth column with a WHERE depth < n, or SQL Server's OPTION (MAXRECURSION 100). Real hierarchy data contains cycles — an employee who is their own grandparent — and without a guard the query runs until the server gives up.
Recursive CTE or a hierarchy column?

If you read a tree far more often than you change it, storing a materialised path (/1/14/97/), a nested-set pair, or SQL Server's hierarchyid turns the recursion into a single indexed LIKE '/1/14/%'. It costs more on write and needs maintenance when a node moves. Naming that trade-off is the senior answer; reaching for it before measuring is not.

  1. A CTE names a step. Its main value is readability and being able to run each step alone while debugging.
  2. A CTE is not automatically materialised. In SQL Server and MySQL it is inlined and re-evaluated per reference.
  3. When you need single evaluation, say so: AS MATERIALIZED, or a temp table — which also gets statistics.
  4. A recursive CTE has an anchor and a recursive member joined by UNION ALL.
  5. The recursive member sees only the previous iteration, which is why it terminates.
  6. Always add a depth guard. Production hierarchy data contains cycles.
  7. UNION instead of UNION ALL breaks cycles by deduplication, and pays for a sort each iteration.
  8. Read-heavy trees can be stored as materialised paths and queried without recursion at all.

Interview questions this chapter answers

CTE or subquery — what is the difference?

Mostly readability and reuse: a CTE is named, can be referenced more than once, and can be recursive. Performance-wise they are usually identical because the CTE is inlined — the exception is PostgreSQL, where MATERIALIZED makes it an explicit optimisation fence.

How do you query a hierarchy of unknown depth?

A recursive CTE: an anchor selecting the roots, then a recursive member joining the table back to the CTE, combined with UNION ALL. I would carry a depth column and bound it, because real data contains cycles and an unbounded recursion runs until the server stops it.

Does putting an expensive query in a CTE make it run once?

Not in SQL Server or MySQL — it is inlined, so three references mean three evaluations. To guarantee one evaluation, materialise it: AS MATERIALIZED in PostgreSQL, or a temporary table, which has the side benefit of getting statistics.
