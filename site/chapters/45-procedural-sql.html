Procedural SQL: T-SQL and PL/SQL

Variables, control flow, cursors, error handling and packages — the two procedural dialects adverts name.

From the advert

“Esperienza in sviluppo PL/SQL a livello junior” — “a livello junior” means they expect you to read and modify packages, not architect them. That is a much smaller ask than it sounds.

Why procedural SQL exists

🧒 Simple

SQL is very good at saying what you want. It has no way of saying “try this, and if it goes wrong do that instead, and keep a note of how many times you tried”. The procedural dialects add that — and the first rule of using them is to use as little of them as possible.

✔ The rule that keeps procedural code fast

Write set-based SQL, and use procedural code only for control flow around it. A loop that processes one row per iteration is the commonest reason a stored procedure is slow (chapter 29). Variables, IF, error handling and transactions are the legitimate uses; iteration almost never is.

T-SQL, the shape you will meet

CREATE OR ALTER PROCEDURE dbo.usp_ShipOrder
  @order_id INT,
  @version  INT,
  @actor    SYSNAME = NULL
AS
BEGIN
  SET NOCOUNT ON;              -- stop "n rows affected" messages confusing the caller
  SET XACT_ABORT ON;           -- ON ERROR, ROLL BACK THE WHOLE TRANSACTION.
  --  ^ Without this, some errors abort only the STATEMENT and leave the transaction
  --    open and half-applied. It is the single most important line in the file.

  DECLARE @now DATETIME2(3) = SYSUTCDATETIME();
  SET @actor = COALESCE(@actor, SUSER_SNAME());

  BEGIN TRY
    BEGIN TRANSACTION;

      UPDATE dbo.orders
      SET status = 'shipped', shipped_at = @now, version = version + 1
      WHERE id = @order_id
        AND version = @version              -- optimistic concurrency, chapter 24
        AND status  = 'confirmed';          -- and the state machine, chapter 04

      IF @@ROWCOUNT = 0
      BEGIN
        -- Distinguish "gone", "changed under us" and "wrong state" — the caller
        -- needs different behaviour for each, so do not return one vague error.
        IF NOT EXISTS (SELECT 1 FROM dbo.orders WHERE id = @order_id)
          THROW 50404, 'Order not found.', 1;
        THROW 50409, 'Order was modified or is not in a shippable state.', 1;
      END

      INSERT INTO dbo.order_events (order_id, from_status, to_status, at, actor)
      VALUES (@order_id, 'confirmed', 'shipped', @now, @actor);

      INSERT INTO dbo.outbox (topic, payload, created_at)
      VALUES ('order.shipped',
              (SELECT @order_id AS orderId FOR JSON PATH, WITHOUT_ARRAY_WRAPPER), @now);
      --      ^ the outbox write is in the SAME transaction. Chapter 24.

    COMMIT TRANSACTION;
  END TRY
  BEGIN CATCH
    IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION;   -- check the count; see chapter 21
    THROW;                                     -- rethrow PRESERVING the original error
  END CATCH
END
⚠ Three T-SQL traps in that one procedure
  1. Without SET XACT_ABORT ON, several classes of error abort only the current statement. The CATCH block runs with a transaction still open and partially applied — which is how "it half-worked" incidents happen.
  2. THROW, not RAISERROR. Bare THROW inside a CATCH rethrows the original error with its number, message and line. RAISERROR cannot do that: it substitutes its own, and the real cause is lost.
  3. @@ROWCOUNT must be read immediately. Any statement in between — including an IF — resets it. Capture it into a variable on the very next line if you need it twice.

PL/SQL, the same thing in Oracle

CREATE OR REPLACE PACKAGE orders_pkg AS
  -- The SPEC is the public interface. Anything not declared here is private to
  -- the body — which is real encapsulation, and the thing PL/SQL genuinely has
  -- that T-SQL does not.
  PROCEDURE ship_order(p_order_id IN NUMBER, p_version IN NUMBER);
  e_conflict EXCEPTION;
  PRAGMA EXCEPTION_INIT(e_conflict, -20409);
END orders_pkg;
/

CREATE OR REPLACE PACKAGE BODY orders_pkg AS
  PROCEDURE ship_order(p_order_id IN NUMBER, p_version IN NUMBER) IS
  BEGIN
    UPDATE orders
       SET status = 'shipped', shipped_at = SYSTIMESTAMP, version = version + 1
     WHERE id = p_order_id AND version = p_version AND status = 'confirmed';

    IF SQL%ROWCOUNT = 0 THEN                 -- the PL/SQL @@ROWCOUNT
      RAISE_APPLICATION_ERROR(-20409, 'Order modified or not shippable');
    END IF;

    INSERT INTO order_events (order_id, from_status, to_status)
    VALUES (p_order_id, 'confirmed', 'shipped');
    COMMIT;
  EXCEPTION
    WHEN OTHERS THEN
      ROLLBACK;
      RAISE;                                 -- rethrow, preserving the stack
  END ship_order;
END orders_pkg;
/

🎓 The two PL/SQL features worth knowing by name
  • BULK COLLECT / FORALL — the fix when a cursor loop is genuinely unavoidable. It moves rows between SQL and PL/SQL in batches instead of one at a time, eliminating the per-row context switch. Order-of-magnitude improvements are routine, and it is the first thing to reach for in slow legacy PL/SQL.
  • %TYPE and %ROWTYPE — declare a variable as "whatever type that column is". The declaration follows the schema automatically, so widening a column does not silently truncate in a procedure nobody remembered.

Cursors, and the honest use for them

-- If you must, at least tell the engine what you are doing:
DECLARE c CURSOR LOCAL FAST_FORWARD READ_ONLY FOR SELECT ...;
--            ^ local scope  ^ forward-only, read-only: far cheaper than the default

-- But first ask: could this be one statement? It usually could.
-- The legitimate cases:
--   * each row requires a separate external action
--   * you are deliberately batching a huge update to avoid lock escalation
-- And in both cases, write the reason in a comment — because the default
-- assumption on reading a cursor is that the author did not know better.

Reading somebody else's procedure

✔ A five-minute order of attack
  1. The signature. Parameters in, parameters out, return value. That is the contract.
  2. Transaction boundaries. Where does it begin and commit, and is there a path that leaves one open?
  3. The error paths. What happens on failure, and is the original error preserved or swallowed?
  4. Loops and cursors. Anything row-at-a-time is where the time goes.
  5. Only then, the business logic. Which is usually the part that is actually fine.
  1. Set-based SQL for the work, procedural code only for control flow around it.
  2. SET XACT_ABORT ON in every T-SQL procedure with a transaction.
  3. THROW rethrows the original error; RAISERROR replaces it.
  4. @@ROWCOUNT is reset by the next statement. Capture it immediately.
  5. Check @@TRANCOUNT before rolling back in a CATCH.
  6. Distinguish “not found” from “changed under us” from “wrong state” — the caller needs to.
  7. Packages give PL/SQL real encapsulation: a public spec and a private body.
  8. BULK COLLECT and FORALL are the fix for an unavoidable PL/SQL loop.
  9. %TYPE keeps a variable in step with its column.
  10. A cursor needs LOCAL FAST_FORWARD READ_ONLY and a comment explaining itself.

Interview questions this chapter answers

How do you handle errors in a stored procedure?

In T-SQL: SET XACT_ABORT ON, a TRY block containing the transaction, and a CATCH that rolls back if @@TRANCOUNT is non-zero and then bare-THROWs to rethrow the original error with its number and line. In PL/SQL it is an EXCEPTION block with RAISE to rethrow. The two things I care about are not leaving a transaction open and not losing the original error.

What is a package in PL/SQL?

A named container with a public specification and a private body. Anything not declared in the spec is invisible outside, so it gives real encapsulation and a versionable interface — which is the main structural thing PL/SQL has that T-SQL does not.

You inherit a procedure that takes eight minutes. Where do you look first?

For a cursor or a WHILE loop doing row-at-a-time work, because that is usually the whole answer. Then for scalar functions inside a predicate, and for a table variable being joined to — both of which give the optimiser no useful estimate. The business logic is normally fine; the shape around it is not.
