Views, procedures, functions and triggers

The four programmable objects, what each is genuinely for, and the one that causes most production incidents.

From the advert

“Sviluppo di stored procedure, viste, funzioni e trigger” — the codebase already has business logic inside the database. You will maintain it whether or not you think that was a good idea.

The four objects, and what each is genuinely for

ObjectGenuinely forCosts
ViewAn interface: a stable name over a query, so the tables underneath can changeNothing at runtime — it is expanded. Nesting them hides real cost
Stored procedureA multi-statement unit that belongs next to the data: a transaction, a batch, a permission boundaryLogic that is hard to version, test and diff
FunctionA reusable expression (inline table-valued) — genuinely usefulScalar ones are a plan disaster. See below
TriggerAuditing and invariants nothing else can expressInvisible action at a distance. The commonest source of "why did that happen?"

Views: an interface, not a cache

🧒 Simple

A view is a nickname for a question. Saying the nickname does not make the answer arrive any faster — somebody still has to go and count. What it does mean is that if the counting changes, everyone using the nickname carries on unaffected.

⚠ Trap — nested views

A view selecting from a view selecting from two views is expanded into one enormous query the optimiser then has to plan. Each level looks reasonable in isolation; four levels down, a SELECT of three columns joins eleven tables and nobody can see why. Nesting more than two deep is where "just use a view" goes wrong. Keep them shallow, and read the plan of the query you are actually running rather than the view you think you are querying.

Updatable views and WITH CHECK OPTION

A simple single-table view is updatable. Add WITH CHECK OPTION and rows that would disappear from the view cannot be written through it — so a view defined as WHERE region = 'EMR' cannot be used to insert a Lombardia row. It is a neat, little-known way to express a scoping rule, and it is a genuine alternative to row-level security on older engines.

Stored procedures: the real argument

🎓 For
  • Fewer round trips. A five-statement transaction becomes one call.
  • A permission boundary. Grant EXECUTE on the procedure and nothing on the tables — the application cannot issue arbitrary SQL even if compromised. This is a real security argument and the strongest one.
  • Change without redeploying the application. Which is also the strongest argument against.
  • The logic lives with the data, so three applications sharing a database share the rules.
🎓 Against
  • Version control is awkward and diffs are poor — an ALTER PROCEDURE in a migration is not the same as a file whose history is the truth.
  • Testing is harder and there are fewer tools.
  • Business logic in two places is worse than in either, and that is what usually happens.
  • Changing without a deploy means changing without review, without CI, and without anybody knowing.
✔ The answer that avoids the trap

This question is often asked to see whether you have an ideology. “It depends on who owns the data. One application, one team — I would keep logic in the application, where it is versioned and tested. Several applications sharing one database, or a hard requirement that the app account cannot run ad-hoc SQL — procedures, and I would keep them in source control as files, deployed by a migration tool like anything else.” That is a position, with a reason, and no contempt for the alternative.

Functions: the one that matters

⚠ The three-way distinction to remember

Inline table-valued: expanded, estimated, parallelisable — use freely. Multi-statement table-valued: a black box with a fixed row estimate — avoid in a join. Scalar: historically once per row, no costing, forces a serial plan — avoid over large sets. SQL Server 2019's scalar UDF inlining helps, but only for functions simple enough to inline, and you cannot tell by looking.

Triggers

🧒 Simple

A trigger is a note stuck inside the drawer saying “whenever anyone puts something in here, also do this”. Very useful. Also the reason somebody spends an afternoon asking why a row they never touched changed.

🎓 The rules that make them survivable
  1. They fire per statement, not per row. In SQL Server the inserted and deleted pseudo-tables contain all affected rows. A trigger written as though a single row were being changed — SELECT @id = id FROM inserted — is silently wrong the first time somebody updates two rows at once. This is the single most common trigger bug.
  2. They run inside the caller's transaction. So a slow trigger makes every write slow, and a failing trigger rolls back a statement that looked innocent.
  3. They can cascade. Trigger A writes to table B whose trigger writes back to A. Nesting is limited (32 levels in SQL Server) and the error when you hit it is not obvious.
  4. They are invisible. Nothing in the calling code mentions them. Whatever you do, make them findable: name them consistently, and list them in the schema documentation.
✔ Where a trigger is genuinely the right answer

Auditing. An audit row written by a trigger is written no matter which application, script or person made the change — which is exactly the property an audit trail needs and exactly what application-level auditing cannot promise. Almost every other use of a trigger has a better alternative: a generated column, a constraint, a job, or explicit code.

  1. A view is an interface, not a cache. It is expanded and re-executed every time.
  2. Nested views hide cost. Two levels is plenty; read the plan of the query you actually run.
  3. WITH CHECK OPTION stops writes that would fall outside the view's own filter.
  4. The strongest argument for procedures is the permission boundary: EXECUTE only, no table access.
  5. The strongest argument against is logic that changes without review, CI or anyone knowing.
  6. Inline table-valued functions are good; multi-statement ones estimate a fixed guess; scalar ones run per row.
  7. Triggers fire per statement. A trigger that assumes one row is wrong the first time two are updated.
  8. Triggers run in the caller's transaction, so a slow one makes every write slow.
  9. Auditing is where a trigger genuinely wins, because it cannot be bypassed.

Interview questions this chapter answers

Should business logic live in stored procedures?

It depends on who owns the data. One application and one team: I keep it in the application, where it is versioned, reviewed and tested. Several applications sharing one database, or a requirement that the app account cannot run ad-hoc SQL: procedures — kept as files in source control and deployed by a migration tool, not edited in place.

What is wrong with scalar user-defined functions?

Historically they execute once per row, the optimiser has no cardinality estimate for them, and they force the whole query serial. An inline table-valued function used with CROSS APPLY gets the same reuse and is expanded into the query, so it is estimated and parallelisable.

What is the most common bug in a trigger?

Assuming it fires once per row. It fires once per statement, with all affected rows in inserted/deleted, so a trigger written with a scalar variable silently processes one arbitrary row when somebody updates two. The fix is to write it set-based.
