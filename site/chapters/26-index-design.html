Index design: order, covering, selectivity

Why (a, b) is not (b, a), what INCLUDE is for, and the real cost of the index nobody uses.

From the advert

“Ottimizzazione e tuning delle query” — adding an index is easy. Knowing which one, in which column order, and which existing three to delete, is the job.

Column order is the whole game

🧒 Simple

A phone book is sorted by surname, then first name. Finding “Rossi, Marco” is easy. Finding everyone called Marco is not — you have to read the whole book, because first names are scattered all through it. The order you sorted by decides which questions are cheap.

🎓 The leftmost-prefix rule

An index on (a, b, c) can seek on a, on (a, b), and on (a, b, c). It cannot seek on b alone, or on (b, c), because those values are not sorted independently — they are only sorted within a value of a.

So an index on (customer_id, placed_at) serves “this customer's orders” and “this customer's recent orders”. An index on (placed_at, customer_id) serves “orders in March” — and serves “this customer's orders” not at all.

QueryIndex (a, b, c) can…
WHERE a = 1✅ seek
WHERE a = 1 AND b = 2✅ seek on both
WHERE a = 1 AND c = 3✅ seek on a, then filter c inside the range
WHERE b = 2❌ scan
WHERE a > 1 AND b = 2⚠ seek the range on a; b cannot narrow it further
ORDER BY a, b✅ no sort needed
ORDER BY b❌ sort required
⚠ Trap — a range column stops the index dead

In row 5 above, once you use an inequality on a the entries are no longer grouped by b, so b can only filter rows already read, not narrow the seek. Hence the ordering rule: equality columns first, then the range column, then anything only needed for sorting or covering. This one sentence is the answer to most “design an index for this query” questions. 

-- SELECT ... WHERE status = 'shipped' AND placed_at >= ? ORDER BY placed_at
CREATE INDEX ix ON orders (status, placed_at);
--                          ^equality  ^range and sort. Correct order.

-- Reverse it and the seek becomes a scan of every shipped-or-not row in the range.

Covering indexes

🎓 An index that answers the query by itself

If every column a query touches — in SELECT, WHERE, JOIN, ORDER BY — is in the index, the engine never reads the table at all. No key lookup, no random reads. In a plan this shows as an index-only scan (PostgreSQL) or an index seek with no key lookup beside it (SQL Server), and it is often a 10–100× improvement on a wide table. 

-- SQL Server: INCLUDE puts columns in the LEAF only — not in the key.
-- They do not affect ordering or seekability, they cost nothing in the upper
-- levels, and they remove the lookup.
CREATE INDEX ix_orders_status_cov
  ON orders (status, placed_at)      -- key: used for seeking and ordering
  INCLUDE (customer_id, total_cents); -- payload: available without a lookup

-- PostgreSQL 11+ has the same thing:
CREATE INDEX ix ON orders (status, placed_at) INCLUDE (customer_id, total_cents);

-- MySQL has no INCLUDE: extra columns must go in the key.
⚠ Trap — the covering index that covers everything

It is tempting to INCLUDE every column so all queries are covered. That reproduces the table inside the index: every insert writes twice, every update of an included column updates two structures, and your buffer pool now holds two copies of the same data. Cover the columns your hot queries need, not all of them.

Selectivity: which column is worth indexing

Selectivity is the fraction of rows a predicate eliminates. An index on a column with two distinct values across a million rows cannot help a lookup — reading half the table through an index is worse than scanning it.

✔ Except when it is skewed, which is the interesting case

A status column that is 99% 'delivered' and 1% 'failed' is useless for finding delivered orders and excellent for finding failed ones. Which is exactly what a partial (filtered) index expresses: 

CREATE INDEX ix_orders_failed ON orders (placed_at) WHERE status = 'failed';
-- 1% of the size, seeks straight to the rows anyone actually queries for,
-- and rows leave the index entirely when they stop being failed.

-- The reference database uses the same idea for the outbox worker:
CREATE INDEX ix_outbox_pending ON outbox (created_at) WHERE published_at IS NULL;
-- stays tiny however large the outbox grows.

PostgreSQL calls them partial indexes, SQL Server calls them filtered indexes, Oracle achieves the same with a function-based index that returns NULL for uninteresting rows. MySQL has no equivalent.

What an index costs

🎓 The four costs, and the one people forget
  1. Write amplification. An insert into a table with six indexes is seven writes. An update touching two indexed columns updates those two indexes as well.
  2. Space, in the buffer pool as much as on disk — every unused index is evicting pages something else wanted.
  3. Maintenance: statistics, rebuilds, backups all get bigger.
  4. Optimiser choice. More indexes means a larger plan search space and more opportunities to pick a wrong one. This is the cost nobody mentions and it is real.
-- Which indexes are you paying for and not using?
-- SQL Server
SELECT OBJECT_NAME(s.object_id) AS tbl, i.name, s.user_seeks, s.user_scans,
       s.user_lookups, s.user_updates
FROM sys.dm_db_index_usage_stats s
JOIN sys.indexes i ON i.object_id = s.object_id AND i.index_id = s.index_id
WHERE s.database_id = DB_ID() AND s.user_seeks + s.user_scans + s.user_lookups = 0
ORDER BY s.user_updates DESC;      -- pure cost, no benefit

-- PostgreSQL
SELECT relname, indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes WHERE idx_scan = 0 ORDER BY pg_relation_size(indexrelid) DESC;
⚠ Trap — the stats reset on restart

Those counters are cumulative since the last service restart (or since pg_stat_reset()). An index used only by the quarterly report looks unused in January. Check the uptime before you drop anything, and prefer disabling to dropping so you can put it back in one statement.

  1. An index on (a, b, c) serves any leftmost prefix, and nothing else.
  2. Equality columns first, then the range column, then columns needed only for sorting or covering.
  3. Once you use an inequality on a column, later columns can only filter, not narrow the seek.
  4. A covering index removes the lookup entirely and is often the single biggest win available.
  5. INCLUDE adds leaf-level payload without affecting seekability or key width.
  6. Do not cover everything — that is a second copy of the table, written on every insert.
  7. Low selectivity kills an index, unless the distribution is skewed — then use a partial index.
  8. Every index costs writes, space, buffer pool and optimiser search space.
  9. Usage statistics reset on restart. Check uptime before dropping an index nobody appears to use.

Interview questions this chapter answers

Design an index for WHERE status = ? AND placed_at >= ? ORDER BY placed_at.

(status, placed_at): equality first so it can seek, then the range column — which also supplies the ORDER BY, so there is no sort. If the select list is small I would INCLUDE those columns to make it covering.

Why is (a, b) not the same as (b, a)?

An index is sorted left to right, so b is only ordered within a given a. A predicate on b alone therefore cannot seek. Only leftmost prefixes are seekable.

Can you have too many indexes?

Yes. Every one is written on insert and on updates to its columns, occupies buffer pool, enlarges backups, and adds to the optimiser's search space. I would look at the usage statistics for indexes with zero seeks and a high update count — checking server uptime first, because those counters reset.
