JSON and semi-structured data

When a JSON column is the right answer, when it is a schema you refused to design, and how to index one.

No advert asked for this

Every engine grew JSON support and every legacy schema now has a “settings” column. Nobody advertises it; everybody meets it.

When a JSON column is the right answer

🧒 Simple

A filing cabinet has a drawer for each kind of thing, and that is why you can find anything. A JSON column is a drawer labelled “miscellaneous”. Sometimes you genuinely need one. But if everything ends up in it, you do not have a filing cabinet any more — you have a box.

🎓 Professional

Three cases where a JSON column is a good decision:

  1. Genuinely open-ended attributes. Per-tenant custom fields, where the set of keys is defined by customers and not by you.
  2. A payload you received and must keep verbatim. A webhook body, an API response, an audit snapshot. You store it to prove what arrived, and you query the columns you extracted from it — not the blob.
  3. A sparse, rarely-queried settings bag. Forty optional preferences that are read as a unit and never filtered on.

And the case where it is not: a field you filter, join or aggregate on. That is a column. If you find yourself indexing a JSON path because a query needs it, the schema is telling you something.

⚠ Trap

A JSON column has no constraints. No type checking, no NOT NULL, no foreign key, no uniqueness. Every value in it is “whatever the application wrote last Tuesday”, including the typo'd key name that has been silently accumulating for six months. The relational engine cannot help you, which is the entire point of having chosen one.

Reading it, four ways

-- PostgreSQL (jsonb — the binary, indexable one; prefer it to json)
SELECT data ->> 'email'                    AS email,      -- ->> returns text, -> returns jsonb
       (data -> 'prefs' ->> 'lang')        AS lang,
       jsonb_array_length(data -> 'tags')  AS n_tags
FROM events WHERE data @> '{"type":"signup"}';             -- @> is the containment operator

-- SQL Server 2016+
SELECT JSON_VALUE(data, '$.email')          AS email,      -- scalar
       JSON_QUERY(data, '$.prefs')          AS prefs       -- object or array
FROM events WHERE ISJSON(data) = 1;

-- MySQL 5.7+
SELECT data ->> '$.email' AS email FROM events;

-- Oracle 12c+
SELECT JSON_VALUE(data, '$.email') FROM events;
json vs jsonb in PostgreSQL

json stores the exact text, preserving key order and whitespace, and re-parses on every access. jsonb stores a parsed binary form: slightly slower to write, much faster to read, deduplicates keys, loses formatting, and is the only one that can be indexed usefully. Use jsonb unless you must reproduce the original bytes exactly — which is really the "keep the payload verbatim" case, and then a text column is more honest.

Indexing inside a document

-- PostgreSQL: a GIN index supports containment (@>) and key-existence over the WHOLE document.
CREATE INDEX ix_events_data ON events USING GIN (data jsonb_path_ops);

-- Or, far more often what you want: index ONE extracted path with a B-tree.
CREATE INDEX ix_events_email ON events ((data ->> 'email'));

-- SQL Server has no JSON index. You index a computed column instead:
ALTER TABLE events ADD email AS JSON_VALUE(data, '$.email') PERSISTED;
CREATE INDEX ix_events_email ON events (email);
✔ The pattern that actually works in production

Promote the fields you query into real columns — as generated/computed columns derived from the JSON, so there is still one source of truth — and keep the document for everything else. You get constraints, types, statistics and ordinary indexes on the parts that matter, and flexibility on the parts that do not. Describing this in an interview is a much stronger answer than either “JSON is bad” or “we put everything in JSON”. 

-- PostgreSQL 12+: a stored generated column. Always in step, indexable, typed.
ALTER TABLE events
  ADD COLUMN email TEXT GENERATED ALWAYS AS (data ->> 'email') STORED;
CREATE INDEX ix_events_email ON events (email);

Turning a document into rows

-- PostgreSQL: expand an array into rows, then treat it as a normal table.
SELECT e.id, t.tag
FROM events e
CROSS JOIN LATERAL jsonb_array_elements_text(e.data -> 'tags') AS t(tag);

-- SQL Server:
SELECT e.id, t.value AS tag
FROM events e
CROSS APPLY OPENJSON(e.data, '$.tags') AS t;

-- OPENJSON with an explicit schema is how you bulk-load a JSON payload into a table:
INSERT INTO order_lines (order_id, sku, quantity)
SELECT @order_id, j.sku, j.qty
FROM OPENJSON(@payload, '$.lines')
     WITH (sku VARCHAR(32) '$.sku', qty INT '$.quantity') AS j;
-- SQLite (the playground) has JSON1 built in:
SELECT json_extract(data, '$.email')     AS email,
       json_array_length(data, '$.tags') AS n_tags
FROM events
WHERE json_extract(data, '$.type') = 'signup';

-- Then look at the query plan and notice: full scan. Now add
CREATE INDEX ix_ev_type ON events (json_extract(data, '$.type'));
-- and look again.

The honest summary

🎓 What to say when asked “relational or document?”

“A JSON column is the right tool for genuinely schemaless data inside an otherwise relational system — custom fields, stored payloads, sparse settings. What it costs is every guarantee the database exists to provide: types, constraints, referential integrity and statistics. So I use it for the parts of a record nobody queries, promote anything I filter on into a real column, and treat a JSON column that has grown an index on three different paths as a schema waiting to be written.”

  1. JSON is right for open-ended attributes, verbatim payloads and sparse settings — not for anything you filter, join or aggregate.
  2. A JSON column has no types, no constraints and no foreign keys. Everything the engine could have checked, it now cannot.
  3. PostgreSQL: use jsonb, not json. Only jsonb indexes usefully.
  4. Index one extracted path with a B-tree far more often than the whole document with GIN.
  5. SQL Server has no JSON index; index a PERSISTED computed column instead.
  6. Promote queried fields into generated columns: one source of truth, real indexes and statistics.
  7. Expand arrays into rows with jsonb_array_elements / OPENJSON and then use ordinary SQL.
  8. Three indexes on three JSON paths is a schema asking to be written.

Interview questions this chapter answers

When would you store JSON in a relational database?

When the shape is genuinely defined by someone other than me — per-tenant custom fields — or when I must keep a payload verbatim, or for sparse settings read as a unit. Not for anything I filter or join on: that loses types, constraints and statistics for no benefit.

How do you make a query on a JSON field fast?

Index the specific extracted path rather than the document: an expression index in PostgreSQL, a persisted computed column plus an index in SQL Server. If several paths need indexing, that is a signal to promote them to real columns.

What do you lose by using a JSON column?

Type checking, NOT NULL, uniqueness, foreign keys, column statistics and therefore good cardinality estimates. The engine can no longer prevent bad data or plan well against it — which are the two reasons for using a relational database at all.
