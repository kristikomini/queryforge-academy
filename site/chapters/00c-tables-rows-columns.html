Tables, rows, columns and the shape of an answer

The four words the rest of the course is written in — and what a result set is, exactly.

No advert asked for this

Every later chapter uses these words in load-bearing sentences. Getting them precisely right once costs ten minutes and saves fifty pages of quiet confusion.

A table is one kind of thing

🧒 Simple

A table is a list of cards, where every card has the same boxes printed on it. One table for customers, where every card has a name box, an email box and a city box. A different table for orders, where every card has a date box, a total box, and a box saying which customer it belongs to. One card is a row. One printed box, considered across every card, is a column.

🎓 Professional

A table is a relation: a set of tuples over a fixed set of typed attributes. Two consequences follow from “set” and matter constantly. First, rows have no order — the engine may return them in any order it likes unless you ask for one. Second, in the formal model a relation holds no duplicates; real SQL tables allow them, which is exactly why a primary key is the first thing you declare.

Every column has a type, and the type is a promise

Unlike a spreadsheet cell, a column has a declared type and the engine enforces it. A column declared as a date cannot hold “n/a”. That refusal is the feature: it means every query downstream can rely on the column really being a date, forever, without checking.

The primary key: which row is which

If two rows are identical in every column, no query can tell them apart, and no update can change one of them without changing the other. So every table gets a primary key: one or more columns whose value is unique and never NULL.

Tables point at each other

The reason data is split across several tables at all is that repeating a customer's name on every one of their orders means storing the same fact many times — and then having to change it in many places. Instead, an order stores the customer's id, and the engine can be told to enforce that the customer exists.

A result set is a table too

When you run a query, what comes back is rows and columns with a header. That is a table — an unnamed, temporary one. This is the single most useful idea in SQL, because it means the output of one query can be the input of another, forever.

✔ Why “a result is a table” matters so much

Because it composes. A query can select from another query, a view is a saved query used as a table, and a CTE is a named query used as a table. You never learn a new mechanism for “a thing that produces rows” — there is only one, and it is the table.

  1. A table is a set of rows over a fixed set of typed columns; a row is one instance, a column is one property.
  2. Rows have no inherent order. Insertion order is not a promise and relying on it fails silently.
  3. Every table needs a primary key, or its rows cannot be told apart, addressed or corrected.
  4. A surrogate key identifies and never changes; a natural key describes and eventually does. Use a surrogate as the key and a UNIQUE constraint for the natural one.
  5. A foreign key stores a pointer rather than a copy, and the engine enforces that the target exists.
  6. A result set is a table: unnamed and temporary, but composable, which is why queries can be nested at all.
  7. NULL is not zero and not an empty string; it means the value is absent or unknown.

What is the difference between a primary key and a unique constraint?

A primary key is the row's identity: exactly one per table, never NULL, and what other tables point at. A unique constraint says “no two rows share this value” and you can have several, and in most engines it permits NULLs. Practically: id is the primary key, email gets a unique constraint.

Why split data across several tables instead of keeping it in one?

So that each fact is stored once. Repeating the customer's city on every order means the same fact in a thousand places, and a change that has to find all of them — an update anomaly. The cost of splitting is that answering a question needs a join, and that is a trade worth making almost every time. Chapter 05 is the formal version.
