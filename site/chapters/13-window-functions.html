Window functions

ROW_NUMBER, RANK, DENSE_RANK and OVER(PARTITION BY …). The highest-leverage thing in modern SQL.

From the advert

“Ottima conoscenza del linguaggio SQL” — if you learn one thing from this course that changes what you can do at work, it is this chapter.

Aggregate without collapsing

🧒 Simple

GROUP BY puts your receipts into envelopes and you lose the receipts. A window function leaves every receipt on the table and writes a note in the corner of each one: “this is the third biggest in its shop”, “the shop's total is 412”. Nothing is thrown away.

🎓 Professional

A window function computes a value over a set of rows related to the current row without collapsing the result. OVER (PARTITION BY … ORDER BY …) defines that set. Crucially, window functions are evaluated after WHERE, GROUP BY and HAVING, and before ORDER BY — which is exactly why you cannot filter on one in WHERE and always need a wrapping query or CTE to do it. 

SELECT
  customer_id,
  placed_at,
  total_cents,
  SUM(total_cents)   OVER (PARTITION BY customer_id)                       AS customer_total,
  ROW_NUMBER()       OVER (PARTITION BY customer_id ORDER BY placed_at)    AS nth_order,
  total_cents * 100.0
    / SUM(total_cents) OVER (PARTITION BY customer_id)                     AS pct_of_customer
FROM orders;
-- Same number of rows as `orders`. Every row now knows about its neighbours.

⚠ Trap

ROW_NUMBER() breaks ties arbitrarily, and the arbitrary choice can change between runs when the plan changes. If you use it to pick “the one row to keep”, add a deterministic tie-breaker — ORDER BY updated_at DESC, id DESC. Without it, a de-duplication job can delete a different row each time it runs, which is a genuinely horrible bug to diagnose.

Top-N per group: the canonical use

-- The most recent order per customer.
WITH ranked AS (
  SELECT o.*,
         ROW_NUMBER() OVER (PARTITION BY customer_id
                            ORDER BY placed_at DESC, id DESC) AS rn
  FROM orders o
)
SELECT * FROM ranked WHERE rn = 1;
Why the CTE is not optional

WHERE rn = 1 cannot go in the same SELECT, because WHERE is evaluated before window functions exist (chapter 06). Every top-N-per-group query therefore has two levels. If you find yourself writing WHERE ROW_NUMBER() OVER (…) = 1 and getting a syntax error, this is why — and the error message will not tell you.

De-duplication, done properly

-- Keep the newest row per (email); delete the rest. One statement, no temp table.
WITH dupes AS (
  SELECT id,
         ROW_NUMBER() OVER (PARTITION BY LOWER(email)
                            ORDER BY updated_at DESC, id DESC) AS rn
  FROM customers
)
DELETE FROM customers
WHERE id IN (SELECT id FROM dupes WHERE rn > 1);
✔ Before you run this on production

Run the SELECT half first and read the count. Then wrap the delete in an explicit transaction and check the affected row count against that number before committing. “I would run the select first and compare the counts inside a transaction” is a sentence that makes interviewers relax.

Naming a window

Repeating OVER (PARTITION BY customer_id ORDER BY placed_at) five times is how a typo gets into one of them. Standard SQL lets you name it once: 

SELECT customer_id, placed_at,
       ROW_NUMBER() OVER w  AS nth,
       LAG(total_cents) OVER w AS prev_total,
       SUM(total_cents) OVER w AS running_total
FROM orders
WINDOW w AS (PARTITION BY customer_id ORDER BY placed_at)
ORDER BY customer_id, placed_at;
-- PostgreSQL, MySQL 8, SQLite, Oracle. SQL Server does not support WINDOW.

What they cost

🎓 The index that makes them fast

A window function needs its input sorted by PARTITION BY then ORDER BY. An index on exactly (customer_id, placed_at) supplies that order for free and the plan shows no sort operator. Without it, the engine sorts — and if the estimate is wrong, that sort spills to disk, which is the single most common reason a window query is slow. Look for a Sort with a spill warning before you blame the function. 

-- Every customer's orders, numbered, with their share of the customer's spend
-- and the gap in days since their previous order. One pass.
SELECT customer_id, id, placed_at,
       ROW_NUMBER() OVER w                              AS nth_order,
       ROUND(100.0 * total_cents
             / SUM(total_cents) OVER (PARTITION BY customer_id), 1) AS pct,
       julianday(placed_at) - julianday(LAG(placed_at) OVER w)      AS days_since_prev
FROM orders
WINDOW w AS (PARTITION BY customer_id ORDER BY placed_at)
ORDER BY customer_id, placed_at;
  1. A window function adds a column about neighbouring rows without collapsing the result.
  2. Window functions run after WHERE/GROUP BY/HAVING and before ORDER BY. Filtering one always needs a CTE or derived table.
  3. ROW_NUMBER gives distinct numbers, RANK skips after ties, DENSE_RANK does not.
  4. ROW_NUMBER breaks ties arbitrarily and non-deterministically. Add a tie-breaker whenever the result decides something.
  5. Top-N per group is ROW_NUMBER() OVER (PARTITION BY … ORDER BY …) filtered in an outer query.
  6. De-duplicate by ranking within the duplicate key and deleting rn > 1 — after checking the count.
  7. Name a repeated window with WINDOW w AS (…) — everywhere except SQL Server.
  8. An index on (partition cols, order cols) removes the sort. A spilling sort is the usual cause of a slow window query.

Interview questions this chapter answers

Difference between ROW_NUMBER, RANK and DENSE_RANK?

On ties: ROW_NUMBER gives each row a distinct number arbitrarily; RANK gives ties the same number and then skips (1,1,3); DENSE_RANK gives ties the same number without skipping (1,1,2). Use ROW_NUMBER when you need exactly one row per group, DENSE_RANK for “the nth distinct value”.

Find the second-highest salary.

DENSE_RANK() OVER (ORDER BY salary DESC) filtered to 2, because the question means the second distinct salary — ROW_NUMBER would return the second row, which is the same salary again if the top two are tied. Mentioning that distinction unprompted is the point of the question.

Why can't I write WHERE ROW_NUMBER() OVER (…) = 1?

Because WHERE is evaluated before window functions are computed, so the value does not exist yet. Wrap the query in a CTE or derived table and filter in the outer level. Same reason you cannot use a SELECT alias in WHERE.
