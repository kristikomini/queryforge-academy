Aggregation, GROUP BY and HAVING

COUNT(*) vs COUNT(col), why HAVING is not a second WHERE, and the grouping error the engine will not catch.

From the advert

“Ottima conoscenza del linguaggio SQL” — every reporting task you will ever be given is an aggregation with a filter argument attached.

Grouping changes the grain

🧒 Simple

You have a pile of receipts. You sort them into envelopes — one envelope per shop — and then you write one number on the outside of each envelope. Afterwards you no longer have receipts; you have envelopes. You cannot ask “what time was this receipt?” any more, because there is no “this receipt”, only a shop.

🎓 Professional

GROUP BY changes the grain of the result: after it, one output row represents a set of input rows. Every column in SELECT must therefore be either a grouping column or inside an aggregate — because for anything else the question “which of the twelve values do you mean?” has no answer. Standard SQL rejects this; MySQL historically returned an arbitrary value, which is worse than an error because it looks like it worked.

Functional dependency, the one legal exception

PostgreSQL and MySQL (with ONLY_FULL_GROUP_BY) allow selecting a column that is functionally dependent on the grouping key — grouping by customers.id lets you select customers.name, because the primary key determines it and there can only be one value. It is legal, it is convenient, and it is non-portable. SQL Server requires every column in the GROUP BY.

⚠ Trap

COUNT(DISTINCT …) is expensive: it requires a sort or hash of all the values and it does not parallelise as well as a plain count. Several of them in one query multiply that cost. If a dashboard is slow and has four COUNT(DISTINCT)s, that is your answer before you look at anything else — and the fix is usually pre-aggregation (chapter 32), or an approximate count (APPROX_COUNT_DISTINCT, HyperLogLog) if the number is a dashboard tile rather than an invoice.

HAVING is not a second WHERE

The rule: if the condition does not involve an aggregate, it belongs in WHERE. Putting status <> 'cancelled' in HAVING gives the same answer and makes the engine group rows it is about to throw away.

Conditional aggregation: the technique that replaces five queries

🎓 One pass, many answers

Because aggregates ignore NULL, a CASE inside an aggregate acts as a filter for that column alone. This turns “count the shipped ones, count the cancelled ones, and total the confirmed ones” from three scans into one.

Note the missing ELSE

CASE WHEN … THEN 1 END with no ELSE yields NULL for non-matches, and COUNT ignores nulls — which is exactly what you want. Writing ELSE 0 there would count everything. For SUM the reverse is true: ELSE 0 is harmless and makes the intent obvious.

GROUPING SETS, ROLLUP and CUBE

Subtotals in one pass, rather than three queries glued together with UNION ALL:

Those NULLs are ambiguous — is it a subtotal, or a genuine null city? — which is what GROUPING() is for: it returns 1 when the null was produced by the rollup. GROUPING SETS gives you arbitrary combinations; CUBE gives you all of them.

  1. GROUP BY changes the grain: one output row now stands for many input rows.
  2. Every selected column must be grouped or aggregated. MySQL's old behaviour of picking one arbitrarily is worse than an error.
  3. COUNT(*) counts rows; COUNT(col) counts non-nulls; COUNT(1) is identical to COUNT(*) and no faster.
  4. COUNT(DISTINCT) needs a sort or hash. Several in one query is a common cause of a slow dashboard.
  5. A condition without an aggregate belongs in WHERE, not HAVING.
  6. Conditional aggregation answers several questions in one scan, because aggregates ignore nulls.
  7. In COUNT(CASE …) omit the ELSE; in SUM(CASE …) write ELSE 0.
  8. ROLLUP produces subtotals in one pass; GROUPING() tells you which nulls it created.

Interview questions this chapter answers

WHERE or HAVING — which and why?

WHERE filters rows before grouping and can use an index; HAVING filters groups after and is the only option for a condition on an aggregate. Anything that does not mention an aggregate should be in WHERE, so the grouping does less work.

Count shipped and cancelled orders per customer in one query.

Conditional aggregation: COUNT(CASE WHEN status='shipped' THEN 1 END) and the same for cancelled, grouped by customer. One scan instead of two, and the null-ignoring behaviour of COUNT is what makes it work.

Is COUNT(1) faster than COUNT(*)?

No. Every mainstream optimiser treats them identically; the plans are the same. The real distinction is COUNT(column), which skips nulls and is a different question.
