JOINs, semi-joins and anti-joins

INNER, LEFT, FULL, CROSS, self — plus the two joins that have no keyword and are asked about constantly.

From the advert

“Ottima conoscenza del linguaggio SQL” — if there is one thing every SQL interview tests, it is whether you understand joins beyond “INNER keeps matches”.

A join is a filtered cross product

🧒 Simple

Put every customer card next to every order card — every possible pairing, which is a huge pile. Now throw away every pair where the names do not match. What is left is the join. The database does not literally do it that way, but if you think of it that way you will never be surprised by the number of rows you get back.

🎓 Professional

Logically, A JOIN B ON p is the Cartesian product of A and B restricted to rows satisfying p. Outer joins then add back the rows from the preserved side that found no partner, padded with NULL. That is the whole definition, and it explains both the row counts and why NULL behaves the way it does in the result.

JoinKeepsTypical use
INNER JOINOnly matching pairsThe default. Orders with their customer
LEFT JOINAll left rows; nulls where no match“…and their orders, if any”
RIGHT JOINAll right rowsRare. Rewrite as a LEFT and swap the tables — it reads better
FULL OUTER JOINAll rows from both sidesReconciliation: what is in one system and not the other
CROSS JOINEvery pairingDeliberate: a calendar table × every product, to make gaps visible
self joinA table joined to itselfEmployee → manager, hierarchies, comparing a row to its neighbour

The two joins with no keyword

These are asked about constantly and have no dedicated syntax, which is exactly why they separate candidates.

🎓 Semi-join — “does a match exist?”

Returns rows from the left table that have at least one match, without duplicating them and without returning any right-hand columns. Written as EXISTS. A plain INNER JOIN is not the same thing: a customer with three orders comes back three times.

🎓 Anti-join — “where is there no match?”

Rows from the left table with no match. Written as NOT EXISTS, or as a LEFT JOIN … WHERE right.key IS NULL. Do not write it as NOT IN over a nullable column — see the trap below.

⚠ Trap — NOT IN and a single NULL

If the subquery returns even one NULL, NOT IN returns no rows at all. Not an error — an empty result. The reason is three-valued logic: x NOT IN (1, 2, NULL) expands to x <> 1 AND x <> 2 AND x <> NULL, and the last term is UNKNOWN, so the whole conjunction can never be TRUE.

NOT EXISTS does not have this behaviour, handles the null case correctly, and usually produces the same or a better plan. Use NOT EXISTS. This is one of the highest-value facts in the whole course: it is asked often, and it has caused silent data loss in a report that "worked yesterday".

Fan-out: the duplicate-row bug

⚠ Trap — the report that is exactly 3× wrong

This is the classic "the totals on the invoice report are wrong" ticket. The instinct is to add DISTINCT, which removes the duplicate rows but does nothing for a SUM, and hides the real bug. The fix is to aggregate each branch before joining, so each side contributes exactly one row per order.

The three join algorithms

You do not choose these — the optimiser does — but recognising them in a plan is most of what plan reading is.

AlgorithmHow it worksGood whenBad when
Nested loopsFor each outer row, seek the innerOuter input is small and the inner side is indexedOuter is large — you get millions of seeks
Hash joinBuild a hash table on the smaller input, probe with the largerBig unsorted inputs, equality joinsNeeds memory; spills to disk if the estimate was wrong
Merge joinWalk both inputs in sorted orderBoth already sorted on the join keyRequires a sort if they are not
✔ The diagnosis this gives you

A nested loops join whose outer input was estimated at 10 rows and actually produced 400 000 is the single most common shape of “this query used to be fast”. The engine chose loops because it expected a small input; the estimate was wrong, so it is now doing 400 000 index seeks. The fix is upstream — statistics, or a predicate the optimiser cannot estimate — not the join itself. See chapter 28.

  1. A join is a cross product filtered by ON; an outer join adds back the unmatched rows, null-padded.
  2. ON defines the match; WHERE filters the result. A right-table predicate in WHERE turns a LEFT JOIN into an inner join.
  3. Use NOT EXISTS for anti-joins. NOT IN returns nothing at all if the subquery yields a single NULL.
  4. EXISTS is a semi-join: it does not duplicate the left row and does not need DISTINCT.
  5. Joining two one-to-many children of the same parent multiplies rows. Pre-aggregate each branch instead.
  6. DISTINCT as a fix for duplicates hides a fan-out and does not fix the aggregates.
  7. In a LEFT JOIN, COUNT(*) counts unmatched rows as one. COUNT(right.col) counts zero.
  8. Nested loops for small outer inputs, hash for large unsorted ones, merge for pre-sorted. A loops join over a badly estimated outer input is the classic regression.

Interview questions this chapter answers

Difference between WHERE and ON in an outer join?

ON decides which rows pair up; unmatched rows are still preserved and null-padded. WHERE runs after the join and filters the result, so a predicate on the non-preserved table eliminates the null-padded rows and silently converts the outer join to an inner one.

Find customers with no orders.

SELECT c.* FROM customers c WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id). Then add why not NOT IN: a single null in the subquery makes the whole predicate UNKNOWN and returns an empty set.

The totals in this report are three times too high. What happened?

A fan-out: two one-to-many joins from the same parent, so the rows multiply and the parent's value is summed once per combination. The fix is to aggregate each child branch in a derived table or CTE first, then join those one-to-one. DISTINCT would remove the duplicate rows but leave the sums wrong.
