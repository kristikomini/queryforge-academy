The screening test

The take-home and the live exercise: what they really check, and the twelve queries that keep appearing.

No advert asked for this

Written from the exercises actually set by Italian software houses for junior database roles.

What they are really checking

🧒 Simple

They are not checking whether you can remember the exact word for something. They are checking that when you are given a table and a question, something sensible happens — and that you say out loud what you are doing while it happens.

🎓 Four things, in this order of weight
  1. Do you produce a correct query? Syntax is forgiven; a wrong answer stated confidently is not.
  2. Do you handle the edge cases? Nulls, ties, zero rows, division by zero. This is the single biggest discriminator, because most candidates write the happy path and stop.
  3. Do you narrate? An interviewer cannot mark silence. Saying “I will use a left join here so customers with no orders are kept” is worth as much as the join.
  4. Do you ask about the data? “Can customer_id be null?” “Are there ties?” Asking is a senior behaviour and it is being watched for explicitly.

The twelve exercises that keep appearing

Work each of these in the playground against the reference database before an interview. Not to memorise the answers — to make the shape automatic.

1 · Second-highest value

-- DENSE_RANK, because "second highest salary" means the second DISTINCT value.
SELECT DISTINCT salary_cents FROM (
  SELECT salary_cents, DENSE_RANK() OVER (ORDER BY salary_cents DESC) AS r
  FROM employees) t
WHERE r = 2;
-- Say why not ROW_NUMBER: with a tie at the top it returns the same salary again.

2 · Nth per group (top-N per group)

WITH r AS (SELECT o.*, ROW_NUMBER() OVER (PARTITION BY customer_id
                                          ORDER BY placed_at DESC, id DESC) rn
           FROM orders o)
SELECT * FROM r WHERE rn = 1;
-- The tie-breaker on id is the detail they are looking for.

3 · Find and delete duplicates

WITH d AS (SELECT id, ROW_NUMBER() OVER (PARTITION BY LOWER(email)
                                         ORDER BY id) rn FROM customers)
SELECT * FROM d WHERE rn > 1;         -- LOOK first
-- DELETE FROM customers WHERE id IN (SELECT id FROM d WHERE rn > 1);
-- Then say: "and I would add the unique constraint that should have prevented it."

4 · Rows in A not in B

SELECT c.* FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);
-- Say why NOT EXISTS and not NOT IN. This is the most-tested single fact in SQL.

5 · Running total

SELECT placed_at, total_cents,
       SUM(total_cents) OVER (PARTITION BY customer_id
                              ORDER BY placed_at
                              ROWS UNBOUNDED PRECEDING) AS running
FROM orders;
-- The explicit ROWS is the detail: the RANGE default gives every same-day row
-- the same day-end total.

6 · Month-on-month change

WITH m AS (SELECT strftime('%Y-%m', placed_at) mo, SUM(total_cents) t
           FROM orders GROUP BY mo)
SELECT mo, t, LAG(t) OVER (ORDER BY mo) AS prev,
       ROUND(100.0 * (t - LAG(t) OVER (ORDER BY mo))
             / NULLIF(LAG(t) OVER (ORDER BY mo), 0), 1) AS pct
FROM m ORDER BY mo;
-- NULLIF guards the division. They will check.

7 · Pivot without PIVOT

SELECT strftime('%Y-%m', placed_at) mo,
       COUNT(CASE WHEN status = 'delivered' THEN 1 END) delivered,
       COUNT(CASE WHEN status = 'cancelled' THEN 1 END) cancelled
FROM orders GROUP BY mo;

8 · Gaps and islands

-- Consecutive runs: group by (value − row_number). Chapter 14.

9 · Hierarchy

-- Recursive CTE with an anchor, UNION ALL, and a depth guard. Chapter 12.

10 · Customers above average

SELECT customer_id, SUM(total_cents) spend FROM orders GROUP BY customer_id
HAVING SUM(total_cents) > (SELECT AVG(t) FROM
       (SELECT SUM(total_cents) t FROM orders GROUP BY customer_id));
-- The trap: "average" of WHAT? Average order value, or average customer spend?
-- Ask. The question is deliberately ambiguous and asking is the point.

11 · Fill the gaps in a date series

-- LEFT JOIN from a calendar table or a recursive date spine, with COALESCE(n, 0).
-- The trap is putting the date filter in WHERE and re-inner-joining. Chapter 06.

12 · “Optimise this query”

-- Almost always one of: a function on the filtered column, a correlated subquery
-- repeated three times, a fan-out hidden by DISTINCT, or SELECT *. Chapter 29.
-- SAY WHAT YOU ARE LOOKING FOR as you scan it. That is the answer they want.

The edge cases that separate candidates

✔ Five sentences to have ready
  • “I will use LEFT JOIN and COUNT(o.id) so customers with no orders show zero rather than one.”
  • “NOT EXISTS rather than NOT IN, because a single null in the subquery makes NOT IN return nothing.”
  • “I will add id as a tie-breaker so the ordering is deterministic.”
  • “NULLIF on the denominator so a zero does not error.”
  • “Is this run often? Then I would want an index on (customer_id, placed_at) — equality first, then the range.”

The take-home

🎓 What actually gets marked
  1. Does it run? Against a clean database, from the instructions in your README. A submission that does not run is not marked.
  2. Is it readable? CTEs with names, consistent formatting, and a comment wherever a decision was made rather than wherever the syntax was unusual.
  3. Did you handle the messy data they deliberately put in? There is always a null, a duplicate or a negative value. Finding it and saying what you did about it is most of the mark.
  4. Did you state your assumptions? A short README saying “I assumed cancelled orders are excluded from revenue; if not, remove line 14” is worth more than getting the ambiguous case right by luck.
⚠ Do not over-engineer it

A take-home with a Docker Compose stack, a migration framework and ninety tests for a four-query exercise signals poor judgement about scope, not enthusiasm. Do what was asked, do it well, add one thing that shows care — usually the README with assumptions — and stop. And respect the stated time limit; if it says four hours, spend four hours and note what you would do with more.

The live exercise

✔ How to behave when you are stuck on a call
  1. Restate the question. “So: one row per customer, with their most recent order — including customers with no orders?” Half the time this reveals a misunderstanding before you have written anything.
  2. Say the approach before the syntax. “I will rank orders per customer by date and take the first.” If the approach is wrong they will stop you, which saves five minutes of typing.
  3. Say what you are unsure about. “I think it is ROWS UNBOUNDED PRECEDING — I would check the exact frame syntax.” Interviewers are fine with this and are not fine with confident wrongness.
  4. If you are properly stuck, say so and offer a worse solution. “I cannot remember the window syntax; I could do it with a correlated subquery, which is slower but correct.” Getting to an answer is the point.
Looking things up

Ask: “may I check the syntax?” Almost every interviewer says yes, because it is what you would do at work. What they are watching is whether you know what to look up — which is the real skill, and is unaffected by having the documentation open.

  1. They are checking correctness, edge cases, narration and whether you ask about the data.
  2. Edge cases are the biggest discriminator: nulls, ties, zero rows, division by zero.
  3. Narrate. An interviewer cannot mark silence.
  4. Restate the question before writing anything.
  5. Say the approach before the syntax, so a wrong approach is stopped early.
  6. Say what you are unsure of. Confident wrongness is the thing that loses.
  7. Practise the twelve shapes until they are automatic, not memorised.
  8. On a take-home: make it run, state your assumptions, handle the deliberate mess, and stop.
  9. Respect the stated time limit and note what you would do with more.
  10. Ask to check syntax. Knowing what to look up is the skill being tested.

Interview questions this chapter answers

Write a query for the second-highest salary.

DENSE_RANK() OVER (ORDER BY salary DESC) filtered to 2 — and say why: the question means the second distinct salary, so ROW_NUMBER would return the same value again if the top two are tied. Then ask what should happen if there is no second distinct value.

Find customers who placed no orders last month.

Watch the trap: the date filter must be inside the NOT EXISTS or the ON clause, not in WHERE, or the outer join collapses to an inner one and you get "customers with no orders at all" instead. Saying that out loud is the answer.

Here is a slow query. What would you do?

Narrate the checklist as you read it: is a function wrapping a filtered column, is there a correlated subquery repeated per row, is there a DISTINCT hiding a fan-out, is it selecting columns nobody uses. Then say I would confirm with an actual plan and look at the estimate-versus-actual gap before changing anything.
