The dialects: SQL Server, Oracle, PostgreSQL, MySQL

The same query in four dialects, the differences that matter, and how to answer “which do you know?”.

From the advert

“Ottima conoscenza del linguaggio MS T-SQL” — and the honest reassurance that T-SQL is the standard you already know plus a lookup table you can absorb in a week.

Most of it is the same

🧒 Simple

Italian, Spanish and Portuguese. If you speak one properly you can read the others on day one and speak one badly by the end of the week. The grammar is shared; what changes is a few hundred words and a handful of habits.

SELECT, joins, GROUP BY, subqueries, CTEs and window functions are standard and behave the same everywhere. What differs is the top-N syntax, the date functions, string concatenation, identity generation and the procedural language — and that is genuinely most of the list.

The differences that are not syntax

🎓 Six that change how you design, not just how you type
  1. Clustering. SQL Server and InnoDB cluster by the primary key, so that choice is a physical storage decision and every secondary index inherits its width. PostgreSQL has no clustered index at all.
  2. Concurrency model. PostgreSQL, Oracle and InnoDB are MVCC by default; SQL Server locks until you enable READ_COMMITTED_SNAPSHOT. That single setting changes how much of the legacy T-SQL you will read makes sense.
  3. Transactional DDL. PostgreSQL and SQL Server yes; MySQL and Oracle no. This decides how migrations must be written (chapter 36).
  4. The empty string. Oracle treats '' as NULL. Every other engine treats it as a zero-length string. This causes genuine bugs when porting and it is the single most surprising Oracle behaviour.
  5. Nulls in a unique index. SQL Server allows one; PostgreSQL, Oracle and MySQL allow many.
  6. Case sensitivity. PostgreSQL folds unquoted identifiers to lowercase, Oracle to uppercase. So a quoted "MyTable" in one is not the same object as MyTable — the classic cause of "the table exists but the query says it does not".

The Oracle trap worth knowing

Writing portable SQL — and when not to

✔ Cheap portability, worth doing by default
  • COALESCE rather than ISNULL/NVL — standard, n-ary, and it will not truncate your default.
  • CASE rather than IIF/DECODE.
  • Explicit JOIN syntax, never comma joins with conditions in WHERE.
  • Standard FETCH FIRST … ROWS ONLY where the engine supports it.
  • Half-open date ranges rather than BETWEEN.
⚠ Expensive portability, usually not worth it

Avoiding window functions because an ancient version lacked them; refusing ON CONFLICT and hand-rolling an upsert; building an abstraction layer so the SQL could target four engines. That last one is the classic: almost nobody ever changes engine, and the abstraction costs you the specific features that made the engine worth choosing. Portability is a habit worth having and a project worth refusing.

Answering “which databases do you know?”

✔ Depth in one, honest levels for the rest

“SQL Server is where I am deepest — I have written the reporting views and done the query tuning, and I am comfortable in T-SQL including error handling and execution plans. I read PL/SQL comfortably and have written simple procedures, but I have not shipped a package. I use PostgreSQL for personal projects and prefer it, and I know the main differences from SQL Server: no clustered index, MVCC by default, transactional DDL.”

Three named levels, one concrete claim each, and one sentence that proves the comparison is real. It beats a list of nine products every time — and it is unbluffable, which is the point.

  1. The standard is most of it. The differences are top-N, dates, concatenation, identity and the procedural language.
  2. SQL Server and InnoDB cluster by the primary key; PostgreSQL has no clustered index.
  3. SQL Server blocks readers on writers until READ_COMMITTED_SNAPSHOT is enabled.
  4. DDL is transactional in PostgreSQL and SQL Server, not in MySQL or Oracle.
  5. Oracle treats the empty string as NULL. Nothing else does.
  6. SQL Server permits one null in a unique index; the others permit many.
  7. PostgreSQL folds unquoted identifiers to lower case, Oracle to upper case.
  8. ROWNUM is applied before ORDER BY. Use FETCH FIRST.
  9. Cheap portability is a habit; a database abstraction layer is a project that rarely pays.
  10. Claim depth in one engine with a concrete example, and give honest levels for the rest.

Interview questions this chapter answers

You only know PostgreSQL and we use SQL Server. Is that a problem?

The language is largely the same — joins, grouping, CTEs, window functions are standard. What I would need to absorb is the T-SQL spellings and the procedural dialect, which is a week, and the behavioural differences that matter: clustered indexes, the locking model unless read-committed snapshot is on, and identity versus sequences. I would rather name those specifically than claim it is nothing.

Name a difference between SQL Server and PostgreSQL that affects design.

Clustered indexes. In SQL Server the primary key normally determines physical row order and every non-clustered index carries it as the row locator, so the key's width and sequentiality matter enormously. PostgreSQL has no clustered index — the table is a heap and every index is secondary — so that whole consideration disappears.

Should SQL be written to be portable across engines?

The cheap parts, yes — COALESCE, explicit joins, standard FETCH FIRST, half-open date ranges. Building an abstraction layer so the same code runs on four engines, no: almost nobody changes engine, and it costs exactly the features that made the engine worth choosing.
