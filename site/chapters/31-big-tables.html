Big tables: partitioning, archiving, sharding

Partition elimination, the sliding window, and the honest answer about when you need any of it.

No advert asked for this

Adverts say “grandi moli di dati” without saying what to do about it. This is what to do about it.

Start by not needing any of this

✔ The answer that shows judgement

Before partitioning: is the working set the problem, or the table? A billion-row table where every query filters to last month is not a big-table problem — it is an indexing problem, and the right index makes the other 999 million rows irrelevant. Partitioning is for when you need to manage the data in chunks: load it, archive it, drop it, or compress it by age. Reaching for it as a performance fix is the classic mistake, and saying so is worth more than reciting the syntax.

Partitioning

🧒 Simple

One enormous filing cabinet becomes twelve smaller ones, one per month. It is still one filing system and you look things up the same way — but when somebody asks for March you open one drawer, and when the year ends you throw away a whole drawer instead of picking out sheets one at a time.

Partition elimination is the payoff — and it is conditional

⚠ Trap — partitioning can make queries slower

A query that does not filter on the partition key now touches n indexes instead of one, and merges n sorted streams instead of reading one. So partitioning by month and then querying by customer_id is worse than not partitioning at all. Choose the partition key from how the data is queried and managed, and accept that one key cannot serve every access pattern.

The sliding window

The real reason range partitioning earns its complexity: retention becomes metadata, not work.

🎓 Compare that with the alternative

DELETE FROM orders WHERE placed_at < '2025-02-01' on 40 million rows: hours of work, a transaction log the size of the data, lock escalation, index fragmentation, and bloat to vacuum afterwards. The partition switch is a metadata update. That is the argument for partitioning, and it is an argument about operations, not about SELECT speed.

Archiving without partitioning

Most systems that think they need partitioning need this instead:

Three details that make it safe
  1. Bounded batch size, so each transaction stays under the lock escalation threshold and the log can truncate between batches.
  2. Ordered by the key, so each batch is a contiguous index range rather than a scan of the whole table looking for survivors.
  3. A pause between batches in a busy system, so other work gets through. Ten minutes of polite deletion beats one minute of blocking everything.

Sharding, and what it really costs

🎓 Partitioning splits a table. Sharding splits a database.

Sharding puts different rows on different servers, which is the only way past one machine's write capacity. What you give up is significant and permanent:

  • No cross-shard transactions. ACID stops at the shard boundary.
  • No cross-shard joins or foreign keys. Both move into application code.
  • Rebalancing is a project, not a maintenance task — which is why consistent hashing and "many more logical shards than physical servers" exist.
  • Every query needs the shard key, or it fans out to all of them.
✔ The honest ladder, in order
  1. Index properly. Most "too big" tables are an indexing problem.
  2. Archive what nobody queries.
  3. Read replicas, if the load is reads.
  4. Partition, for manageability and retention.
  5. A bigger machine — genuinely, this buys years and costs less than the alternatives.
  6. Shard, when writes exceed one machine and you have exhausted the rest.

Being able to give that ladder — and say “most systems never get past step 4” — is a much better answer than describing a sharding scheme.

  1. Most big-table problems are indexing problems. Check that first.
  2. Partitioning is for manageability — loading, archiving, dropping by age — more than for speed.
  3. Partition elimination only happens when the predicate is on the raw partition key.
  4. A query that does not filter on the partition key is slower when partitioned.
  5. The partition key must be in the primary key, because uniqueness cannot be enforced across partitions cheaply.
  6. Detaching a partition is a metadata operation; deleting the same rows is hours of logged work.
  7. Batched, ordered, bounded deletes are the archiving strategy for everyone who is not partitioned.
  8. Sharding costs cross-shard transactions, joins and foreign keys, permanently.
  9. Index, archive, replicate, partition, bigger machine, and only then shard.

Interview questions this chapter answers

When would you partition a table?

When I need to manage the data in chunks — a retention policy where dropping a month should be a metadata operation, or a load that replaces one slice at a time. Not as a first response to slowness: if queries filter to a small subset, an index does that better, and partitioning actively hurts queries that do not filter on the partition key.

How would you delete 40 million old rows from a live table?

In batches of a few thousand, ordered by the primary key, each in its own transaction, looping until nothing is affected — so locks never escalate and the log can truncate between batches. If the table were range-partitioned by date I would detach and drop the partition instead, which is a metadata operation.

Partitioning or sharding?

Partitioning splits a table within one database and keeps transactions, joins and constraints. Sharding splits across servers and gives all three up, so it is the last step, not an early one. I would index, archive, add read replicas, partition and buy a bigger machine first — most systems never need to go further.
