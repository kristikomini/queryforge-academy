Transactions and ACID

BEGIN, COMMIT, ROLLBACK, savepoints — and what each of the four letters actually buys you.

From the advert

“Esperienza su ambienti di produzione” — production is where you find out what a transaction actually guarantees, usually at the worst possible moment.

ACID, one letter at a time

🧒 Simple

Moving money between two piggy banks is two actions: take out of one, put into the other. If the lights go out in the middle, you must not end up with the money in neither. A transaction is a promise that the pair either both happen or neither does — there is no in-between anyone can see.

🎓 The C is the one worth being sceptical about

Consistency in ACID means only “the database moves from one state satisfying its declared constraints to another”. If you declared no constraints, it promises nothing at all. It is not the same word as the C in CAP, and it is not a guarantee that your business rules hold — it is a guarantee that the rules you wrote down hold. Saying that out loud in an interview is a very cheap way to sound like you have thought about it.

Beginning, committing, and the thing about autocommit

⚠ Trap — you are probably in autocommit right now

Every mainstream client defaults to autocommit: each statement is its own transaction and commits as it completes. So the two updates above, run without BEGIN, are two transactions, and a crash between them leaves money that has left one account and arrived nowhere. Oracle is the exception — it starts a transaction implicitly and requires an explicit COMMIT, which surprises people coming the other way.

Savepoints: a partial rollback

Savepoints are what an ORM uses to implement nested transactions — there is no such thing as a genuinely nested transaction in SQL, so the inner “transaction” becomes a savepoint. Worth knowing because it explains why an inner rollback in your ORM does not abort the outer one.

⚠ Trap — SQL Server's nested transaction count is a lie

In T-SQL, a nested BEGIN TRANSACTION only increments @@TRANCOUNT. A nested COMMIT decrements it and commits nothing; only the outermost commit is real. But a ROLLBACK TRANSACTION — at any depth — rolls back everything and sets the count to zero. So nesting looks symmetric and is not. Use savepoints if you need partial rollback, and check @@TRANCOUNT in error handlers.

Long transactions are the real production problem

🎓 What a long transaction costs, by engine
  • PostgreSQL: it holds back the vacuum horizon, so dead row versions accumulate across the whole database. One forgotten open transaction is the single most common cause of table bloat.
  • SQL Server: the transaction log cannot truncate past the oldest active transaction, so the log grows until the volume fills.
  • All of them: locks are held to the end of the transaction, so everyone else waits longer.
⚠ Never hold a transaction open across a network call

BEGIN → call a payment API → COMMIT means your database transaction now lasts as long as somebody else's HTTP timeout, holding locks the whole time. The same applies to waiting for user input. Do the external work outside, and reconcile with an idempotency key (chapter 20) or a transactional outbox.

Is DDL transactional?

EngineDDL in a transaction?
PostgreSQLYes — CREATE TABLE, ALTER, even DROP, all rollback-able. Migrations can be atomic
SQL ServerMostly yes
MySQL / MariaDBNo — DDL causes an implicit commit. A failed migration leaves you half-migrated
OracleNo — implicit commit before and after

This single difference shapes how you write migrations: on PostgreSQL a migration can be one atomic unit, and on MySQL every step must be independently safe to have half-applied. See chapter 36.

  1. Atomicity is all-or-nothing; isolation is what other sessions can see meanwhile. They are different letters for a reason.
  2. Consistency in ACID only means “the constraints you declared still hold”. Declare none and it promises nothing.
  3. Durability means it survives a crash, not a dead disk. That is backups.
  4. You are in autocommit unless you said otherwise — except in Oracle, where you are not.
  5. Savepoints give partial rollback and are how ORMs fake nested transactions.
  6. In T-SQL, a nested COMMIT commits nothing but a ROLLBACK at any depth rolls back everything.
  7. Long transactions bloat PostgreSQL, grow the SQL Server log, and make everyone else wait.
  8. Never hold a transaction open across a network call or user input.
  9. DDL is transactional in PostgreSQL and SQL Server, and is not in MySQL or Oracle. That decides how migrations must be written.

Interview questions this chapter answers

Explain ACID.

Atomicity: all statements or none, via the undo log. Consistency: declared constraints hold at commit — which is weaker than people assume. Isolation: concurrent transactions do not corrupt each other, to the degree the isolation level specifies. Durability: once committed it survives a crash, because the log was flushed before the commit returned.

Why are long-running transactions a problem?

They hold locks to the end, so contention rises. In PostgreSQL they hold back the vacuum horizon and cause bloat across the whole database; in SQL Server they prevent the log truncating. And a transaction held open across an external HTTP call lasts as long as somebody else's timeout.

Can you roll back a CREATE TABLE?

In PostgreSQL and SQL Server, yes — DDL is transactional, which is why a migration can be atomic there. In MySQL and Oracle, no: DDL causes an implicit commit, so a failed multi-step migration leaves the schema half-changed and every step must be independently safe.
