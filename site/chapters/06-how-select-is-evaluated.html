How a SELECT is really evaluated

FROM before WHERE before GROUP BY before SELECT. Nearly every beginner error is this one order.

From the advert

“Ottima conoscenza del linguaggio SQL” — “ottima” starts with knowing that the clauses do not run in the order they are written. Almost every beginner error is this one fact.

Written order is not evaluation order

🧒 Simple

You write a shopping list starting with “I want apples”, but you do it in a different order: first you go to the shop, then you walk to the fruit aisle, then you look at what is there, then you pick apples, then you queue. SQL is the same. You say SELECT first, but the database does it almost last — it has to know which rows it is looking at before it can decide what to show you about them.

Four things this explains

🎓 1 · You cannot use a SELECT alias in WHERE

WHERE runs at step 2; the alias is created at step 5. It does not exist yet, and the error message — “invalid column name” — sounds like a typo rather than an ordering problem. Repeat the expression, or wrap the query in a derived table or CTE.

🎓 2 · ORDER BY can use an alias

Because it runs at step 6, after SELECT. So ORDER BY spend DESC is legal in exactly the query where WHERE spend > … is not. That asymmetry looks arbitrary until you know the order, and then it is obvious — which is precisely why interviewers like the question.

🎓 3 · WHERE and HAVING are not interchangeable

WHERE filters rows before grouping; HAVING filters groups after. Where a condition could go in either, put it in WHERE: it can use an index, and it removes rows the aggregate would otherwise have had to read. Filtering in HAVING what you could have filtered in WHERE is correct and slower — and saying why it is slower is the answer that lands.

🎓 4 · A LEFT JOIN condition in WHERE is an INNER JOIN

The join happens at step 1, producing NULLs for unmatched rows. WHERE then runs at step 2 — and a predicate on the right-hand table is UNKNOWN for those NULLs, so they are dropped. The outer join has been silently undone. If the condition is part of the matching rule it belongs in ON; if it is a filter on the result it belongs in WHERE. See chapter 08.

"Logical" order, not physical order

The clarification that separates good candidates from great ones

This ordering is a semantic definition, not a description of what the engine does. The optimiser will happily push a WHERE predicate down inside a join, use an index to satisfy ORDER BY without sorting, or stop early because of a LIMIT. It may do anything at all provided the answer is the same as if it had followed this order. So the order tells you what your query means; the execution plan tells you what actually happened. Say both halves of that and you have answered the follow-up before it was asked.

⚠ Trap

SELECT DISTINCT is evaluated after SELECT, so it deduplicates the projected rows — including columns you added only to make the output readable. Adding o.id to a SELECT DISTINCT makes every row unique and silently disables the deduplication. When DISTINCT appears as a fix for duplicates, the real bug is almost always a fanning join; see chapter 08.

  1. Evaluation order is FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT.
  2. Aliases are born in SELECT, so ORDER BY can use them and WHERE cannot.
  3. WHERE filters rows, HAVING filters groups. If it can go in WHERE, put it there.
  4. A predicate on the outer table of a LEFT JOIN placed in WHERE turns it into an inner join, with no error.
  5. This order is what the query means. The optimiser may do anything that produces the same answer.
  6. DISTINCT applies to the projected row. Adding a unique column to the select list disables it.
  7. Reaching for DISTINCT to remove duplicates usually means the join is wrong.

Interview questions this chapter answers

Why can't I use a column alias in the WHERE clause?

Because WHERE is evaluated before SELECT, and the alias is created by SELECT. ORDER BY runs after, which is why the alias works there. Repeat the expression, or wrap the query in a derived table or CTE.

What is the difference between WHERE and HAVING?

WHERE filters rows before grouping, HAVING filters groups after. Beyond correctness there is a performance consequence: a WHERE predicate can use an index and reduces the rows the aggregate has to process, so a condition that could live in either should live in WHERE.

My LEFT JOIN is returning fewer rows than the left table. Why?

There is a condition on the right-hand table in WHERE rather than ON. Unmatched rows have nulls there, the predicate evaluates to UNKNOWN, and they are filtered out — so the join behaves as an inner join. Move the matching condition into ON.
