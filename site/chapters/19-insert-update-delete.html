INSERT, UPDATE, DELETE and RETURNING

Bulk loading, UPDATE … FROM, the WHERE clause you forgot, and getting the changed rows back.

From the advert

“Ottima conoscenza del linguaggio SQL” — the read half of SQL is where you spend your time; the write half is where you can do real damage.

The habit that will save your career

🧒 Simple

Before you rub something out, first draw a circle round exactly what you are about to rub out, and count it. If the circle contains more than you expected, you have just saved yourself.

🎓 Professional

Write the SELECT first, read the count, then convert it into the UPDATE or DELETE — inside an explicit transaction, checking the affected row count against the number you just read before committing. It costs fifteen seconds. The alternative costs a restore.

⚠ Trap — autocommit

Most clients run in autocommit: every statement commits as it finishes, so BEGIN is not implied and there is nothing to roll back. SSMS, psql and DBeaver all default this way. Know which mode your tool is in before you run a delete, not after — and prefer a tool where the transaction state is visible on screen.

You almost always want to know what a write did — the generated id, the previous value, the rows affected. Three dialects, three spellings, one idea:

✔ Why this matters more than it looks

RETURNING makes “write then read what I wrote” one round trip and one atomic step. The alternative — insert, then SELECT last_insert_id(), then select the row — is three round trips and has a race in the middle in any connection-pooled application. It is also the clean way to implement an optimistic-concurrency check: the row count is the answer.

UPDATE from another table

⚠ Trap — the non-deterministic UPDATE ... FROM

In SQL Server, if the joined source produces more than one row per target row, the update does not fail — it silently applies one arbitrary match and discards the rest. PostgreSQL behaves the same way with UPDATE … FROM. The same statement can produce a different result on the next run. Always make sure the source is aggregated or otherwise unique on the join key, and if you are not sure, prove it with a GROUP BY … HAVING COUNT(*) > 1 first.

🎓 Why one-row-at-a-time is so much slower

Each statement in autocommit is its own transaction, so each one waits for a log flush to disk. That is the durability guarantee being paid for, ten thousand times. Wrapping ten thousand inserts in one transaction turns ten thousand flushes into one and is routinely 50–100× faster — with no loss of safety, because the whole batch is still atomic. This is the single most useful performance fact about writing data.

The detail interviewers listen for

TRUNCATE is DDL, not DML, in most engines — which is why it fires no triggers, takes a schema-level lock, cannot be filtered, and in MySQL and Oracle causes an implicit commit that ends your transaction whether you wanted it to or not. Saying “it is DDL” explains all five differences at once.

  1. Write the SELECT first, read the count, then convert it to the write.
  2. Wrap destructive statements in an explicit transaction and check the affected row count before committing.
  3. Know whether your client is in autocommit before you run a delete, not after.
  4. RETURNING / OUTPUT makes “write then read” one atomic round trip and removes a race.
  5. UPDATE … FROM with a non-unique source silently applies one arbitrary match. Aggregate the source.
  6. Ten thousand inserts in one transaction is one log flush instead of ten thousand — routinely 50–100× faster.
  7. TRUNCATE is DDL: no triggers, no filtering, and an implicit commit in MySQL and Oracle.
  8. A DELETE from a parent with unindexed foreign keys on children will scan every child table.

Interview questions this chapter answers

Difference between DELETE and TRUNCATE?

DELETE is DML: it logs each row, fires triggers, can be filtered and rolled back. TRUNCATE is DDL in most engines: it deallocates pages, is far faster, fires no triggers, cannot have a WHERE, usually resets the identity, and in MySQL and Oracle commits your transaction implicitly.

How would you insert a million rows?

The engine's bulk path — COPY, BULK INSERT, LOAD DATA — or batched multi-row inserts inside one transaction. The cost of row-at-a-time is one log flush per statement; batching turns that into one flush per batch without losing atomicity. I would also consider dropping and rebuilding non-clustered indexes around a very large load.

How do you get the id of a row you just inserted?

RETURNING id (PostgreSQL, SQLite, MariaDB) or OUTPUT inserted.id (SQL Server) — one round trip, no race. The last_insert_id()-style functions are connection-scoped and become fragile with triggers or connection pooling.
