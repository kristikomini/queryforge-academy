Strings, dates, times and time zones

Date arithmetic that survives DST, why storing local time is a bug, and collation as a correctness problem.

From the advert

“Ottima conoscenza del linguaggio SQL” — and specifically the parts of it that are not standard at all. Dates are where dialects diverge most and where bugs hide longest.

Never wrap the column

This is chapter 07 again, and it is worth repeating because date filtering is where it happens most: 

WHERE YEAR(placed_at) = 2026                              -- scan
WHERE CAST(placed_at AS DATE) = '2026-03-14'              -- scan
WHERE DATE_TRUNC('day', placed_at) = '2026-03-14'         -- scan

WHERE placed_at >= DATE '2026-03-14'
  AND placed_at <  DATE '2026-03-15'                      -- seek
✔ The half-open habit

>= start AND < next_start is correct for a date, a DATETIME, a DATETIME2(7) and whatever precision somebody changes the column to in 2029. BETWEEN is correct only for pure dates and loses the last day for everything else. Adopt half-open once and you never think about it again.

Time zones: the three-layer rule

🧒 Simple

“Half past two on the last Sunday in October” happens twice in Italy — the clocks go back and that hour is repeated. So if you only wrote down “02:30”, you cannot tell which of the two it was, and you never will be able to. Writing down the real moment instead — the one everyone in the world agrees on — costs nothing and can never be ambiguous.

🎓 Professional
  1. Store instants in UTC, or in a zone-aware type (timestamptz, DATETIMEOFFSET). Every event, log line, audit row.
  2. Store the zone separately when the local zone is part of the meaning — a meeting at 09:00 Europe/Rome, which stays 09:00 across a DST change. Store the local time and the IANA zone name, not the offset: offsets change, zones do not.
  3. Convert at the edge, when displaying. Never in the middle of a query you also want to be indexable.
⚠ Trap — “+02:00” is not a time zone

An offset is a snapshot; a zone is a rule with history. Rome is +01:00 in winter and +02:00 in summer, and the rules have changed before and will again — Italy has debated abolishing DST twice. Storing the offset makes future dates wrong the moment the rule changes. Store Europe/Rome. 

-- PostgreSQL: the conversion is a first-class operation.
SELECT placed_at AT TIME ZONE 'Europe/Rome' AS local_time FROM orders;

-- SQL Server 2016+:
SELECT placed_at AT TIME ZONE 'UTC' AT TIME ZONE 'W. Europe Standard Time' FROM orders;
--     ^ tell it what the stored value IS, then what you want.
--     Note the Windows zone names differ from the IANA ones. Of course they do.

⚠ Trap — DATEDIFF counts boundaries, not elapsed time

DATEDIFF(day, '2026-03-14 23:59', '2026-03-15 00:01') is 1, even though two minutes passed. It counts how many day boundaries were crossed. That makes “orders older than 30 days” subtly wrong at the edges. If you mean elapsed time, subtract and compare to an interval.

Strings: the functions and the two real traps

-- Portable-ish
UPPER(s) LOWER(s) LENGTH(s) TRIM(s) REPLACE(s, a, b)
SUBSTRING(s FROM 2 FOR 5)          -- standard; SUBSTR / SUBSTRING(s, 2, 5) elsewhere
s || t                             -- standard concat; SQL Server uses +, MySQL CONCAT()
POSITION('x' IN s)                 -- CHARINDEX in T-SQL, INSTR in Oracle/MySQL
⚠ Trap 1 — LEN vs DATALENGTH

T-SQL's LEN() ignores trailing spaces; DATALENGTH() returns bytes (so double for NVARCHAR). Validating an IBAN or a VAT number with LEN() silently accepts trailing whitespace. Standard CHAR_LENGTH() does not have this behaviour.

⚠ Trap 2 — collation decides equality

Under a case-insensitive collation 'Rossi' = 'rossi' is true, so a UNIQUE constraint rejects the second one and a GROUP BY merges them. Under a case-sensitive one, both are separate. This is not a display setting — it changes which rows come back. And joining columns with different collations forces an implicit conversion that kills the index (chapter 07). Decide once, at database creation. 

-- Normalising a messy imported column, the pattern you will use constantly:
SELECT
  NULLIF(TRIM(LOWER(email)), '')                      AS email_norm,
  REPLACE(REPLACE(TRIM(vat_number), ' ', ''), '.', '') AS vat_norm
FROM staging_customers;
-- Then dedupe on email_norm, not on email. See chapter 15.

The calendar table

🎓 A table nobody teaches and every reporting system needs

A dim_date table with one row per day and columns for month, quarter, ISO week, day name, whether it is a working day and whether it is an Italian public holiday. It turns “sales per working day” and “fill in the days with no orders” from awkward date arithmetic into an ordinary join, it is trivially indexable, and it is the only sane place to encode the fact that Ferragosto exists. Every mature warehouse has one; suggesting it in an interview signals reporting experience.

  1. Never wrap a date column in a function to filter it. Half-open ranges instead.
  2. BETWEEN on a timestamp loses the last day.
  3. Store instants in UTC or a zone-aware type; convert at the edge.
  4. Store a zone name (Europe/Rome), never an offset. Offsets are snapshots of a rule that changes.
  5. Local time is ambiguous for one hour every autumn, permanently and unrecoverably.
  6. DATEDIFF counts boundaries crossed, not elapsed time.
  7. T-SQL LEN() ignores trailing spaces; use DATALENGTH or CHAR_LENGTH when it matters.
  8. Collation decides equality, grouping and uniqueness — not just sort order.
  9. Build a calendar table. Working days and holidays are data, not arithmetic.

Interview questions this chapter answers

How would you store a timestamp for a multi-country application?

Instants in UTC or a zone-aware column, and if the local wall-clock time is part of the meaning — a scheduled appointment — the local time plus the IANA zone name, not the offset. Conversion happens on display. Local-only storage is ambiguous for one hour each autumn and cannot be repaired later.

Get all orders from March 2026.

WHERE placed_at >= '2026-03-01' AND placed_at < '2026-04-01'. Half-open, so it is correct at any precision and can seek an index — unlike MONTH(placed_at) = 3, which scans.

Two queries compare the same strings and give different results. Why?

Different collations — on the columns, the database, or introduced by a cast. A case- or accent-insensitive collation makes 'Perù' = 'Peru' true. It also affects GROUP BY, UNIQUE and index seekability across a join.
