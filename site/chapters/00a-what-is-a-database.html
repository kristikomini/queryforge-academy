What a database actually is

Why not a spreadsheet, what the engine does for you, and the words everyone else will assume you know.

No advert asked for this

Every advert assumes it. This chapter and the nine after it exist because the rest of the course was written for somebody who already knew what a SELECT was — and a course that begins there is a course for people who do not need it. If you can already say what a database gives you that a spreadsheet does not, skip to chapter 0D.

A database is a program that answers questions about data

🧒 Simple

Imagine a very large filing cabinet with a very fast, very literal assistant standing in front of it. You never open the drawers yourself. You write your request on a slip of paper — “every order from Modena in March, sorted by value” — and the assistant comes back with exactly those pages, in that order, usually before you have finished putting your pen down. The cabinet is the data. The assistant is the database engine. The language on the slip of paper is SQL.

🎓 Professional

A relational database management system is a server process that owns a set of files on disk and mediates every access to them. It accepts declarative statements — you describe the result you want, not the steps to produce it — compiles each one into an execution plan, and runs that plan while guaranteeing four properties concurrent readers and writers could not otherwise have: atomicity, consistency, isolation and durability. The declarative gap is the entire point: you say what, and the engine decides how, which is why the same statement can get faster next year without being rewritten.

Why not a spreadsheet

This is the honest comparison, because a spreadsheet is what most people have actually used. A spreadsheet is excellent, and it fails at exactly five things — each of which is a whole feature of a database.

The problemIn a spreadsheetIn a database
Two people at once One person's save overwrites the other's. Or the file is locked and the second person waits. Thousands of concurrent readers and writers, with rules about who sees what and when (chapter 22).
Half-finished work The laptop dies between two edits. The file now says the money left one account and never arrived at the other. A transaction: both changes happen or neither does, even if the power fails mid-write (chapter 21).
Rules that cannot be broken A validation rule you can paste over, and a colleague who types “n/a” into a date column. Constraints: the engine refuses the write. Not warns — refuses (chapter 04).
Size A million rows and it is unusable. Ten million and it will not open. Hundreds of millions of rows, answering in milliseconds, because of indexes (chapter 25).
Being asked a new question Somebody rebuilds the pivot table by hand, and gets a slightly different number than last month. One query, written once, that gives the same answer every time and can be read and checked by anyone.
⚠ The point is not that spreadsheets are bad

They are the right tool for a one-off analysis by one person. The moment two people need the same numbers, or the numbers must still be correct after a crash, or a rule must hold for every row forever — those are the moments a database earns its complexity. Knowing which situation you are in is a real skill, and “this could stay a spreadsheet” is sometimes the senior answer.

The five words the rest of the course assumes

You will meet these on every page from here on. They are worth getting exactly right once.

WordWhat it meansIn this course
Engine (or DBMS) The program that stores the data and answers queries. SQL Server, PostgreSQL, MySQL, Oracle, SQLite. The playground runs a real one — SQLite — inside your browser.
Database One named collection of tables, owned by an engine. An engine can hold many. The reference database is called forge: an order-fulfilment system.
Table One kind of thing, stored as rows and columns. customers, orders. Chapter 0C, in full.
SQL The language you ask questions in. Pronounced “ess-cue-ell” or “sequel”; nobody minds. Standardised, and every engine deviates. Chapter 44 is the differences.
Query One statement you send to the engine. Strictly, a question; loosely, any statement. Chapter 0D writes your first one.

What a query looks like, before you can write one

You are not expected to understand this yet. Read it the way you would read a sentence in a language you are starting to learn: notice the shape, notice that it is almost English, and notice that every single line has a comment explaining it. Every code example in this course is annotated that way, and each one has a syntax anatomy underneath it that explains every keyword it uses.

Which engine should you learn?

The one your target employer runs. In the Italian market that is most often SQL Server, then Oracle in larger and older estates, with PostgreSQL and MySQL common in newer product teams. The good news is that the differences are perhaps 15% of what you write, and the 85% underneath is the same everywhere.

✔ What this course does about that

It writes standard SQL by default, flags dialect-specific spellings inline where they matter, and uses SQLite in the playground because it needs no installation and runs in a browser tab. Where SQLite cannot demonstrate something — locking, isolation levels, real execution plans — the chapter says so and gives you the one-line Docker command for an engine that can.

Who does what, in a real team

The titles overlap and every company draws the lines differently, but the distinction worth knowing at interview is this one:

  • Database developer — designs schemas, writes queries and stored procedures, tunes the slow ones. Lives inside the data. This is the job this course is built backwards from.
  • DBA (database administrator) — installs, patches, backs up, restores, monitors, manages security and capacity. Lives around the data.
  • Data engineer — moves data between systems, builds pipelines and warehouses. Chapter 40.
  • Analyst — asks the questions and turns answers into decisions. Often writes more SQL per day than anybody else in the building.

In a small Italian software house one person may be all four before lunch. Saying which of them you want to be, and why, is a better interview answer than claiming to be all of them.

  1. A database engine is a program that owns the data files and mediates every access to them; you never read the files yourself.
  2. SQL is declarative: you describe the result you want and the engine decides how to produce it.
  3. A database earns its complexity when there are concurrent users, work that must not be half-applied, rules that must always hold, or more data than fits in memory.
  4. The vocabulary is engine, database, table, SQL, query — and everything later in the course is written in those words.
  5. Dialects differ in perhaps 15% of what you write; the relational core underneath is the same everywhere.

What is a database, in one sentence?

A server program that owns a set of data files and answers declarative questions about them, while guaranteeing that concurrent readers and writers cannot corrupt each other's work.

Why not just use Excel?

Because of four things Excel cannot do: many people writing at once, work that must be all-or-nothing, rules the file cannot be edited around, and datasets that will not fit in memory. For a one-off analysis by one person, Excel is often the correct answer — and saying that is a stronger response than reciting a list of database features.

What does “declarative” mean, and why does it matter?

You state the result you want rather than the algorithm to compute it. It matters because the engine is then free to choose a different, faster plan when the data grows or an index is added — without anybody rewriting the query.
