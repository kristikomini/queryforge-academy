DDL and constraints: the database defends itself

PRIMARY KEY, FOREIGN KEY, UNIQUE, CHECK, NOT NULL, DEFAULT — the cheapest bugs you will ever prevent.

From the advert

“Progettazione e modellazione di basi dati relazionali” — “modelling” in practice means writing constraints. A model that is only a diagram enforces nothing.

Constraints are the cheapest tests you will ever write

🧒 Simple

Think of a form with boxes that will not let you write in them wrongly. The date box only accepts dates. The “how many” box refuses negative numbers. You cannot post the form without filling in your name. The form is not being annoying — it is making it impossible to send back something nobody can use.

🎓 Professional

A constraint is an invariant enforced by the engine, so it holds regardless of which application, script, ETL job, migration or DBA-at-2am is writing. Application-level validation is the same rule written in a place that can be bypassed — and over a system's life it will be bypassed: by the import job, by the hotfix, by the second application nobody told you about. The constraint is also the only version that is true for the data that is already there.

The six constraints, and what each one is for

ConstraintPreventsCost
NOT NULLUnknown where unknown is not a valid stateFree
PRIMARY KEYDuplicate or unidentifiable rowsCreates an index; usually decides physical order
UNIQUETwo customers with one VAT numberCreates an index; a write must check it
FOREIGN KEYAn order line pointing at an order that never existedA lookup per write; index the child column yourself
CHECKNegative quantities, a ship date before the order dateAn expression per write. Usually negligible
DEFAULTEvery caller having to remember created_atFree
⚠ Trap — the one that costs real money

A foreign key does not create an index on the child column. The parent side is indexed because it is a key; the child side is not, in any major engine except MySQL, which creates one silently. So DELETE FROM orders WHERE id = ? has to scan the whole of order_lines to check nothing references it — and it holds locks while it does. This is one of the most common causes of mysterious delete-and-blocking incidents in the field. Index every foreign key column. 

CREATE TABLE orders (
  id           INTEGER PRIMARY KEY,
  customer_id  INTEGER NOT NULL REFERENCES customers(id),
  status       VARCHAR(12) NOT NULL DEFAULT 'draft',
  placed_at    TIMESTAMP   NOT NULL DEFAULT CURRENT_TIMESTAMP,
  shipped_at   TIMESTAMP   NULL,
  total_cents  BIGINT      NOT NULL DEFAULT 0,

  -- The state machine, enforced where it cannot be bypassed.
  CONSTRAINT ck_orders_status CHECK (status IN
    ('draft','submitted','confirmed','shipped','delivered','cancelled')),
  -- A total can be zero but never negative.
  CONSTRAINT ck_orders_total CHECK (total_cents >= 0),
  -- Shipped implies a ship date, and it cannot precede the order.
  CONSTRAINT ck_orders_shipped CHECK (
    (status <> 'shipped' AND status <> 'delivered')
    OR (shipped_at IS NOT NULL AND shipped_at >= placed_at))
);

-- The index the foreign key did NOT create for you:
CREATE INDEX ix_orders_customer ON orders (customer_id);

ON DELETE: the four options and when each is right

ActionBehaviourRight for
NO ACTION / RESTRICTRefuse the deleteThe default you should want. Anything financial or legal
CASCADEDelete the children tooGenuine ownership: an order and its lines, a user and their sessions
SET NULLOrphan the childrenAn optional link — a task whose assignee left
SET DEFAULTPoint them at a fallback rowRare. A “deleted user” placeholder
🎓 Cascade is a loaded weapon

ON DELETE CASCADE means one statement can silently remove rows from tables that are not named in it, through chains several levels deep, with no row count that reflects the damage. Use it where the child genuinely has no independent existence, and nowhere else. For business records the honest pattern is usually soft delete — a deleted_at column and a filtered index — because “delete the customer” almost never really means “destroy seven years of invoices”, and a tax authority may disagree with you about whether it did.

Name your constraints

An unnamed constraint gets a generated name like CK__orders__7A672E12. That name is different in every environment, so a migration that drops it cannot be written portably, and an error message that mentions it tells the support engineer nothing. 

-- Not this:
ALTER TABLE orders ADD CHECK (total_cents >= 0);

-- This. The error message now reads "ck_orders_total_nonneg", which is a sentence.
ALTER TABLE orders ADD CONSTRAINT ck_orders_total_nonneg CHECK (total_cents >= 0);

A convention that survives contact with a real team: pk_, fk_<child>_<parent>, uq_<table>_<cols>, ck_<table>_<rule>, ix_<table>_<cols>.

Constraints the optimiser can use

🎓 A constraint is information, not just a rule

The optimiser reads your constraints. A CHECK (status IN (...)) lets it discard a branch querying for a status that cannot exist. A NOT NULL lets it skip null handling. A UNIQUE tells it a join cannot multiply rows, which changes the join algorithm it picks. In SQL Server a constraint added WITH NOCHECK is marked untrusted and stops being used for any of this — a genuinely obscure fact that shows up as a plan regression after someone bulk-loads data. Add constraints WITH CHECK and verify with sys.check_constraints.is_not_trusted.

  1. A constraint is an invariant that holds no matter who is writing. Application validation is the same rule in a bypassable place.
  2. Foreign keys do not index the child column. Index it yourself, or deletes on the parent will scan the child.
  3. Default to RESTRICT; use CASCADE only where the child cannot exist alone.
  4. For business records, prefer soft delete to cascade. “Delete the customer” rarely means “destroy the invoices”.
  5. Name every constraint. The generated name differs per environment and tells nobody anything.
  6. CHECK is the cheapest place to put a business rule that must never be false.
  7. Constraints are information the optimiser uses. An untrusted constraint enforces the rule but stops helping the plan.
  8. Write NOT NULL unless there is a genuine business state that is unknown.

Interview questions this chapter answers

Should business rules live in the database or the application?

Invariants — things that must never be false about the data — belong in the database, because it is the only layer every writer passes through. Policy that changes with the business, involves external systems, or needs a human-readable error belongs in the application. “A quantity is never negative” is a constraint; “gold customers get free shipping over €50” is not.

A delete on the parent table is suddenly very slow. Why?

Almost always an unindexed foreign key on a child table: the engine has to scan the child to prove nothing references the row, and holds locks while it does. Find every FK column without a leading index on it and add one.

What does ON DELETE CASCADE do, and when would you avoid it?

It deletes referencing rows automatically, recursively. I avoid it for anything with legal or financial meaning, because a single statement can then destroy rows in tables it does not name and the row count gives no clue. Ownership relationships — an order and its lines — are where it is genuinely right.
