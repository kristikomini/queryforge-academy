Users, roles, least privilege and GDPR

GRANT and REVOKE, row-level security, encryption at rest vs in transit, and what GDPR asks of a schema.

From the advert

“Conoscenza dei principi di sicurezza dei dati e GDPR” — a table of Italian customers is a legal object as well as a technical one, and the schema is where several of the obligations actually land.

Least privilege, concretely

🧒 Simple

The person who waters the plants gets a key to the front door, not to the safe. Not because you distrust them — because if they lose the key, you have only lost the plants. 

-- Grant to ROLES, assign roles to users. Never grant to a person: people leave,
-- roles do not, and a role is a sentence about a job rather than about a name.
CREATE ROLE app_readwrite;
GRANT SELECT, INSERT, UPDATE ON orders, order_lines TO app_readwrite;
GRANT SELECT                  ON products, customers  TO app_readwrite;
-- Note what is absent: DELETE, DDL, and any access to the audit tables.

CREATE ROLE reporting_readonly;
GRANT SELECT ON v_orders_geo, v_order_totals TO reporting_readonly;
-- Views only. The analyst never sees a column the view does not expose.

GRANT app_readwrite TO svc_orders_api;
⚠ Trap — the application logs in as the owner

The commonest real-world finding. The connection string uses sa, postgres, or the schema owner, so an injection flaw anywhere becomes total compromise, a bug can drop a table, and every audit trail says the same username. Separate accounts for migrations (DDL), the application (DML on its own tables) and reporting (SELECT on views) costs one afternoon and changes the blast radius of every other mistake.

Row-level security

Multi-tenant systems usually filter by tenant in application code — which works until one query forgets. RLS moves the rule into the database, where it cannot be forgotten: 

-- PostgreSQL
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.tenant_id')::int);
-- Every query against orders now silently carries that predicate.
-- The application sets: SET LOCAL app.tenant_id = '42';

-- SQL Server: an inline table-valued function plus a security policy.
CREATE SECURITY POLICY TenantFilter
  ADD FILTER PREDICATE dbo.fn_tenant_predicate(tenant_id) ON dbo.orders;
Two things to know about it
  1. The predicate is added to every query, so it must be indexable — a policy calling a slow function turns every query into that function's cost.
  2. It does not apply to the table owner or to superusers unless you say so (FORCE ROW LEVEL SECURITY), which is exactly the case where people believe they have tested it and have not.

Encryption: three different things

KindProtects againstDoes NOT protect against
In transit (TLS)Network interceptionAnything at either end
At rest (TDE, filesystem)A stolen disk or backup fileAny authenticated query. The engine decrypts transparently
Column-level / application-levelA DBA or an attacker reading the tableBeing searchable, sortable or joinable — you gave that up
⚠ Trap — "the database is encrypted" answers almost nothing

Transparent Data Encryption protects the files. It does not protect against a compromised application account, an injection flaw, or a curious DBA — because for anyone holding a valid connection, the data is simply there. It is genuinely valuable for lost backups and decommissioned disks, and it is not a defence against the threat most people are imagining when they say it. Being precise about that separates a real answer from a compliance checkbox.

What GDPR actually asks of a schema

🎓 The obligations that land on the database designer
  • Data minimisation (Art. 5). Do not store a personal data field you have no purpose for. A column that exists because "we might want it" is a liability with storage costs. This site's own accounts service stores no email address for exactly this reason, and says so.
  • Erasure (Art. 17). You must be able to delete a person's data on request. That is a schema question: can you find everything about one person? Foreign keys and a documented data map are what make the answer yes.
  • Portability (Art. 20). Export it in a machine-readable form — which is a query you should have written before somebody asks for it.
  • Storage limitation (Art. 5). A retention policy, implemented as a scheduled job, not as an intention.
  • Records and access control (Art. 30, 32). Who accessed personal data, and when. That is an audit trail — and see chapter 33 on why a trigger is the honest place for it.
✔ The tension worth naming out loud

Erasure conflicts with immutable accounting records. You cannot delete an invoice; Italian tax law requires it be kept for ten years, and Article 17 has an explicit exemption for legal obligations. The usual resolution is pseudonymisation: delete or hash the identifying columns, keep the transaction with a non-identifying key. Knowing that the two requirements collide, and that the answer is pseudonymisation rather than "delete everything" or "keep everything", is precisely the kind of thing that distinguishes someone who has done this from someone who has read about it. 

-- Pseudonymisation in practice: the person disappears, the accounting does not.
UPDATE customers
SET name        = 'ERASED',
    email       = 'erased+' || id || '@invalid',   -- keeps the unique constraint valid
    vat_number  = NULL,
    erased_at   = now()
WHERE id = :id;
-- orders, order_lines and payments are untouched: they reference customer_id,
-- which is now a meaningless surrogate. Which is what a surrogate key is for.

Masking, and what it is worth

-- SQL Server dynamic data masking: non-privileged users see a masked value.
ALTER TABLE customers ALTER COLUMN email
  ADD MASKED WITH (FUNCTION = 'email()');
-- 'mario.rossi@esempio.it'  ->  'mXXX@XXXX.com'
⚠ Masking is a display feature, not a security boundary

Microsoft's own documentation says so. A user who can query the column can infer it: WHERE email LIKE 'a%' still filters on the real value, so a few dozen queries recover it. It is useful for keeping production data off a support screen. It is not a substitute for not granting access.

  1. Grant to roles, not people. Roles outlive employees and describe a job.
  2. Separate accounts for migrations, the application and reporting. It changes the blast radius of every other mistake.
  3. An application connecting as the owner turns any injection flaw into total compromise.
  4. Row-level security moves a tenant filter into the database, where it cannot be forgotten — and its predicate must be indexable.
  5. Encryption at rest protects stolen disks and backups, not authenticated queries.
  6. Column-level encryption costs you searching, sorting and joining on that column.
  7. Data minimisation is a schema decision: a column with no purpose is a liability.
  8. Erasure requires knowing where a person's data is. That is a data map plus foreign keys.
  9. Erasure and accounting retention conflict; pseudonymisation is the standard resolution.
  10. Dynamic data masking is a display feature and can be inferred around.

Interview questions this chapter answers

How would you secure a database for an application?

Separate accounts by purpose — migrations get DDL, the application gets DML on its own tables and nothing else, reporting gets SELECT on views. Grants go to roles, not users. TLS in transit and encryption at rest for the backups. Then verify what the application account can actually do, because the finding is almost always that it is the owner.

A customer asks to be forgotten, but their invoices must be kept ten years. What do you do?

Pseudonymise rather than delete: clear or hash the identifying columns on the customer record and keep the transactions, which reference a surrogate key that no longer identifies anyone. GDPR Article 17 has an explicit exemption for legal obligations, so the two requirements are reconcilable — but only if the schema separates identity from transaction.

Is encryption at rest enough?

It protects a stolen disk or backup file. It does nothing against a compromised application account or an injection flaw, because the engine decrypts transparently for anyone with a valid connection. It is worth having and it answers a narrower question than people usually mean.
