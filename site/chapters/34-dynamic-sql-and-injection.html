Dynamic SQL and SQL injection

How injection actually works, why parameters are not string escaping, and safe dynamic SQL when you must.

From the advert

“Conoscenza dei principi di sicurezza dei dati e GDPR” — injection is the oldest vulnerability on the OWASP list and it is still in the top three, because the mistake is so easy to make and so invisible once made.

How injection actually works

🧒 Simple

You dictate a letter to somebody and say “write: Dear Mr Rossi”. If they write exactly that, fine. But if halfway through you say “…and now stop writing and go and burn the filing cabinet”, and they do it — that is the bug. They could not tell your instructions apart from the words you wanted written down. 

-- The vulnerable pattern, in any language:
sql = "SELECT * FROM users WHERE email = '" + input + "'"

-- input:  x' OR '1'='1
-- becomes: SELECT * FROM users WHERE email = 'x' OR '1'='1'    ← every row

-- input:  x'; DROP TABLE users; --
-- becomes: SELECT * FROM users WHERE email = 'x'; DROP TABLE users; --'
🎓 The root cause, stated precisely

Data and code are travelling in the same channel. The parser cannot tell which characters were meant as a value and which as syntax, because by the time it sees them they are one string. Every mitigation is really an attempt to separate the two channels again — and only one of them separates them properly.

Parameters are not escaping

✔ The distinction that answers the question properly

Escaping tries to neutralise dangerous characters in a string that is still going to be concatenated. It is a blacklist, and blacklists lose — to multi-byte character-set tricks, to a missed quote style, to a context you did not anticipate. Parameterisation sends the query and the values separately: the statement is parsed and planned first, and the values are bound to placeholders afterwards, as values, never re-parsed. There is nothing to escape because nothing is ever concatenated. Saying “parameters are a different channel, not better escaping” is the answer that lands. 

-- Correct, everywhere:
SELECT * FROM users WHERE email = ?      -- or $1, @email, :email
-- The driver sends the SQL and the values in separate protocol fields.

-- And it is FASTER: the same statement text means the same cached plan, instead
-- of a new plan for every distinct literal filling the cache.
⚠ Trap — an ORM does not make you safe

Every ORM has a raw-SQL escape hatch, and every ORM codebase uses it. String interpolation inside db.raw(...), EntityManager.createNativeQuery("... " + x) or an f-string in a Django .extra() is injectable exactly as before. Grep for string concatenation near the word SELECT — that, not the framework's name, is the audit.

The thing parameters cannot do

A parameter can be a value. It can never be a table name, a column name, a sort direction or a keyword — because those change the shape of the statement, which must be fixed before parsing. So this does not work: 

ORDER BY ?          -- binds a STRING; it sorts by a constant, silently doing nothing
SELECT * FROM ?     -- syntax error
🎓 So how do you build a sortable, filterable report?

Allow-list. Map user input to a fixed set of known-good identifiers in code, and if it is not in the map, reject the request. Never sanitise the input — choose from a list you wrote. 

// The only correct shape. Note there is no escaping anywhere.
const SORTABLE = { date: "o.placed_at", total: "o.total_cents", customer: "c.name" };
const col = SORTABLE[req.query.sort];
if (!col) return badRequest("unknown sort column");
const dir = req.query.dir === "asc" ? "ASC" : "DESC";     // also an allow-list

const sql = `SELECT ... ORDER BY ${col} ${dir} LIMIT ?`;  // identifiers from the map
db.query(sql, [pageSize]);                                // VALUES still parameterised

Safe dynamic SQL inside the database

-- SQL Server: sp_executesql takes parameters. EXEC(@sql) does not — that is the
-- entire difference, and it is why one is safe and the other is not.
DECLARE @sql NVARCHAR(MAX) = N'
  SELECT id, total_cents FROM orders
  WHERE customer_id = @cid AND placed_at >= @from';

IF @status IS NOT NULL
  SET @sql += N' AND status = @status';   -- SHAPE varies; VALUES never concatenated

EXEC sp_executesql @sql,
     N'@cid INT, @from DATE, @status VARCHAR(12)',
     @cid = @customer_id, @from = @from_date, @status = @status;

-- If an IDENTIFIER genuinely must be dynamic, quote it with the engine's own
-- quoting function — never with your own string manipulation:
SET @sql = N'SELECT * FROM ' + QUOTENAME(@table_name);   -- SQL Server
-- PostgreSQL: format('SELECT * FROM %I', tbl)   -- %I quotes an identifier
-- and %L quotes a literal, for the rare case that is genuinely needed.
This is also the fix for the optional-parameter plan problem

WHERE (@p IS NULL OR col = @p) caches one plan for every combination of supplied parameters (chapter 07). Building the statement so it contains only the clauses actually needed produces a different statement text per shape, and therefore a correctly-tailored cached plan for each — while the values remain parameters. Safe dynamic SQL is a performance technique as much as it is a hazard.

⚠ Second-order injection

A malicious string is stored safely via a parameterised insert. Later, a report builds a query by concatenating that stored value — and it executes. The input was never "untrusted" at the moment it mattered, because it came from your own database. The lesson: the rule is not "validate user input", it is never concatenate a value into SQL, whatever its origin.

  1. Injection happens because data and code share one channel. Parameters give them two.
  2. Parameterisation is not better escaping. Escaping is a blacklist; parameters are never parsed as syntax.
  3. Parameterised queries are also faster: one cached plan instead of one per literal.
  4. An ORM is not a defence. Its raw-SQL escape hatch is injectable like anything else.
  5. A parameter can be a value, never an identifier, a keyword or a sort direction.
  6. For dynamic identifiers, use an allow-list in code — choose from a map, do not sanitise input.
  7. Inside the database, sp_executesql takes parameters and EXEC(@sql) does not.
  8. Safe dynamic SQL is also the fix for the optional-parameter plan problem.
  9. Second-order injection comes from your own tables. The rule is never to concatenate a value, whatever its origin.

Interview questions this chapter answers

What is SQL injection and how do you prevent it?

User input is concatenated into a statement, so the parser reads it as syntax rather than as a value. The fix is parameterised queries — the SQL and the values travel in separate protocol fields, so nothing is ever re-parsed. Not escaping, which is a blacklist. Then least privilege to limit the blast radius if something else goes wrong.

How do you handle a user-supplied ORDER BY column?

An allow-list. Map the input to a fixed set of known identifiers in code and reject anything not in the map, because a parameter cannot be an identifier — bind it and you sort by a constant, silently. The sort direction gets the same treatment.

Are stored procedures immune to injection?

No. A procedure that builds a string and runs EXEC(@sql) is exactly as vulnerable. What procedures give you is a permission boundary — the application account can be granted EXECUTE and nothing else — which limits damage rather than preventing the flaw.
