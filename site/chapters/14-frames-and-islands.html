Frames, running totals, gaps and islands

ROWS and RANGE are not the same thing. Plus LAG/LEAD and the classic interview problem, solved three ways.

No advert asked for this

No advert names it, but “find the consecutive runs” and “running balance” appear in most technical screens.

The frame: the part everyone skips

🧒 Simple

Line the rows up in order. The frame is how far you can see from where you are standing: everything behind you, or three rows either side, or the whole line. Change how far you can see and the same question gives a different answer.

🎓 Professional

Inside OVER (…), after PARTITION BY and ORDER BY, comes the frame: which rows of the ordered partition the function actually sees.

  • No ORDER BY → the frame is the whole partition. That is why SUM(x) OVER (PARTITION BY c) is a partition total.
  • With ORDER BY and no explicit frame → the default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. That gives a running total — which is why adding an ORDER BY silently changes a total into a running total, the most surprising behaviour in the whole feature.

ROWS and RANGE are not the same thing

⚠ Trap — the default is the slow, surprising one

ROWS counts physical rows. RANGE counts peer rows — every row with the same ORDER BY value is included together.

So with three orders on the same day, RANGE … CURRENT ROW includes all three in every one of their running totals; ROWS … CURRENT ROW includes one, two, three respectively. If your running total "jumps" on days with several rows, this is why. And RANGE is the default, and is generally slower. Write ROWS explicitly unless you specifically want peer semantics.

FrameMeans
ROWS UNBOUNDED PRECEDINGStart of partition → here. Running total
ROWS BETWEEN 6 PRECEDING AND CURRENT ROWA 7-row sliding window
ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWINGNeighbours either side. Smoothing
ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWINGHere → end. “How much is still to come”
RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROWA true time window, gaps and all

That last row is the one case where RANGE is clearly better than ROWS: “the last seven days” is not “the last seven rows” when some days have no data. PostgreSQL and Oracle support it; SQL Server does not.

LAG, LEAD and the value-at functions

⚠ Trap — LAST_VALUE almost never does what you expect

With the default frame, "the last value" is the current row, so LAST_VALUE(x) OVER (ORDER BY d) just returns x. You must extend the frame: LAST_VALUE(x) OVER (ORDER BY d ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING). In practice FIRST_VALUE over a reversed ORDER BY is easier to read and harder to get wrong.

Gaps and islands

🧒 Simple

You have a list of days somebody came to work: 1, 2, 3, 7, 8, 12. The islands are the runs of consecutive days — 1–3, 7–8, 12 — and the gaps are the holes between them. The trick to finding them is beautiful: subtract each day's position in the list from the day itself. Inside a run, that difference never changes.

🎓 The general version: a gap flag and a running sum

The subtraction trick only works for a fixed step. The portable technique — and the one to show in an interview — is to mark where a new group starts and then take a running sum of those marks. It works for sessions, status runs, anything.

  1. No ORDER BY in OVER means the frame is the whole partition — a total, not a running total.
  2. Adding ORDER BY silently changes the default frame to “start of partition → current row”.
  3. ROWS counts physical rows; RANGE includes all peers with the same ordering value.
  4. RANGE is the default and is usually not what you meant. Write ROWS.
  5. RANGE with an INTERVAL is the one place it wins: a true time window across missing days.
  6. LAST_VALUE needs an explicit frame to the end of the partition, or it returns the current row.
  7. Islands of consecutive integers: group by value − ROW_NUMBER().
  8. The general form: flag where a new group starts, then take a running SUM of the flag as the group id.

Interview questions this chapter answers

Difference between ROWS and RANGE?

ROWS counts physical rows; RANGE includes every peer row sharing the current row's ORDER BY value. With duplicate ordering values they give different answers, and RANGE — the default — is also usually slower.

Compute a running total.

SUM(amount) OVER (PARTITION BY account ORDER BY d ROWS UNBOUNDED PRECEDING). The explicit ROWS matters: with the default RANGE, several rows on the same date all get the same day-end total.

Find runs of consecutive days.

Gaps and islands. Number the rows in date order and group by date − row_number, which is constant inside a run. For irregular steps, flag each row where the gap from the previous exceeds the threshold and take a running sum of that flag as a group id.
