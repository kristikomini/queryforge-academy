Set operations and de-duplication

UNION vs UNION ALL is a performance decision, not a style one. Plus four ways to delete duplicate rows.

From the advert

“Ottima conoscenza del linguaggio SQL” — and one specific habit: writing UNION when you meant UNION ALL, which is a hidden sort on every row you return.

🧒 Simple

Two guest lists. UNION ALL staples them together, so anyone on both appears twice. UNION staples them and then goes through crossing out repeats — which means reading the whole thing. If you already know there are no repeats, making somebody check anyway is just wasted work.

🎓 Professional

UNION ALL is a concatenation: the engine streams one branch then the other, and can start returning rows immediately. UNION additionally requires duplicate elimination across the whole combined result, which means a sort or a hash — so it is blocking (nothing is returned until everything has been read), it needs memory, and it can spill to disk if the estimate was low. That is a difference in algorithm, not a flag, which is why the cost is so much larger than the syntax suggests.

⚠ Trap

UNION is the default habit and it is the wrong one. It forces a full deduplication of the combined result — a sort or hash over every row, which can spill to disk — and it does it even when the two branches cannot possibly overlap. Default to UNION ALL and use UNION only when you actually need duplicates removed. On a large result this is not a micro-optimisation; it is often the difference between two seconds and forty.

The rules

  • Both branches need the same number of columns, in the same order, with compatible types. Names come from the first branch.
  • ORDER BY applies to the whole result and goes once, at the end. To order inside a branch you need a derived table.
  • For these operators, and only these, two nulls are considered equal. That is the opposite of =, and it is why EXCEPT is such a good table-diff tool.

Four ways to delete duplicate rows

A staple of screening tests. Know at least two, and know which is portable.

1 · ROW_NUMBER — portable, and the one to give first

2 · MIN(id) per group — works on any engine, including ancient ones

3 · A physical row identifier — when there is no key at all

4 · Rebuild the table — for very large clean-ups

✔ Say this before you run any of them

“First I would run the SELECT to count what will go, then check whether a UNIQUE constraint should have prevented this in the first place — because otherwise I will be doing it again next month.” The second clause is the one that separates fixing a symptom from fixing a bug.

DISTINCT, and when it is a lie

SELECT DISTINCT deduplicates the projected row, so adding any unique column disables it entirely. More importantly, DISTINCT appearing in a query with joins is usually a symptom: the join is fanning out (chapter 08), and DISTINCT hides the duplicate rows while leaving every SUM and COUNT wrong.

  1. UNION deduplicates and therefore sorts or hashes the whole result. UNION ALL concatenates.
  2. Default to UNION ALL; reach for UNION only when duplicates must actually go.
  3. Branches must match in column count and order; names come from the first branch.
  4. One ORDER BY, at the end, applying to the whole result.
  5. Set operators treat two nulls as equal — the opposite of = — which makes EXCEPT an excellent table-diff.
  6. De-duplicate with ROW_NUMBER and an explicit tie-breaker; check the count first.
  7. After removing duplicates, add the UNIQUE constraint that should have stopped them.
  8. DISTINCT in a joined query usually means the join fans out. Fix the join.

Interview questions this chapter answers

UNION vs UNION ALL?

UNION removes duplicates and so has to sort or hash the entire combined result; UNION ALL just concatenates. It is a performance decision, not a style one, and ALL should be the default because most branches cannot overlap anyway.

Delete duplicate rows keeping the newest.

ROW_NUMBER() OVER (PARTITION BY <dup key> ORDER BY updated_at DESC, id DESC) in a CTE, then delete where rn > 1. The tie-breaker on id makes it deterministic. Then add the unique constraint that should have prevented it.

How would you find what differs between two tables?

EXCEPT in both directions. It compares whole rows, treats nulls as equal — so a null-to-null match does not show as a difference — and needs no join keys.
