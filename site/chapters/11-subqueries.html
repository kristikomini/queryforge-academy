Subqueries: EXISTS, IN and the correlated one

Three ways to ask the same question, one of which is a trap the moment a NULL appears.

From the advert

“Ottima conoscenza del linguaggio SQL” — knowing which of three equivalent forms to reach for, and which one has a null bug in it.

Four kinds of subquery

KindReturnsWhere it goes
ScalarExactly one row, one columnAnywhere a value goes: SELECT, WHERE
Row / columnOne column, many rowsIN, ANY, ALL
Derived tableA whole tableFROM. Must be aliased
CorrelatedDepends on the outer rowWHERE EXISTS, SELECT, LATERAL
🧒 Simple

A normal subquery is a question you answer once and write on a sticky note. A correlated subquery is a question you have to answer again for every single row — “for this customer, is there an order?” — so it is like looking something up once per line of a list rather than once for the whole list.

EXISTS, IN and JOIN: the same question, three ways

-- 1. Semi-join with EXISTS — no duplicates, stops at the first match.
SELECT c.* FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- 2. IN — equivalent HERE, and dangerous with NULLs in the negative form.
SELECT c.* FROM customers c
WHERE c.id IN (SELECT customer_id FROM orders);

-- 3. JOIN — DIFFERENT: a customer with 3 orders appears 3 times.
SELECT c.* FROM customers c
JOIN orders o ON o.customer_id = c.id;              -- needs DISTINCT to match the others
🎓 Which one, and the honest answer about performance
  • EXISTS is the default for “does a match exist?”. It is null-safe, cannot duplicate rows, and can short-circuit at the first match.
  • IN reads better with a literal list. With a subquery it is fine in the positive form and a landmine in the negative (chapter 09).
  • JOIN when you actually need columns from the other table.
“EXISTS is faster than IN” is folklore

Modern optimisers rewrite all three into the same internal semi-join and produce identical plans in the common cases. Saying “EXISTS is faster” in an interview is a small trap; saying “they usually plan identically, so I choose on semantics — and I avoid NOT IN because of nulls” is the answer that shows you have checked rather than repeated.

Correlated subqueries, and when they hurt

-- The most recent order date per customer, as a correlated scalar subquery.
SELECT c.name,
       (SELECT MAX(o.placed_at) FROM orders o WHERE o.customer_id = c.id) AS last_order
FROM customers c;

Logically that runs once per customer. In practice a good optimiser will often decorrelate it into a grouped join — but not always, and not when the subquery contains something it cannot transform (a scalar UDF, a TOP with a tie-break, an ORDER BY). When it cannot, you have written an N+1 inside the database.

⚠ Trap — the same subquery three times

This shape is extremely common and is three correlated executions per row:

SELECT c.name,
  (SELECT COUNT(*)         FROM orders o WHERE o.customer_id = c.id) AS n,
  (SELECT SUM(total_cents) FROM orders o WHERE o.customer_id = c.id) AS spend,
  (SELECT MAX(placed_at)   FROM orders o WHERE o.customer_id = c.id) AS last
FROM customers c;

Rewrite as one pre-aggregated join — one pass over orders instead of three per customer. This is a favourite “optimise this query” exercise in screening tests precisely because the fix is mechanical once you see it. 

SELECT c.name, COALESCE(o.n, 0) AS n, COALESCE(o.spend, 0) AS spend, o.last
FROM customers c
LEFT JOIN (
  SELECT customer_id, COUNT(*) AS n, SUM(total_cents) AS spend, MAX(placed_at) AS last
  FROM orders GROUP BY customer_id
) o ON o.customer_id = c.id;

LATERAL and APPLY: a join that can see the left row

🎓 The top-N-per-group tool

A normal derived table in FROM cannot reference columns from tables to its left. LATERAL (standard, PostgreSQL, Oracle 12c+, MySQL 8.0.14+) and CROSS APPLY / OUTER APPLY (SQL Server) lift that restriction. That makes “the three most recent orders for each customer” expressible directly — and it is often faster than the window-function version, because it can stop after three rows per customer instead of ranking all of them. 

-- PostgreSQL / MySQL 8 / Oracle
SELECT c.name, o.id, o.placed_at
FROM customers c
CROSS JOIN LATERAL (
  SELECT id, placed_at FROM orders
  WHERE customer_id = c.id                -- ← sees the outer row
  ORDER BY placed_at DESC LIMIT 3
) o;

-- SQL Server: CROSS APPLY, and OUTER APPLY to keep customers with no orders.
SELECT c.name, o.id, o.placed_at
FROM customers c
CROSS APPLY (SELECT TOP (3) id, placed_at FROM orders
             WHERE customer_id = c.id ORDER BY placed_at DESC) o;
CROSS vs OUTER

CROSS APPLY / CROSS JOIN LATERAL drops left rows whose subquery returned nothing — so customers with no orders disappear. OUTER APPLY / LEFT JOIN LATERAL … ON TRUE keeps them with nulls. Same relationship as inner and left joins, and the same bug when you pick the wrong one. 

-- Compare the two ways to get "the latest order per customer".
-- Window function: ranks everything, then filters.
SELECT * FROM (
  SELECT o.*, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY placed_at DESC) rn
  FROM orders o
) t WHERE rn = 1;

-- LATERAL: seeks the top row per customer. Usually faster when customers are few
-- and orders are many, and there is an index on (customer_id, placed_at DESC).
  1. A scalar subquery must return one row and one column, or it is a runtime error — not a null.
  2. EXISTS is the default for existence checks: null-safe, non-duplicating, short-circuiting.
  3. EXISTS, IN and a de-duplicated join usually produce the same plan. Choose on meaning, not on folklore.
  4. Never NOT IN over a nullable column. NOT EXISTS instead.
  5. Three correlated subqueries over the same table is three passes. Pre-aggregate and join once.
  6. A correlated subquery the optimiser cannot decorrelate is an N+1 inside the database.
  7. LATERAL / APPLY lets a derived table see the outer row — the natural top-N-per-group tool.
  8. CROSS APPLY drops rows with an empty subquery; OUTER APPLY keeps them.

Interview questions this chapter answers

Difference between EXISTS and IN?

Semantically, EXISTS asks whether any row matches and short-circuits; IN compares a value against a set. They plan the same way in most engines for the positive case. The real difference is negative: NOT IN returns nothing if the set contains a null, and NOT EXISTS does not.

Get the three most recent orders per customer.

Two good answers. ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY placed_at DESC) filtered to <= 3, which is portable; or CROSS APPLY/LATERAL with ORDER BY … LIMIT 3, which can stop early per customer and is usually faster with the right index.

This query has four correlated subqueries and is slow. What do you do?

Collapse them into one pre-aggregated derived table joined once. Four correlated subqueries over the same child table can mean four executions per outer row; one GROUP BY plus a join is a single pass.
