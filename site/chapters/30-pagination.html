Pagination that scales

OFFSET 100000 reads a hundred thousand rows in order to throw them away. Keyset pagination does not.

No advert asked for this

In no advert; in every application. Page 5 000 of a report is where OFFSET stops being acceptable.

Why OFFSET degrades

🧒 Simple

To read page 500 of a book with no page numbers, you count pages from the beginning. Every time. Page 1 is instant, page 500 takes five hundred times as long — and you throw away everything you counted. 

SELECT * FROM orders ORDER BY placed_at DESC
OFFSET 100000 ROWS FETCH NEXT 20 ROWS ONLY;   -- reads 100 020, returns 20
🎓 Professional

OFFSET n is not a seek. The engine must produce the first n rows in order and discard them, so the cost is O(offset + limit) and grows linearly with page number. Page 1 is free, page 5 000 is a table scan with extra steps. Worse, the cost is paid on every page, so a user paging through results makes it slower as they go — which is exactly the opposite of what they expect.

Keyset pagination

🧒 Simple

Instead of counting from the front, use a bookmark: “carry on from where I left off”. Turning to a bookmark costs the same whether it is page 2 or page 900. 

-- Page 1
SELECT id, placed_at, total_cents FROM orders
ORDER BY placed_at DESC, id DESC
LIMIT 20;

-- Every subsequent page: remember the LAST ROW of the page you just showed
-- (placed_at = :last_at, id = :last_id) and ask for what comes after it.
SELECT id, placed_at, total_cents FROM orders
WHERE (placed_at, id) < (:last_at, :last_id)     -- row-value comparison
ORDER BY placed_at DESC, id DESC
LIMIT 20;
🎓 Two things make this work
  1. The tie-breaker. placed_at alone is not unique, so two orders with the same timestamp would be skipped or repeated across the page boundary. Adding id makes the sort total, which is what makes the bookmark unambiguous.
  2. The row-value comparison. (a, b) < (x, y) is lexicographic and — crucially — sargable against an index on (a, b). Expanding it by hand into a < x OR (a = x AND b < y) is logically identical and typically not optimised into a single seek. PostgreSQL, MySQL and Oracle support the tuple form; SQL Server does not, so write the expanded form there and check the plan.
CREATE INDEX ix_orders_page ON orders (placed_at DESC, id DESC);
-- Now every page is one seek plus twenty sequential rows. Page 5 000 costs
-- exactly what page 1 costs.

What keyset pagination cannot do

⚠ Be honest about this in an interview
  • No “jump to page 47”. You can only go forward and back from where you are. For infinite scroll and “next page” that is fine; for a numbered pager it is not.
  • No total page count without a separate COUNT(*), which on a large filtered set is itself expensive. Approximate counts (reltuples, sys.dm_db_partition_stats) or "showing 1–20 of many" are the usual compromises.
  • The sort must be total, and the sort columns must be stable — you cannot keyset-paginate by a column that changes while the user is paging.
✔ Keyset has one advantage nobody mentions

It is correct under concurrent inserts. With OFFSET, a row inserted before your position while you are reading shifts everything down by one, so page 2 repeats the last row of page 1 — and a deleted row skips one entirely. Users report it as "duplicates in the list" and nobody can reproduce it. Keyset pagination anchors on a value, not a count, so this cannot happen.

API cursors are keyset pagination with a wrapper

-- Encode the bookmark opaquely so clients cannot construct one, and so you can
-- change the sort later without breaking them.
{ "items": [...],
  "nextCursor": "eyJhdCI6IjIwMjYtMDMtMTRUMDk6MTIiLCJpZCI6ODgxfQ" }
-- base64 of {"at":"2026-03-14T09:12","id":881}
Sign it, or at least treat it as untrusted

A cursor is user input that goes straight into a WHERE clause. Base64 is not encryption — anyone can decode, edit and re-encode it. Bind it as a parameter like any other input (chapter 34), and if the cursor carries filter state as well as position, sign it, or a client can page through data they should not see. 

-- In the playground, compare what each has to read.
EXPLAIN QUERY PLAN
SELECT * FROM orders ORDER BY placed_at DESC, id DESC LIMIT 20 OFFSET 1500;

EXPLAIN QUERY PLAN
SELECT * FROM orders
WHERE (placed_at, id) < ('2025-06-01T00:00:00Z', 0)
ORDER BY placed_at DESC, id DESC LIMIT 20;
  1. OFFSET n costs O(offset + limit): it produces and discards every earlier row.
  2. Keyset pagination anchors on the last row's sort values and costs the same on every page.
  3. The sort must be total — add a unique tie-breaker such as the primary key.
  4. Row-value comparison (a, b) < (x, y) is sargable; the hand-expanded OR form usually is not.
  5. SQL Server has no row-value comparison. Write the expanded form and verify the plan.
  6. Index on exactly the sort columns, in the sort direction.
  7. Keyset cannot jump to an arbitrary page and cannot cheaply give a total count. Say so.
  8. Keyset is also correct under concurrent inserts; OFFSET silently duplicates and skips rows.
  9. An API cursor is untrusted user input. Parameterise it, and sign it if it carries filter state.

Interview questions this chapter answers

Why is page 5 000 slow?

Because OFFSET is not a seek — the engine has to generate the first 100 000 rows in sorted order and throw them away. The cost is proportional to the offset, so it grows as the user pages. Keyset pagination replaces the count with a value comparison and is flat.

Implement keyset pagination.

Order by a total sort — the display column plus a unique tie-breaker — and filter with a row-value comparison against the last row of the previous page, with an index matching the sort. And I would say what it costs: no jumping to page 47, and no cheap total count.

A user reports seeing the same record on two consecutive pages. Why?

Either the sort is not total, so equal-valued rows come back in a different order each query, or rows are being inserted while they page and OFFSET is shifting the window. Both are fixed by a stable total sort, and the second is fixed properly by keyset pagination.
