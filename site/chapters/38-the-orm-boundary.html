The ORM boundary

What Hibernate, EF and Eloquent actually generate, N+1 seen from the database side, and when to drop to SQL.

No advert asked for this

Most SQL you will be handed to fix was generated by an ORM. Reading it back is a distinct skill.

Why this is your problem

🧒 Simple

Somebody else's machine wrote the letter. It is your job to read it back and say why the postman is taking so long — even though you did not choose a single word of it.

🎓 Professional

Most SQL you will be handed to fix was generated by Hibernate, Entity Framework, Eloquent or Doctrine. Nobody wrote it; it came out of an object graph. So reading generated SQL back to the code that produced it is a distinct skill from writing SQL, and it is the one the person asking for help does not have. It is also why the database developer is often the most useful person in a performance conversation about an application they did not build.

N+1, from the database side

// The code. It looks completely innocent.
var orders = db.Orders.Where(o => o.CustomerId == 42).ToList();
foreach (var o in orders)
    Console.WriteLine(o.Lines.Count);        // ← lazy load, once per order

-- What the database sees:
SELECT * FROM orders WHERE customer_id = 42;                 -- 1
SELECT * FROM order_lines WHERE order_id = 1;                -- 2
SELECT * FROM order_lines WHERE order_id = 2;                -- 3
...                                                          -- N+1
⚠ Why you will not find it in a slow-query report

Every one of those queries is fast — a single-row index seek. Nothing exceeds a slow-query threshold, and sorting by average duration puts them at the bottom. They only appear when you sort pg_stat_statements or sys.dm_exec_query_stats by total time and notice one statement with a call count in the millions. That is the diagnostic: a high call count on a trivial query.

✔ What to tell the application developer

Not “your ORM is bad” — a fix they can apply: eager-load the collection. .Include(o => o.Lines) in EF Core, JOIN FETCH in JPQL, ->with('lines') in Eloquent, selectinload() in SQLAlchemy. That turns N+1 into one or two queries. Naming the exact method for their stack is the difference between being consulted again and not.

The other four ORM shapes you will meet

1 · The Cartesian explosion from over-eager loading

-- .Include(o => o.Lines).Include(o => o.Payments)
-- becomes one query joining BOTH collections: 2 lines x 3 payments = 6 rows per
-- order, every order column repeated six times. The fan-out of chapter 08, over
-- the wire. EF Core calls the fix "split queries"; Hibernate needs two fetches.

2 · SELECT of every column, always

An ORM materialises entities, so it selects every mapped column whether or not you use them — which is SELECT * with all of its consequences, including defeating a covering index. The fix is projection: select into a DTO (.Select(o => new { o.Id, o.Total })) so only those columns are requested.

3 · Client-side evaluation

// A filter the ORM cannot translate is sometimes applied IN MEMORY —
// after fetching the whole table. EF Core 3+ throws instead, which is a mercy.
.Where(o => MyHelper.IsInteresting(o))     // not translatable to SQL

4 · Parameter type mismatch

The classic .NET/SQL Server incident: the ORM binds a string parameter as NVARCHAR against a VARCHAR column, forcing an implicit conversion of the column and losing the index seek — on a query that is otherwise perfect. The plan shows a convert warning; the code shows nothing at all. See chapter 07.

Seeing what it really sends

-- The application side (ask for this first — it is the fastest route):
--   EF Core:     LogTo(Console.WriteLine) with EnableSensitiveDataLogging
--   Hibernate:   show_sql, or the org.hibernate.SQL logger
--   Eloquent:    DB::listen(...)
--   SQLAlchemy:  echo=True

-- The database side, when nobody can turn logging on:
SELECT calls, total_exec_time, mean_exec_time, rows, left(query, 150)
FROM pg_stat_statements ORDER BY calls DESC LIMIT 20;    -- ← sort by CALLS for N+1

SELECT TOP 20 qs.execution_count, qs.total_worker_time/1000 AS cpu_ms,
       SUBSTRING(t.text, 1, 150) AS sql
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) t
ORDER BY qs.execution_count DESC;

When to drop to SQL

🎓 The honest boundary

An ORM earns its place on the write side: change tracking, unit of work, identity map and relationship graphs are genuinely hard to hand-write and genuinely useful. It earns much less on the read side, where you want a specific shape rather than an object graph. So the common, sensible architecture is:

  • Writes through the ORM. Loading an aggregate, changing it and saving it is what it is for.
  • Reads that are reports, exports or dashboards: hand-written SQL into a flat DTO. Faster, clearer, and reviewable — you can read it and know exactly what it costs.
This is CQRS, without the ceremony

“Different model for reading than for writing” is the whole idea, and it does not require event sourcing, a message bus, or two databases. Saying it plainly — “I would keep writes going through the ORM and write the reports as SQL” — is a strong, unpretentious answer to a question that often attracts an architecture lecture.

✔ And do not be the person who says "ORMs are bad"

You will be interviewed by people whose codebase is an ORM. The useful position is: they solve a real problem well, they hide costs that only become visible from the database side, and part of your value is making those costs visible early — with the fix expressed in their framework's vocabulary, not as a suggestion to remove it.

  1. Most SQL you are asked to fix was generated. Reading it back to the code is a distinct skill.
  2. N+1 shows up as a huge call count on a trivial query, never as a slow query.
  3. The fix is eager loading, named in the developer's own framework.
  4. Two eager-loaded collections in one query is a Cartesian explosion; split the queries.
  5. An ORM selects every mapped column. Project into a DTO when it matters.
  6. Untranslatable predicates get evaluated client-side, after fetching everything.
  7. Parameter type mismatch silently defeats an index and looks like nothing at all.
  8. Sort by call count for N+1; sort by total time for everything else.
  9. ORM for writes, hand-written SQL for reports. That is CQRS without the ceremony.

Interview questions this chapter answers

What is the N+1 problem and how do you spot it?

One query for a collection, then one more per item because of lazy loading. From the database it looks like a trivial query with a call count in the millions — so you find it by sorting query statistics by call count or total time, never by average duration. The fix is eager loading, and I would name the specific method for their framework.

Would you use an ORM?

For writes, yes — change tracking and unit of work are genuinely valuable and tedious to hand-write. For reports and exports I would write SQL and project into a flat type, because there I want a specific result shape rather than an object graph, and I want to be able to read what it costs.

The developers say the ORM is slow. What do you do?

Ask them to turn on SQL logging, or look at query statistics sorted by call count and total time. It is usually one of four things: N+1, a Cartesian explosion from two eager loads, selecting every column and defeating a covering index, or a parameter bound as the wrong type. All four have a fix inside the ORM, which is what I would hand back.
