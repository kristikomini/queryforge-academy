The queries that are always slow

A checklist of ten shapes. If a query is slow, it is almost certainly one of them.

From the advert

“Ottimizzazione e tuning delle query” — this chapter is the checklist. If a query is slow, it is almost certainly one of these ten shapes.

🧒 Simple

Most slow things are slow for boring reasons. Before you invent a clever explanation, check the ten boring ones — the same way a mechanic checks the fuel before rebuilding the engine.

🎓 Professional

The ten shapes below are not a miscellany — they fall into three families, and naming the family is usually enough to find the fix. Predicates the optimiser cannot use (1, 2, 7): the query could seek and does not. Row-at-a-time work (4, 5, 6): a set-based engine being asked to behave like a loop, once per row. Doing more than was asked (3, 8, 9, 10): reading columns, rows or groups that the caller never uses. A slow query is nearly always one of those three sentences, and saying which one — before touching the plan — is what makes the diagnosis quick.

1 · A function wrapping the filtered column

The commonest single cause. See chapter 07.

2 · Implicit conversion

Invisible: the query is correct and returns the right answer, merely a hundred times slower. Very often introduced by an ORM binding NVARCHAR against a VARCHAR column.

3 · SELECT *

Three costs, ascending in importance: bytes nobody asked for; forced off-page LOB reads; and — the real one — it prevents a covering index from covering, turning an index-only scan into a seek plus a lookup per row. It also breaks silently when someone adds a column.

4 · N+1

⚠ Why this one hides

Every individual query is fast, so nothing appears in a slow-query log and nothing looks expensive in a plan. It only surfaces when you sort the plan cache by total duration, or count round trips. At 0.5 ms of network per call, 500 calls is a quarter of a second of doing nothing at all. See chapter 38.

5 · A cursor or a row-by-row loop

Ten thousand statements, ten thousand plans looked up, ten thousand log records. The set-based equivalent is one statement. The rare legitimate cursor: calling an external procedure per row, or deliberately batching a huge update to avoid lock escalation — and in that case say so in a comment, because the next reader will assume you did not know better.

6 · Scalar user-defined functions in the SELECT or WHERE

Before SQL Server 2019, that function was executed once per row, with no costing, and it made the whole query serial. Inlining (2019+) helps, but only for functions simple enough to inline. The portable fix is to express the logic as an inline table-valued function used with CROSS APPLY, or as a plain expression.

7 · OR across different columns

8 · OFFSET deep in a result set

See chapter 30 for keyset pagination.

9 · COUNT(DISTINCT …), several times, on a dashboard

Each one needs a sort or hash of all values and none of them parallelise well. Four in one query is four times the cost. Pre-aggregate, or use an approximate count for a dashboard tile.

10 · The optional-parameter WHERE

One cached plan for every combination of supplied parameters. Fix with OPTION (RECOMPILE) or safe parameterised dynamic SQL.

The order to check them in

✔ Two minutes, before opening a plan
  1. Is the filtered column wrapped in anything? (1, 2)
  2. Is this one slow query, or many fast ones? (4) — sort by total duration.
  3. Is there a loop, a cursor or a scalar function? (5, 6)
  4. Does it return far more columns or rows than the caller uses? (3, 8)
  5. Only then: open the actual plan and look for the estimate gap (chapter 27).
⚠ The other four causes, which are not query shapes at all

If none of the ten fit, the problem is probably not the query: blocking (chapter 23), a bad cached plan (chapter 28), missing statistics (chapter 28), or the server — memory pressure, a saturated disk, another workload. Chapter 42 is how to tell which, and looking there before rewriting SQL saves a lot of wasted rewriting.

  1. Ten shapes cover almost every slow query. Check them before theorising.
  2. A function or a conversion on the filtered column is the single commonest cause.
  3. SELECT *'s real cost is that it stops an index covering the query.
  4. N+1 is invisible in every per-query report. Sort by total duration to see it.
  5. A cursor is ten thousand statements. If one is genuinely right, comment why.
  6. A scalar UDF in a predicate is a black box: no estimate, no parallelism, once per row.
  7. Deep OFFSET reads and discards everything before the page.
  8. Several COUNT(DISTINCT)s in one query multiply an already-expensive operation.
  9. If none of the ten fit, look at blocking, plans, statistics and the server before rewriting SQL.

Interview questions this chapter answers

Give me some common causes of slow queries.

Non-sargable predicates — a function or an implicit conversion on the filtered column; N+1 from the application; SELECT * defeating a covering index; cursors and scalar UDFs forcing row-at-a-time work; deep OFFSET pagination; and the optional-parameter WHERE that caches one plan for every shape. If none fit, it is usually blocking, a bad cached plan, or the server.

Why avoid SELECT * in production code?

It moves bytes nobody needs, can force off-page LOB reads, and — most importantly — prevents a covering index from covering, so a cheap index-only scan becomes a seek plus a lookup per row. It also silently changes behaviour when someone adds a column.

When is a cursor acceptable?

When each row genuinely requires a separate external action — calling a procedure, sending something — or when you are deliberately batching a huge update to avoid lock escalation. Both cases deserve a comment saying so, because the default assumption on reading a cursor is that the author did not know the set-based form.
